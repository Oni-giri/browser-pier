# BrowserPier — Spec

**Version:** v0.4 · 12 Nov 2026
**Status:** v1 shipped (0.1.5); v1.1 next (see Jira, label `v1.1`)
**Repo:** https://github.com/Oni-giri/browser-pier
**Images:** `ghcr.io/oni-giri/browser-pier` (orchestrator) and `ghcr.io/oni-giri/browser-pier-chromium` (browser)
**Tracking:** Jira epic [PROJ-1](https://geistlogic.atlassian.net/browse/PROJ-1)

Self-hosted, persistent browsers for AI agents. Agents start a browser when they need one, it keeps its cookies and logins, and it stops afterwards to free RAM. A human steps in only to log in or clear a 2FA prompt or a captcha.

---

## 1. Goals and non-goals

### Goals

- A real browser reachable from any web browser, natively: no VNC client and no dedicated VM.
- Runs in Docker anywhere: a generic docker-compose for any VPS or server, plus an Umbrel app (the author's own setup).
- About 99% of driving is done by agents. The human only logs in, handles 2FA, solves captchas or takes over when an agent is stuck.
- Two ways to drive:
  - **API mode:** CDP, for Playwright, browser-use and similar.
  - **Visual mode:** screenshots and the page's element tree from Chromium's accessibility (no CDP), plus OS-level mouse and keyboard, for sites with heavy anti-bot measures.
- Persistent profiles: cookies, logins and local storage survive stops, restarts and updates.
- On-demand browsers: start when an agent asks, stop when idle, so an idle profile uses no RAM.
- A simple web UI and an API to create, list, start, stop and delete profiles and sessions.

### Non-goals

- Multi-user or multi-tenant use. There is one human admin.
- Guaranteed anti-bot bypass. The setup improves the odds; no setup beats every system.
- Fingerprint spoofing. Each profile is a real, stable browser; a fingerprint that changes between sessions is itself a red flag for logged-in accounts.

### Deployment targets

- **Private** (Umbrel or a home server behind Tailscale or a VPN): the safest setup and the recommended one.
- **Public VPS:** supported, with HTTPS required. Expect a datacenter IP, so residential proxies matter much more there.

---

## 2. Why build it rather than use an existing tool

| Option | Good at | Why not, for this use |
|---|---|---|
| Neko | Smooth WebRTC browser in a tab; one long-lived profile. | Built for humans. CDP for agents needs workarounds (config override, policy file, socat relay) that are fragile across image updates. |
| Steel Browser | Agent-first: session API, native CDP, live viewer. | The API server is always on (about 4 GB recommended). Self-hosted profiles share one directory because of an open bug (#347), so separate logins per service aren't possible. One browser per container, headless by default, and both the live viewer and stealth are CDP-based. |

**Decision:** a small custom orchestrator that starts one browser container per session and stops it afterwards. Several ideas from Steel are adopted (see the credits at the end).

---

## 3. Architecture

- **Orchestrator**, always on and lightweight: one Go binary that serves the API, the web UI and an MCP endpoint. It starts and stops browser containers through the Docker SDK and keeps state (profiles, tokens, sessions, handoffs) in SQLite.
- **Web UI:** Go templates with htmx for live updates, embedded in the binary, with no JS build step. Live view and handoff use a small vanilla JS WebRTC client.
- **Browser container**, one per running session: headful Chromium on a virtual display (Xvfb) with no automation flags, on a minimal desktop: a window manager (JWM) and a taskbar. It has OS-level input (xdotool) for Visual mode and exposes CDP for API mode. In a Visual-mode container Chromium also publishes its accessibility tree on the container's private session bus (the file chooser portal's, which every container runs), and the entrypoint's tree reader reads it there (PROJ-150, Visual-mode element tree in §8). A small sidecar captures the display, encodes H.264 (GStreamer) and sends it to the orchestrator.
- **Live stream:** WebRTC, served by the orchestrator with pion on a single muxed UDP port (TCP fallback). It relays each container's stream to the viewer and passes mouse and keyboard from the viewer back over a data channel to xdotool. No CDP is involved, so Visual mode stays clean.
  - **Ports and addresses:** `BROWSERPIER_WEBRTC_PORT` (default 7438) is the one UDP port, and the same TCP port is the fallback; `BROWSERPIER_WEBRTC_IPS` sets the addresses to advertise (a VPS's public IP, the Tailscale IP). The live view is the web UI's profile page, `/profiles/{profile}`, for the signed-in admin (`/live/{profile}` redirects there).
  - **TURN (optional):** for viewers on networks that block UDP or direct connections (corporate Wi-Fi, some mobile carriers). `BROWSERPIER_TURN_URLS` names the servers. A viewer gets them, with credentials, from `/live/{profile}/ice` (the signed-in admin) or `/h/{token}/ice` (the browser holding an open handoff link), behind the same checks as the offer, never before.
    - **Credentials:** with `BROWSERPIER_TURN_SECRET`, the TURN REST API's shared secret, each viewer gets its own. Their username's id is a keyed hash of the viewer (the admin's signed-in browser, or the handoff), the same on every request, so the TURN server's per-user quota holds one viewer however often it asks, and the id says nothing of the session or link. They open no new relay after 12 hours for the admin, or a minute after the link expires for a handoff. coturn checks them only when a relay is set up, so an open relay outlives them until it's closed; BrowserPier closes a handoff's live view when the handoff ends. The secret never leaves the orchestrator, and neither it nor a password is logged. A static login (`BROWSERPIER_TURN_USERNAME`, `BROWSERPIER_TURN_PASSWORD`) is for services without the REST API.
    - **The orchestrator doesn't relay:** viewers' relayed candidates reach its own port. `BROWSERPIER_TURN_PEER_IPS`, the address a TURN server reaches it at (the compose network's, for the bundled coturn), is advertised besides `BROWSERPIER_WEBRTC_IPS` while TURN is on.
    - **Checking it:** `?ice=relay` on the profile page, or on a handoff link's page once it's open, connects through TURN only.
    - Decided 2026-11-12 (PROJ-22).
  - **Streaming:** a browser's stream is read only while someone watches, so an unwatched browser spends nothing on encoding, except for a recording (below). Each frame is one sample; x264 writes one slice per frame.
  - **Recording** (PROJ-23): a profile with **Record sessions** on keeps what agents do on its screen, for the admin to replay. It is off by default, and only the admin sets it, in the web UI: no REST or MCP call reads, lists, starts, stops or turns off a recording, since an agent that could would hide what it did.
    - **A pipeline of its own:** the control socket's `GET /record` runs a second GStreamer pipeline, separate from the live one, while the orchestrator reads it (one reader; SIGTERM, then a kill, when it stops). It captures the X display as the live stream and screenshots do, with no CDP in either mode: at most 5 frames a second, scaled to 3/4 of the screen, H.264 (High profile) at constant quality (x264 `pass=qual`, factor 28, `veryfast`, one thread and `zerolatency`, so a frame leaves the encoder as it comes: about 0.4 s from the request to the first frame), muxed as fragmented MP4 (`mp4mux fragment-duration=200 streamable=true`): about one frame a fragment, each whole on its own. Its arguments are fixed words and the scaled size, computed from the screen's checked numbers. Watching and recording at once run two pipelines; the live stream is unchanged.
    - **When:** only while the one gate (`recording.Gate.Decide`) says so: the setting is on, the session is Running (not starting, stopping or with a person for a handoff), no person has control, and an agent is acting (a CDP connection open, a page call or an input action under way, Visual mode's `visual_snapshot` and click by ref included) or acted in the last 30 s. The session manager asks the gate again, under its lock, at every change to what it reads. Recording is not watching and not activity: a recorded browser stops as idle as any other, and a stop doesn't wait for it beyond closing the segment under way.
    - **Never during a person's control:** Take control and a handoff's opening (Needs help) close the gate under the session manager's lock, before they return and before a person's input can reach the page (the live view forwards input only after Take control succeeded). The recorder's state flips at once; the segment under way ends at the last fragment received whole before, and every byte after is dropped, not flushed; the pipeline stops afterwards, so the person isn't kept waiting. A handoff pauses recording from its opening until it ends, whether or not anyone has opened the link. It stays closed until the person's control has wholly ended: however it ends, the gate is asked again only once the end of the takeover has emptied the browser's clipboard (§11, The live view's clipboard) and agents have the browser back, never during that wait. Afterwards recording waits for the agent's next action (the 30 s tail from before doesn't carry over), in a new segment from a new keyframe. `Manager.PauseRecording` holds it off for BrowserPier's own work; PROJ-57 decides whether vault fills use it.
    - **Segments:** each is an MP4 that plays alone: ftyp, moov, then moof and mdat pairs, starting with a keyframe (each stream is a fresh pipeline, so the first fragment is one), with the pipeline's real timestamps; at most 30 s and 8 MiB. A still screen sends fragments of a few dozen bytes (x264's skip frames); after 3 s of them the segment ends, nothing more is kept, and the next change starts a new segment, so stillness makes a gap, not bytes. Each segment is written under a temporary name and renamed when whole.
    - **What a new segment costs:** a segment ends by closing the stream and opening the next, for a fresh keyframe (the container lets the next reader wait up to 2 s for the last pipeline to exit, and the recorder retries every 50 ms for a second). The fragment that ended it and the new pipeline's start aren't recorded: measured, a rotation after 30 s loses about 0.6 s, and a change after a still stretch is recorded from about 1 s after it. The index marks both as `restart` gaps.
    - **The orchestrator reads box sizes and nothing more.** The container isn't trusted: every box is capped (256 KiB for the stream's head and a fragment's moof, 8 MiB for a segment, 24 MiB a minute for a session), as are the boxes it may skip (8 in a row) and the segments (20 a minute and 10,000 a session); a stream that ends by itself within 3 s backs the next off, doubling up to 30 s. A stream over a cap, or that isn't the MP4 it should be, is cut and tried again 30 s later (a minute for the per-minute caps), with one warning a session; past 10,000 segments the session isn't recorded any more. Errors from the container's control socket are logged by status only. It never decodes video.
    - **The index:** each session's `index.json` lists its segments (wall-clock start and end, size) and its gaps, each with its reason: `person` (Take control), `handoff`, `idle` (no agent for 30 s), `still` (nothing changed on screen), `stopped`, `lost` (no room, a broken stream, a cap), `restart` (a new segment starting), `off` or `paused`. Times, sizes and reasons only: no page text, title or URL, in the index or the log.
    - **Cost**, measured 2026-11-18 on a 1280×800 screen (960×600 recorded) in a Podman VM: the pipeline uses about 3.5% of a core on a still page, 4.4% while a long page scrolls and 3.3% with a canvas animation playing, and about 33 MB of the container's memory; it writes nothing on a still page (39 kB in 10 minutes, the taskbar clock's changes), about 48 MB an hour scrolling and about 87 MB an hour of animation. Paused or with no agent acting, no pipeline runs.
  - **Control:** a person takes control to send mouse and keyboard. It is refused while an agent is driving: connected over CDP, with a page read under way (snapshot, find, page content and the other page tools but act, each bounded by its own timeouts), in the first 3 seconds of an input action or of an `act` call, or having clicked or typed in the last 5 seconds, counted from the action's end. An input action or an `act` call that has run 3 seconds or more (human-paced typing can take a couple of minutes) is broken off instead, as a handoff breaks it off (whatever it held is released, the agent's call answers 409 and the activity log says "Typing interrupted" or "Input interrupted"; act's 409 lists the steps that ran and says in which step a person took control, and the log says "Actions interrupted: a person took control (N of M steps ran)"), and the person gets the browser once it has ended: unless the browser began to stop meanwhile (even if that stop has since failed), when Take control gives up and leaves the browser to agents should the stop fail, or control was handed back meanwhile (the profile page's Hand back), when it fails too. An agent runs one input action at a time in a session: another sent meanwhile is refused (409, "another input is still running"), so an agent can't queue up minutes of input. While a person has control, agents can only watch: their input and new CDP connections are refused, and open ones close. Esc releases the keyboard; leaving the page or losing focus lets go of any held key or button (while the browser is stopping, it ends the person's control instead, as any input then does). However a person's control ends (their Hand back, a handoff ending or expiring, the profile page's Hand back from another tab, the live view closing or its input channel closing while the video stays connected), any key or button they still hold is let go first, so whoever drives next doesn't inherit a pressed one (a drag when a handoff expires); a lift the browser fails is tried again before the clipboard is emptied, and the browser forgets a held key only once its release is known to have run: an xdotool that exited cleanly after it, or a synchronous release of its own; a release written to an xdotool that died before it ran goes first to the next one, or the hand-back runs it itself; if xdotool had to be killed with input still queued, everything held is let go that way, and a fenced lift that can't let go of its keys answers 500, not 200. A browser picked up after BrowserPier restarts gets the same: held keys let go, then, a tenth of a second later, the clipboard emptied. Whatever the person's live view sends names their takeover, whose number BrowserPier saves before handing it out, and as their control ends the browser fences it (PROJ-196): the hand-back's lift has the browser refuse, with 409, anything from that takeover or an earlier one from then on, however long it was held up on its way or inside the browser, checked right before it acts; an action already under way in the browser finishes first, the live input it had queued in xdotool is run before it answers, and the lift and the emptying that follow undo them. Only a 200 answer giving the fence counts as fenced (an older browser image, which would answer otherwise, is never taken as fenced). On BrowserPier's side, what the live view still has under way is broken off at once, and a live view whose operation the browser refuses gives its control up and stops sending. Agents get the browser back only once the browser has fenced the takeover: the lift is tried, a little later each time, until it answers or the session ends. An operation that never returns can do nothing to the browser after that, so the hand-back goes on after 30 seconds without it. A hand-back is over before whatever started it says so: the live view's Hand back, the profile page's, a handoff's Done or a withdrawal answers once agents have the browser, or, if its request ends first, says the browser is still being handed back, the hand-back going on to its end with agents kept out. One handoff's end runs at a time; another end of it joins it and gets its outcome. The sweep ends each expired handoff on its own, so a browser that doesn't answer holds up no other handoff, and a browser whose hand-back is stuck counts as idle from when it began, whoever watches, so idle stop, the memory limit and Stop can still stop it, which ends the hand-back (the container, and its clipboard, go). Each cleanup names the takeover it is for, and the browser leaves alone a later takeover that has begun meanwhile (its held keys, its clipboard): a lift or emptying held up past its time does nothing to the next person. After a restart, BrowserPier fences the highest takeover it saved, numbers its own above it, and puts a browser left waiting for help with no open handoff back to Running; a browser that doesn't fence within 10 seconds is stopped, logins kept, rather than handed to agents unfenced. A live view drives and hands back through its one input data channel (the first labelled `input`): any other channel is closed unheard, and closing one hands nothing back. A view given control at its offer (a handoff link) that opens no input channel within 30 seconds of getting it loses it. A handoff's live view is for the session the link was opened in, and for that handoff: if the session has ended and the profile started again, or the handoff itself has ended (even while the offer was under way), its offer, and any later take from it, is refused in the same step as the take, and the agent's browser is never taken back. A handoff page closed and reloaded gets control back once the closed page's hand-back is over (its live view stays counted until then, and the reload waits for it, a few seconds at most). A handoff is stored only with the help epoch it opened (the browser goes to Needs help first, then the row is written with it), a restart gives an open handoff its browser's epoch, a handoff whose epoch doesn't match its browser's still ends the help its browser waits for if that help is no newer than the handoff's, never a later handoff's (logged), and a handoff left open whose browser no longer waits for its help (its end cut short by a restart) is ended, cancelled, the next time it is looked at. A handoff ending stops the browser waiting for the help that handoff asked for, and only that, and begins to end its helper's control in one step, so a takeover begun after it (an admin's), or help another handoff asked for, is never ended by it; a browser already waiting for help refuses a second handoff. Control belongs to the takeover that took it: a live view whose control ended elsewhere can't use or end the next person's (§11). Whatever BrowserPier sends to the browser for a person's control (their input, the lift, emptying the clipboard) belongs to that session: a session's end breaks off and waits for it before the profile can start again, so none of it reaches the profile's next browser.
  - **Input safety:** input reaches the browser as structured events (move, button, wheel, key by X keysym name; printable characters as Unicode keysyms, so the viewer's own layout types), fed to one long-running `xdotool`. Every command is built in the container from checked values; nothing a viewer sends becomes script text.
  - **Agents' Visual-mode input** goes through the same checks: each xdotool run's arguments are xdotool's own words, checked integers (pixels, the button) and pauses BrowserPier computes (among them the constant pause after a shortcut inside a key list, PROJ-151), and key names from a fixed table or checked as X keysym names. At human pace (PROJ-113, see §8) typed text becomes one `keydown`/`keyup` pair per character, named from a fixed US-keyboard table; a character with no entry there (`é`, an emoji) keeps the instant path's `type -- <character>`, on its own and last in its run, as typed text always went before. Each run lasts at most about 20 s (typing is split into runs of 8 keys) and is killed when the request ends; a run that fails or is cut short is followed by the release of what it may have held (`mouseup`, or `keyup` of its keys). The pointer's starting point is read from X (`xdotool getmouselocation`) before each glide, so it starts wherever the last action or a person in the live view left it; only before any action has moved it does a pointer in the middle of the screen, where X puts it at start, come in from an edge instead. The live view's own input (`live.go`) is unchanged; the phone's Type button types its text at instant pace, and text is pasted through the clipboard box (§9, Live view), not typed.
  - **Phone:** tap to click, pinch to zoom, and Type, Fit and Clipboard buttons. Type types at instant pace, so a field that refuses pasting still takes it; the clipboard box pastes.
  - **Idle:** a browser someone is watching is never stopped as idle.
- **Session bus and file chooser portal** (PROJ-152; in every browser since PROJ-181): before Chromium starts, the entrypoint starts a private `dbus-daemon` (the image's own, its child, with BrowserPier's config: one `unix:path=` socket in a 0700 folder of the browser's uid, `/tmp/browserpier-bus-<uid>`, EXTERNAL authentication, no TCP, no abstract socket, no service directory) and owns `org.freedesktop.portal.Desktop` on it, replacement refused. It serves `org.freedesktop.portal.FileChooser` only (version 4); every other interface, its properties included, answers D-Bus's standard unknown-interface error. Chromium, the only process given `DBUS_SESSION_BUS_ADDRESS`, then asks the portal for every file chooser and "Save as" instead of showing its GTK dialog, with no switch (measured in `images/chromium/ANTI-BOT.md`). The portal answers only the Chromium the entrypoint started and its descendants: by the caller's pidfd (`ProcessFD`, Linux 6.5 on), read again after the walk up its parents, or else by its pid with the start time compared before and after (logged once at start). `OpenFile` waits, at most 4 at once, until an agent or the person in control answers it with files from `/files/uploads` (§8, File choosers), it is cancelled, Chromium closes it (the tab went away), Chromium exits, or 5 minutes pass (`BROWSERPIER_CHOOSER_TIMEOUT`, for tests), counted again from each change of hands (the control socket's `POST /chooser/restart`); a folder chooser and `SaveFiles` are refused. While one waits, the X focus goes to the taskbar, as a dialog would take it, and comes back after. `SaveFile` is answered at once with a new file in `/files/downloads` (§8). Both modes have it: the chooser is the same for a person in either. Chromium aborts when its session bus goes, so the bus stops only after Chromium has closed (Graceful shutdown). A bus or name that can't be had at start fails the browser's start, saying why: Chromium's fallback, its GTK dialog, lets whoever drives it hand a page any file the browser can read, the profile's cookies included (PROJ-183), and the bus is as vital as Xvfb anyway. Decided 2026-11-18 (PROJ-152); always on and failing closed since PROJ-181.
- **Profile folder**, one per profile: `profiles/<name>/` in the data dir, bind-mounted into the browser container as Chromium's user data directory. It outlives every container, and backing up the data dir backs up every profile. Browser containers run as the orchestrator's own user, so it can read profile files (downloads, export) without a helper container; an orchestrator running as root starts them as uid 1000 instead, since Chromium won't run as root with its sandbox on.
- **Host path:** bind mounts are resolved by the Docker daemon, so the orchestrator needs its data dir's path on the host. When it runs in a container it reads that from its own container's mounts; `BROWSERPIER_HOST_DATA_DIR` overrides it. Before each start the orchestrator writes a marker into the profile folder, and the browser container refuses to start if it doesn't see it, so a wrong path fails loudly instead of opening an empty profile.
- **Proxying:** CDP, the live stream and the visual endpoints are reached only through the orchestrator, behind token checks. Browser containers publish no ports.
- **Control socket:** the container's entry process listens on a Unix socket in a folder shared only with the orchestrator (`profiles/<name>/run/`, so each container sees only its own), never on a network port, so neither pages nor other browser containers can reach it. It relays CDP (headful Chromium binds it to the container's own loopback), serves the H.264 stream, the recording stream (`GET /record`, PROJ-23), Visual-mode input and screenshots.
- **Sandbox:** Chromium's own sandbox stays on. It needs user namespaces, which Docker's default seccomp profile blocks, so the orchestrator starts browser containers with BrowserPier's seccomp profile: Docker's default plus namespace creation. Containers drop every capability except `SYS_CHROOT`, which the sandbox uses inside its own user namespace, and run with `no-new-privileges`. Never `--no-sandbox`. The GPU process, which handles WebGL calls, shaders and compositing for pages, has Chromium's own GPU seccomp policy on top of the container's (`chrome://gpu`: `Sandboxed: true`; two filters in its `/proc` status). Chromium starts that sandbox only once GL has started, and only in a single-threaded process, so Chromium's environment keeps Mesa from starting threads that early: `LP_NUM_THREADS=0` (llvmpipe draws on the GL thread, with no rasteriser threads) and `MESA_SHADER_CACHE_DISABLE=true` (no disk-cache writer thread; the cache was lost with the container anyway). `--gpu-sandbox-failures-fatal=yes` makes a GPU process that still can't sandbox itself exit instead of running on, so after its restarts Chromium falls back to a GPU process without GL, sandboxed, and pages get no WebGL; the image build checks Mesa knows both settings (their names are in its library), and `TestBrowserEnvironment/gpu` checks they work: the sandbox is on. Before PROJ-165 the GPU process ran with the container's filter alone, with SwiftShader as with llvmpipe. Starting the sandbox before GL instead (`--gpu-sandbox-start-early`) doesn't work here: ANGLE then can't open the X display and GL fails. If a GPU process still exits for want of its sandbox (Chromium waits for its threads first, and logs a FATAL line when they stay), the entrypoint logs one warning saying pages can lose WebGL if it keeps failing. The GPU process's FATAL line is then not taken, later, for the reason the browser ended: that reason is a FATAL line (its level read from Chromium's prefix) from the 3 seconds before the browser ended (or the quarter second after it exited, for output still in the pipe; when startup is given up, read before Chromium is closed), the browser process's own (the pid in its prefix) before a child's, as when a zygote that can't set up the sandbox takes it down. The window also keeps a line a compromised child writes in the browser's name from standing for a later exit (PROJ-186). The cost: WebGL gets one core instead of all of them, so a light WebGL page draws at about half the frame rate, and a scene that kept every core busy about as many times slower as the host has cores (5 times on 6), for that much less CPU; ordinary pages, memory and start-up don't change. Checked on amd64 only; arm64 is a release check (PROJ-187). Decided 2026-11-18 (PROJ-165; measurements in `images/chromium/ANTI-BOT.md`).
  - **AppArmor:** Docker's `docker-default` AppArmor profile has no `userns` rule. Under AppArmor 4 without Ubuntu's user namespace restriction (Debian 13, umbrelOS 2.0), whether that refuses the sandbox its user namespace depends on Docker's profile template. Docker 29.1 and earlier (moby/profiles apparmor v0.1.x) write no ABI line, so the host's AppArmor 4 parser mediates user namespaces, the profile refuses them, and Chromium aborts (`credentials.cc:137 … Permission denied (13)`). Docker 29.9 (v0.2.x) pins the profile to `abi <abi/3.0>,`, which doesn't mediate user namespaces, and the sandbox works under it. Both were seen on Debian 13.5 (kernel 6.12, AppArmor 4.1); versions in between are unchecked. So BrowserPier ships its own profile, `browserpier` (`images/chromium/apparmor/`): moby's `docker-default` (moby/profiles apparmor v0.2.0's template), pinned to `abi <abi/4.0>,`, plus `userns,` and `deny pivot_root,`. ABI 4.0 is the first that mediates user namespaces and the last where `network,` still covers unix sockets; under it, POSIX message queues are mediated too, and refused. io_uring isn't mediated before ABI 5.0; the seccomp profile refuses it.
    - **Loading it** takes root on the host, which the orchestrator doesn't have. The compose file's `apparmor` service (the browser image, as root with only `CAP_MAC_ADMIN`, unconfined, no network, the host's `/sys/kernel/security` and `/etc/apparmor.d` mounted) runs once at each `docker compose --profile apparmor up -d`: it loads the profile and installs it in `/etc/apparmor.d`, so the host loads it at boot. It's opt-in, for Debian 13 and later, because Compose can't even create it where those host paths are missing or can't be mounted (rootless Docker or Podman, hosts without AppArmor, Docker Desktop), and `up` would fail. BrowserPier depends on it with `required: false`, so it starts even when loading fails; the loader also refuses early, with a clear message, when it isn't root in the host's user namespace. On Umbrel, `hooks/pre-start` loads it with the host's own parser at every start of the app, a reboot included, without installing it. The hook carries the profile and the loader itself, since Umbrel's app update copies only the app files it knows (`hooks/` among them, not an `apparmor/` folder). Both load it only where it may be needed: the kernel mediates user namespaces (Ubuntu's kernels say so with a `features/namespaces/userns_create` file, Debian's with that word in `features/namespaces/mask`), the host's AppArmor is 4.0 or later, and Ubuntu's restriction is absent. They load it whatever Docker's version: the check then prefers it. The admin can also load it by hand (deploy/README.md, "AppArmor").
    - **Choosing** at start, unless `BROWSERPIER_BROWSER_APPARMOR` names a profile: where the daemon reports its stock AppArmor profile (`name=apparmor`, or `name=apparmor,profile=default` in newer Docker, not a default the admin set, nor a rootless daemon) and the kernel has no `kernel.apparmor_restrict_unprivileged_userns`, or the daemon is remote (`DOCKER_HOST` set, even to a unix socket, which may be forwarded), the orchestrator runs the browser image's sandbox check in a short-lived container with the browsers' exact settings: a child in new user, PID and network namespaces that then chroots, which takes a capability inside its namespace, as Chromium's sandbox does. It tries `browserpier`, then Docker's default (AppArmor 3, Debian 12, or Docker 29.9's ABI 3.0 profile), then `unconfined`, and uses the first that works; when that isn't `browserpier`, the log line says why `browserpier` failed. The check container runs as the browsers' user, is labelled, has no network or mounts, takes 30 s at most, and is removed after. The browser image says it has the check with the label `io.browserpier.sandbox-check`; an older image is reported as such.
    - **Only a real answer settles the choice.** An option fails only if the daemon couldn't apply the profile or the check itself failed. Anything else (the daemon erring, a timeout, the image missing) leaves the choice unsettled: browsers use the fallback for now, and the check runs again before the next browser start. The orchestrator never pulls the browser image at start; without it, the first browser start pulls it and checks. While unsettled, Reconcile keeps browsers running under any AppArmor choice, so a hiccup doesn't stop them.
    - **Unloaded later** (`apparmor_parser -R`, or a host restart where the profile isn't kept in `/etc/apparmor.d`; on Debian 13 `systemctl reload` or `restart apparmor` leaves it loaded, even when it isn't in `/etc/apparmor.d`; umbrelOS is unchecked): a browser start that can't apply the chosen profile unsettles the choice, and the manager tries once more, which checks again. Unloading a profile with `apparmor_parser -R` also leaves the processes it confined unconfined, at once, and loading it again doesn't confine them again: running browsers stay unconfined until they restart, while their label still says `browserpier`.
    - **Not loaded** isn't fatal: browsers run unconfined, with a warning that says how to load the profile, as before BrowserPier had its own. Refusing would break every Debian 13 server updated without the new compose service. If nothing works, an error is logged and browsers run unconfined (local) or under Docker's default (remote). Everything above (seccomp, capabilities, no-new-privileges) applies whatever the choice.
    - Ubuntu is the other way round: with that restriction, an unconfined process gets a user namespace without the capabilities the sandbox needs, while `docker-default` works. There, and wherever that sysctl exists, browsers keep Docker's profile, unchecked.
    - Containers' definition label includes the AppArmor choice, so a browser started under another choice is stopped when BrowserPier restarts, not picked up.
    - `BROWSERPIER_BROWSER_APPARMOR` names a profile to use instead, unchecked. A named profile that isn't loaded fails each browser start with an error saying so.
    - Decided 2026-11-03 (PROJ-35: unconfined where Docker's profile refuses the sandbox) and 2026-11-12 (PROJ-37: BrowserPier's own profile, checked at start).
- **Chrome launch setup:**
  - Drop `--enable-automation` and set `--disable-blink-features=AutomationControlled`.
  - `--ignore-gpu-blocklist --disable-gpu-compositing`, so WebGL works in a container without a GPU: ANGLE's default OpenGL backend renders it on Mesa's llvmpipe over Xvfb's GLX, as on a Linux desktop without a GPU driver, and pages are composited in software. It's still software rendering, and it says so (`ANGLE (Mesa, llvmpipe (LLVM 19.1.7 256 bits), OpenGL 4.5)` on amd64 with Debian trixie's Mesa 25.0), but it isn't SwiftShader, which detection pages count as headless. Without the first switch Chromium blocks llvmpipe and pages get no WebGL at all. One renderer, no fallback and no override: if llvmpipe can't start on a host, pages have no WebGL, and the image build (the GL libraries and llvmpipe are present and link) and the Docker tests (WebGL and WebGL2 contexts on llvmpipe, a drawn triangle read back and seen on the X display, chrome://gpu, the same renderer after a restart and in another profile) say so. The string follows the image's Mesa and LLVM versions and the host CPU's vector width, so it changes when an image update moves Mesa or LLVM, and a profile moved to a host with another CPU can see another one. Decided 2026-11-17 (PROJ-148; measurements in `images/chromium/ANTI-BOT.md`).
  - `--disable-features=BackForwardCache` (PROJ-160): no back/forward cache, so a page a tab leaves isn't kept whole in memory for an instant Back. With it, a page holding 200 MB was still counted against the RAM limit four minutes after the tab left it (Chromium keeps such a page ten minutes, measured, six pages at most, and drops them early only on a memory-pressure signal, which on Linux comes over D-Bus and never reaches the container). Without it the memory goes within 25 s, and Back loads the page again, from the HTTP cache where it can. The memory a page holds no longer stops another profile's browser or refuses a start for a page nobody is looking at. It is the one `--disable-features`, since Chromium reads only the last; the image build fails if a feature it names is no longer a string in Chromium's binary, and `TestBrowserEnvironment/back` checks the cache is really off. The spare renderer stays on: turning it off saved 6–11 MiB a browser, under the 20 MiB it had to save (ANTI-BOT.md, Memory flags).
  - `--webrtc-ip-handling-policy=disable_non_proxied_udp`, so WebRTC sends no UDP, which would go around the forwarder (see Egress) and, behind a proxy, leak the host IP.
  - No component updates, background networking or first-run screens.
  - `--password-store=basic`, so cookies decrypt the same way in every container and logins survive image updates.
  - "Continue where you left off" (`RestoreOnStartup: 1`, a managed policy), as a person's browser often runs. Without it Chromium drops every session-only cookie (no expiry: a login with "remember me" unticked, many SSO and bank sessions) when it closes, so each stop, the idle auto-stop included, logged such sites out. With it Chromium keeps them, and reopens the tabs it had, with their sessionStorage (except after a session BrowserPier typed a secret into: Filled secrets, §8). A tab left on a form's answer comes back without posting the form again. A crash or `docker kill` still loses what wasn't flushed. Decided 2026-11-15 (PROJ-112).
  - **Visual mode only** (`BROWSERPIER_MODE=visual`, which the orchestrator sets from the session's mode): `--force-renderer-accessibility=basic`, and `AT_SPI_BUS_ADDRESS` with `ACCESSIBILITY_ENABLED=1` in Chromium's environment. `AT_SPI_BUS_ADDRESS` names the session bus every browser runs for the file chooser portal (PROJ-152): one `dbus-daemon` with a generated config, one `unix:path=` listener in `/tmp/browserpier-bus-<uid>/`, a 0700 folder of the browser's uid, EXTERNAL authentication, no service activation, no well-known name but the portal's. There is no second bus: no system bus, no at-spi2-core, no screen reader. The bus starts before Chromium and stops after it has closed; if it dies, Chromium aborts and the session ends, in both modes. API mode's command line and environment have no accessibility switch or variable. The state is fixed for the session: accessibility is never switched on or off while a browser runs. Decided 2026-11-18 (PROJ-150).
  - The window sits at 0,0 with no frame and fills the screen above a 32-pixel taskbar along the bottom, so Visual-mode coordinates are screen coordinates. The taskbar shows a clock only: no menus, key bindings or window buttons, so nothing on the desktop starts a program or kills Chromium, and the window can't be moved off 0,0.
- **Graceful shutdown:** Chrome is closed cleanly and waited on before its container stops, so recent cookie writes are never lost. The entry process runs as PID 1 and handles stop signals itself. On SIGTERM it closes Chrome through CDP's `Browser.close`, not a signal: Chrome's own SIGTERM handler exits before flushing the cookie store, which loses a login made in the last half minute. Only then does it stop the session bus, which Chrome would abort without.
- **Egress:** every connection Chromium makes goes through a small SOCKS5 forwarder in the container (`--proxy-server`, with `--proxy-bypass-list=<-loopback>` so loopback and link-local addresses don't skip it). Chromium resolves no name itself (`--host-resolver-rules`), DNS-over-HTTPS is off by policy, and there is no DIRECT fallback: if the forwarder or the proxy is down, pages fail rather than going out directly.
  - **Chromium doesn't send what is typed into the address bar to the search engine's suggestion service before Return:** search suggestions are off (`SearchSuggestEnabled: false`, a managed policy). That holds whether the typing comes from Visual mode's `key ctrl+l` and `type`, from its `open` action (§8, PROJ-164), which types into the same address bar, or from a person in the live view. Then an address goes to its own host, and anything else is a search on the default search engine (DuckDuckGo, the Debian package's default), as before. With suggestions on, Chromium sent that engine successive prefixes of what was typed, one at each pause (so fewer requests than keystrokes at instant pace): a word in full, an `http://` address or one without a scheme up to its query (the path, and a token in it, included), and an `https://` address's host only; a query (`?token=…`) never went. Address-bar history and bookmarks still suggest, from the profile. Network prediction stays at Chromium's default, and connections weren't timed (ANTI-BOT.md). API mode's `navigate` doesn't use the address bar. Measured 2026-11-18 on Chromium 156 (`TestMeasureSuggest`); decided then (PROJ-191).
  - **The local network is off limits:** pages are untrusted, so the forwarder refuses private addresses (the Docker host through the bridge, its other containers, the LAN; `10/8`, `172.16/12`, `192.168/16`, `100.64/10` where Tailscale lives, `fc00::/7`) and the host's own addresses as `BROWSERPIER_WEBRTC_IPS` gives them. It always refuses loopback, link-local (the cloud metadata endpoint `169.254.169.254`) and addresses that aren't one host. IPv6 addresses that carry an IPv4 one (mapped, NAT64, 6to4) are judged by it.
  - **Without an upstream proxy** it resolves names itself, refuses a name if any of its addresses is refused, and connects to the addresses it checked, so a second DNS answer can't swap in a private one.
  - **Opt-in:** a profile can let its pages reach the local network, for a router's admin page, say. Only the admin sets it, in the web UI; agents can't, through the API. Loopback and link-local stay refused.
  - **With an upstream proxy** (HTTP, HTTPS or SOCKS5, with a username and password), the forwarder adds the credentials (Chrome's `--proxy-server` can't take them) and counts traffic. Host names go on to the upstream proxy to resolve, on its own network, so there only addresses and `localhost` names are checked.
  - The credentials reach the container as a file in its control folder that the entrypoint reads and deletes before Chromium starts, never as an environment variable. The orchestrator removes it when the session ends, in case it was never read.
  - **Limits:** the forwarder stops pages, not a compromised browser process, which still has the bridge; and the host's public address is only known when the admin sets it. Network-level isolation is PROJ-31 (later).
  - **Ad and tracker blocking** (PROJ-119): a profile with Block ads and trackers on has its forwarder refuse connections to listed host names, so pages load faster and agents read less. It is a convenience, not a boundary.
    - **The lists:** the orchestrator downloads `BROWSERPIER_BLOCKLIST_URLS` into `<data dir>/blocklists/` (by default Peter Lowe's ad servers, in the hosts format, and EasyPrivacy) and checks each again every 4 days with a conditional request (`If-None-Match`, `If-Modified-Since`). A 304 keeps the list; a failed download, an answer over 32 MB or one in which no line parses keeps the last good one and is tried again an hour later; a restart reads what is on disk without the network. With nothing downloaded yet (a first start offline) browsers start without a list, and a warning says so once; no browser start waits for a download. Such a session blocks nothing and says so: its `block_ads` is `false` with `ad_list_missing: true` in the API, MCP `start_browser` says no list has been downloaded yet, and the profile page shows **No list yet** (kept in the orchestrator's memory: after an orchestrator restart the session shows plain off). The next browser start after a download blocks.
    - **Parsing** (`internal/blocklist`) keeps the hosts format (`0.0.0.0`, `127.0.0.1`, `::` or `::1` then names), Adblock Plus rules of the exact form `||name^`, and a bare name on its line; everything else (element hiding, paths, wildcards, options such as `$third-party`, exceptions) is skipped and counted. Names are lower-cased, Unicode ones converted to punycode; IP addresses, single labels, names that aren't DNS names and public suffixes (`com`, `co.uk`, `github.io`) are refused, so no list can block a whole top-level domain. Lines over 1 KB are skipped; nothing a list says becomes a pattern, so nothing is compiled from it. The set holds at most a million names (the first million distinct ones, in list order), parsed in a few seconds; two million lines take about 6 s under the race detector. Parsing is fuzzed.
    - **Delivery:** a session that blocks gets the compiled set as `blocklist.txt` in its control folder (`internal/domainset`'s format: a header line, then the names sorted, one a line), mode `0444` and owned by the orchestrator, beside `BROWSERPIER_BLOCK_ADS=true`. Unlike the proxy's file it holds no secret and stays; each start rewrites it, and a session that doesn't block has it removed. The entrypoint reads it once, before Chromium starts (at most 64 MB and a million names, every line checked, in order), and keeps the file's bytes plus 4 bytes a name: about 25 MB for a full set, a few hundred KB for the default lists. A missing or unreadable file starts the browser blocking nothing.
    - **Matching:** after the SOCKS request is parsed and the `localhost` check, before any DNS lookup or upstream dial, the forwarder refuses a host name that is listed or whose parent domain is (`ads.example.com` blocks `x.ads.example.com`, never `notads.example.com` or `example.com`), lower-cased and without a trailing dot. IP literals are never matched by the lists; they stay the egress policy's alone, and every name still goes through `egressPolicy.allows` (or to the upstream proxy) exactly as before. A blocked name never leaves the container. It answers SOCKS code 2 (not allowed), which Chromium shows as a failed request, and counts it apart from the policy's refusals (`blocked` in the control socket's `/proxy/stats`).
    - **The allowlist wins:** challenge and CAPTCHA providers and their subdomains are never blocked, whatever a list says: `challenges.cloudflare.com`, `hcaptcha.com`, `recaptcha.net`, `www.gstatic.com`, `www.google.com`, `captcha-delivery.com` (DataDome), `arkoselabs.com` and `funcaptcha.com`. It is built into the image (`domainset.Allowed`); neither an agent nor a list can change it.
    - **Pages opened directly:** the forwarder sees connections, not which one carries the top-level document, so "a page opened directly always loads" is implemented where BrowserPier knows an address was asked for: the page tools' `navigate` with a URL and `tabs` `new` with one tell the session's forwarder (control socket, `POST /proxy/exempt`) to let that host and its subdomains through for the rest of the session. Only a host the list actually blocks (and the allowlist doesn't cover) is exempted, so the unlisted sites an agent visits use up none of the 256 places; a public suffix (`co.uk`, `github.io`, by the Public Suffix List), which would let through every site under it, is refused, as is a single-label name. Past 256 the forwarder answers 409 and the host stays blocked; the orchestrator and the browser each log a warning, once a session. What the page embeds from other listed hosts stays blocked. The Visual-mode `open` action (§8) tells it too. Limits: an address typed into the address bar some other way (an agent's `ctrl+l` and `type`, a person in the live view), a link clicked, a redirect to a listed parent domain, or a raw CDP client's `Page.navigate` isn't known, so such a page on a listed host fails as a blocked request; the agent then starts the session again with `block_ads: false` (§8).
    - **Turning it off:** only the admin changes the profile's setting. An agent can turn blocking off for one session (`POST /api/sessions` with `"block_ads": false`, MCP `start_browser` with `allow_ads`), a running one included: the orchestrator tells its forwarder (`POST /proxy/blocking/off`), which can't be turned back on until the browser restarts. Agents can't edit the lists or the allowlist.
- **Time zone and language match the exit:** before Chromium starts, the entrypoint asks where it exits, through the proxy if there is one (`BROWSERPIER_GEOIP_URL`, an echoip-style JSON endpoint; default `https://ifconfig.co/json`, which sees each exit IP; self-host echoip to avoid that). Chromium then runs with the matching `TZ`, `LANGUAGE`/`LANG` and an Accept-Language list a person there would send (e.g. `de-DE,de,en-US,en`).
  - The location is stored on the profile. While the country stays the same, the stored time zone is kept, so a rotating proxy doesn't move a logged-in account between zones.
  - **Sticky exits (`{sticky}`, PROJ-153):** many residential providers keep a client on one exit IP while it sends the same session code in its credentials (Oxylabs in the user name, `customer-USER-sessid-<code>`; IPRoyal in the password, `PASS_session-<code>_lifetime-30m`, a code of exactly 8 letters and digits). A proxy URL may hold `{sticky}`, literal and lowercase, in its user name or password, any number of times, and nowhere else. It becomes the profile's own token: 8 characters from `a-z0-9` from `crypto/rand`, given when the profile is created (or, for a profile from before, the first time it is needed) and kept through edits of the proxy, stop and start, and export and import; only **New exit IP** in the profile's ⋯ menu replaces it, while the browser is stopped. So one default proxy gives each profile its own exit instead of one shared by all. The stored and shown proxy stays the template; the orchestrator fills it in only when it writes `run/proxy.json`, so the forwarder and the location lookup both use the filled-in URL. The token is as secret as the proxy's password: never logged, shown or given to agents. A template is checked filled in, under the rules every proxy meets: a SOCKS5 proxy's user name and password are at most 255 bytes each (RFC 1929; Basic authentication, for `http`/`https`, has no limit), and an `http`/`https` user name holds no colon. `%7Bsticky%7D` is a literal, not a placeholder.
  - **What it doesn't promise:** `{sticky}` asks for a stable exit; how long one is kept is the provider's choice, and often short unless the template asks for longer (by default Oxylabs keeps one 10 minutes, or until 60 seconds pass without a request, and `sesstime` asks for up to 24 hours; IPRoyal keeps it for the `_lifetime-` given, up to 7 days), and a provider moves the session to another IP when its exit goes offline. The "same country keeps the time zone" rule above stays the safety net. The token's form fits the providers checked (IPRoyal asks for exactly 8 alphanumeric characters, Oxylabs for a random alphanumeric string); others may want another form, which a template can't change.
  - A profile can set its time zone and language by hand, which wins.
  - If the lookup fails, the stored location is used, with a warning. A proxied profile with nothing stored doesn't start: the error says to set the time zone and language by hand. Without a proxy it starts anyway, in UTC and English, with a warning.
  - **Test proxy (PROJ-154):** a Test button next to each proxy field (New profile, Edit profile, Settings' default) checks a proxy before a browser uses it. The orchestrator starts a short-lived container from the browser image, on the browsers' network, whose entrypoint (`proxy-check`) builds the forwarder for that proxy and does a start's lookup through it, to `BROWSERPIER_GEOIP_URL` and nothing else (it follows no redirect: one counts as a lookup with no usable answer, though a start's lookup follows it), with a start's 5 s lookup timeout, which bounds the whole check (the orchestrator gives the container 30 s in all, then removes it). It answers with the exit IP, country, the time zone and languages a browser there would get (on Edit, the ones this profile's browser would run with), and the time of that one lookup (handshake included; not a ping), or a fixed reason: unreachable, TLS to the proxy, credentials refused, no tunnel, timeout (the 5 s ran out before the tunnel opened), or a lookup that gave no usable answer, in time or at all, once the tunnel was open (the proxy may still work). With the lookup off (`BROWSERPIER_GEOIP_URL=off`) nothing is contacted and the test says it can't run. The proxy goes over as `proxy.json` in a folder of the test's own, never in the container's environment, command or labels; a `{sticky}` template is filled in with the profile's own token on Edit (giving it one if it has none, which it keeps) and a throwaway one on New profile and Settings. The test stores nothing: not the result, not the profile's location, not its time zone or language (the one exception: a profile's first `{sticky}` token, as above). On Edit it says what a start would do: another country than last time gets a note (sites may ask its accounts to verify again), the same country keeps the stored time zone, and a time zone or language set by hand wins; the time zone and languages shown are those.

**Capacity:** plan for 1–2 GB per running browser. Visual mode's accessibility costs tens of MB on an ordinary page (a login form: none measurable; Wikipedia's longest articles: about 30–70 MB; images/chromium/ANTI-BOT.md), which this allows for. The author's Umbrel has 16 GB; a typical 4–8 GB VPS fits 2–4 browsers. A new session must fit under the RAM limit (a setting, default 70% of host RAM) **and** in what the host has free, other apps included (its MemAvailable, less what browsers still booting will take). When it doesn't, the orchestrator stops the longest-idle browser that no agent is using. If none can be stopped, it refuses with a clear error saying which ran short and listing what is running, e.g. "the host has 0.8 GB free, other apps included, and a browser needs about 1.0 GB". The host is checked with no RAM limit too (`BROWSERPIER_RAM_LIMIT_PERCENT=0`), and not when BrowserPier reaches Docker through `DOCKER_HOST`, whose host may be another machine. Attaching to a running browser is never refused. Browsers' memory is read from Docker (as `docker stats` counts it), and a new one is expected to need 1 GB. An agent's refusal names only the browsers its token can see; the full list goes to the log. Starting is checked one at a time, so two starts can't both squeeze in. The web UI's estimates ("room for about N more", "fits about N browsers") also count what other apps leave: the host's MemAvailable plus what the browsers use. It shows other apps' share too (PROJ-42); the limit itself counts only BrowserPier's browsers, and the host check covers the rest (PROJ-45).

## 4. Core concepts

- **Profile:** a saved browser identity with its own cookies and logins, named in lowercase (e.g. `google`). Settings: default mode, auto-stop, screen size, optional proxy, handoff policy, local network access (off), Block ads and trackers (on for new profiles, as Settings' default says; off for profiles made before PROJ-119; see Egress in §3), Record sessions (off, for new, imported and existing profiles; the admin's alone; see Recording in §3).
- **Session:** a running browser on one profile.
- **One session per profile.** Chromium locks its profile, so an agent asking for a profile that is already running attaches to the existing session. Different profiles run in parallel.
- **Modes:**
  - **API (CDP):** fast, but easier for anti-bot to spot.
  - **Visual:** screenshot or the page's element tree (read from Chromium's accessibility, no CDP), then OS-level click and type. Slower, but looks human.

  Each profile has a default mode, and agents can override it per session.
- **Agent token:** one per agent, scoped to all profiles or a chosen list. Shown in the UI as "In use by".

## 5. Session lifecycle

| State | Meaning | Main action in the UI |
|---|---|---|
| Starting… | Container and browser booting, a few seconds. | Disabled until ready |
| Running | Browser up; an agent may be attached. | Live view |
| Needs help | An agent requested a handoff and is paused. | Help now |
| Stopping… | Closing the browser, profile flushed to disk. | None |
| Stopped | No container; uses no RAM. Logins kept. | Start |
| Failed | Browser crashed or did not start; last log line shown. | Retry |

- Auto-stop when idle: 5, 10, 15 (default), 30 minutes, or never, set per profile.
  - **What counts as use:** any agent API call on the session (start or attach, screenshot, click, type, upload, each API-mode page tool: snapshot, find, act, wait_for, navigate, tabs, and each content call). A page tool's call keeps the browser busy while it runs (a 30-second `wait_for` too), but it holds no connection between calls, so a browser driven only by the page tools still stops when idle.
  - **In use the whole time:** an open CDP connection, a page call or an agent input action under way (a human-paced type can take a couple of minutes), and a browser a person has during a handoff, are never idle.
  - **Stopping:** an idle browser is stopped gracefully, so its logins are kept.
- A start takes a few seconds. The UI shows Starting… with a spinner and disables the action until the browser is ready.
- **Orchestrator restarts:** browsers keep running while the orchestrator restarts, and it picks them up again. Each container is labelled with the version of its definition (`io.browserpier.spec`); a browser from an older one, such as one started before pages went through the egress filter, is stopped the usual way instead, logins kept, and the next start gets a current one. So is a browser BrowserPier typed a secret into (Filled secrets, §8): the values were in memory only, so its answers could no longer hide them. The activity logs (§9) are in memory only too: a restart forgets every kept run and the live runs' entries, and a browser picked up starts a log that says "BrowserPier restarted: earlier entries of this run are gone".
- Stopping never loses logins, because the profile is written continuously, Chrome is closed gracefully, and it keeps session-only cookies across a restart (see §3, Chrome launch setup).
- A browser starts again with the tabs it had when it stopped; the active tab is the one that was in front. Not after a session BrowserPier typed a secret into (Filled secrets, §8): that start opens none, logins kept.
- **A stop Docker reports as failed** still counts when the container has in fact stopped: it is logged as a warning, and the exit status decides Stopped or Failed as usual. Rootless Podman on Ubuntu does this when AppArmor keeps it from stopping `pasta` (PROJ-64). If the container is still running, the session goes back to the state it was in and the error is returned.

## 6. Authentication

- **Admin password** for the web UI:
  - On Umbrel, it's the app password shown in the app's Info.
  - Elsewhere, it's set on a first-run setup page or through `BROWSERPIER_ADMIN_PASSWORD`.
  - The environment variable wins at every start, so changing it is also how to reset a forgotten password; it signs out every browser. The UI then can't change the password.
  - The setup page asks for a one-time code that the orchestrator prints in its log, so whoever first reaches a fresh public instance can't claim it. It disappears once a password is set.
  - Optional "keep me signed in for 30 days"; otherwise the session ends with the browser, and after a day at most.
  - A 5-minute lockout after 5 failures from one address in 5 minutes. Past 20 failures (and attempts in flight) from anywhere in 15 minutes, sign-ins from unknown devices go one at a time, each after a delay that starts at 2 seconds and doubles with every 20 more failures, up to 30 seconds. Browsers that have signed in before carry a signed device cookie (valid a year, voided by a password change, distrusted after 5 failures; made in the same transaction as the session it comes with, so a browser that a key rotation signs out right after its sign-in never holds one under the new key) and skip this, so an attack from elsewhere never slows the owner's usual devices. A lockout never signs out existing sessions.
  - Cookies are HTTP-only and `SameSite=Lax`, and `Secure` whenever BrowserPier is served over HTTPS (or `BROWSERPIER_PUBLIC_URL` is https). Private plain-HTTP setups (Umbrel, Tailscale) drop `Secure`, because browsers refuse a Secure cookie there.
  - Each sign-in gets a fresh session; changing the password signs out every other browser. Cross-site form posts are refused.
- **Two-step sign-in** (optional, off by default, Umbrel included; PROJ-162): after a right password, a code from an authenticator app (TOTP, RFC 6238: HMAC-SHA-1, 6 digits, 30-second steps, a 20-byte secret; a code is accepted for its step or one either side, and each step signs in once) or one of ten single-use recovery codes (80 random bits each, stored as SHA-256).
  - A right password makes no session and no device cookie: only a pending step, a random cookie on `/login` (kept in memory by its hash, at most 64, good for 5 minutes and one sign-in) that opens the code page. The code's use and the new session are written in one transaction; nothing on `/login` says whether two-step is on before a right password.
  - Wrong codes are counted apart from wrong passwords, and a right password never clears them: 5 end a pending step; 5 from one address in 5 minutes lock code entry there for 5 minutes; and at most 10 wrong app codes from browsers without a trusted device cookie, from all addresses together: the 10th wrong one within 24 hours refuses app codes from such browsers for 24 hours from then (a lockout, not a sliding window, so never looser than 10 a day). This count and lockout are kept in the database (`settings`, `two_step_code_lockout`: the times of the recent wrong codes and the lockout's end, never a code) after every wrong code, so a restart neither clears them nor hands out new guesses; a saved value that can't be read locks app codes from such browsers for 24 hours. Tries in flight are counted in memory only. The per-step and per-address limits and the device cookies' failure counts are in memory, and a restart clears them. Codes typed in Settings to turn two-step off, replace the app or make new recovery codes count on the same account-wide cap, as well as on Settings' own per-address limit. A trusted device cookie doesn't skip the code: it only puts that browser outside the account-wide cap (its wrong codes count on the cookie, which stops being trusted after 5). Recovery codes are outside the account-wide cap. A wrong code after a right password is logged at Warn.
  - Turned on in Settings with the password and a code from the new secret (that code's step is then used), which signs out every other browser and rotates the device key; turning off, replacing the app and new recovery codes need the password and a code. The state is read from the database at every use. It is off only when none of its rows (the secret, the last used step, when it was turned on) and no recovery code exist, and on only when all three rows are there and make sense; anything in between (the secret's row gone while the last step or recovery codes remain, say) or a row that can't be read refuses every sign-in after the password, from known browsers too, with a message pointing to `browserpier 2fa reset`, which clears whatever is left.
  - `BROWSERPIER_ADMIN_PASSWORD` resets the password, never two-step; `browserpier 2fa reset` (§8) does, on a running server. Agents never meet it: tokens, tickets and the PIN are unchanged.
- **The cookie and the token never mix:** the cookie authenticates the UI only, agent tokens the API and MCP only.
- **Client addresses:** `X-Forwarded-For` and `X-Forwarded-Proto` are believed only from `BROWSERPIER_TRUSTED_PROXIES` (CIDRs, or `private`); none by default. The shipped compose files set it for their proxy.
- **Rate limits** on login, setup, handoff PIN and token endpoints, with failed attempts logged (address and outcome, never the secret).
- **Agent tokens** for the API and MCP, never the admin password. Created in the UI with a name and a scope, shown once, hashed at rest (SHA-256 of 256 random bits, prefixed `bp_live_`), and revocable one at a time. Revoking one closes its CDP connections and breaks off its calls under way, page tools, Visual-mode input and a file chooser's answer alike, which answer 401 (input says "input broke off: the agent token was revoked", and the log "Typing interrupted" or "Input interrupted"). An input whose token is revoked after its request came in, while its body was still being read, is never sent: the token is checked again once the input is registered, and it answers 401 ("the agent token was revoked"; a failed check refuses it too). It does so at once from the UI, within 10 seconds from the command line (`token revoke`). A token scoped to a list loses a profile when it is deleted.
- **Handoff PIN:** 4–6 digits, separate from the admin password, set by the human, hashed (argon2id, like the admin password). Agents never see it. A short PIN's hash can be cracked offline in seconds, so the attempt limits, not the hash, are what protect it.
- **Stored as it is:** the secrets the server itself must use can't be hashed: the device cookie's key (`device_key`), proxy passwords, and the two-step authenticator secret, from which the server computes codes. They are never logged, and the authenticator secret is never shown again after it was confirmed. Encrypting them with a key kept in the same data directory would protect nothing.
- **Webhook secret** (Settings → Notifications, PROJ-157): an HMAC key BrowserPier makes (32 random bytes, 64 hex characters), shown once. It must stay usable to sign, so it is stored as it is, not hashed, like a proxy's password; so is the webhook's URL, which for Slack or Discord is itself a credential. Neither is ever logged, and the URL is shown as its scheme and host only.

## 7. Handoff: agent asks a human to take over

1. The agent calls `POST /api/sessions/{id}/handoff` with a reason, a detail (e.g. "Enter the 2FA code"), optionally a stricter `require` level, and optionally `until_url`, where the task ends (see Handing back by itself).
2. The session enters Needs help, the agent is paused, and the API returns a one-time URL.
3. The agent sends the URL to the human through its own channel (chat, Telegram, Slack). If the admin set a webhook (Settings → Notifications), BrowserPier also tells it, signed, with the profile and the reason, and the agent's answer says `notified: true`; the handoff link itself goes in it only for Link + PIN and Full sign-in, since opening a One tap link unlocks it and a chat's link preview could. For headless and scheduled agents, which have no channel to the person, that message is how they learn of it (deploy/README.md, Notifications).
4. The human opens the link (usually on a phone) and passes the profile's policy check. Control is then theirs, with the agent's reason shown.
5. The human taps **Done, hand back** or **Can't do this**, with an optional note. With `until_url`, the handoff also ends as done by itself once the page in front gets there, after they opened the link.
6. The agent, long-polling `GET /api/handoffs/{id}`, receives the status and note, then carries on or stops cleanly. It is told the handoff has ended (`done`, `cant`, `expired`, `cancelled`, a withdrawal or `until_url`) only once its browser is handed back and it can act: the status turns final only then, and reads `pending` until it does (PROJ-196). MCP's `wait_for_handoff` does the same. A request that would end it (a withdrawal, or a look at one that has expired) waits for the hand-back as long as the request lasts, and if it ends first answers that the browser is still being handed back (503), the hand-back going on to its end.

### Handoff policy, per profile

- **Link only:** one tap opens the browser. For low-stakes logins.
- **Link + handoff PIN:** the default.
- **Full sign-in:** admin password required, and the second step when two-step sign-in is on. For email, banking and payments.

### Rules the server enforces

- An agent can raise the level for one handoff, never lower it. Agents browse untrusted pages and can be manipulated through prompt injection, so a lower level asked for by an agent is ignored.
- A link lasts 15 minutes, works once and gives control of that one browser only. It dies as soon as the human hands back.
- Five wrong PIN attempts cancel the link, and the agent is told.
- A handoff that needs the PIN is refused (409) while no handoff PIN is set; the agent can ask for `require=signin` instead.
- Wrong PINs are also capped per address (10), per profile across its links (15) and across all profiles (30), each over 15 minutes, since the PIN is shared.
- An expired link sends the human to the normal sign-in.
- On a public instance, "Link only" requires HTTPS and shows a warning when chosen.
- The handoff prompt names only the page's origin (e.g. `accounts.google.com`), never its path or query. Those are controlled by the page and could be used to word a phishing message.
- After hand-back, the agent is told the page may have changed and must re-read it before acting.
- **How "works once" is enforced:** the first browser to pass the policy check gets a cookie only it holds (stored hashed); any other browser is refused, even with the PIN.
- **Handoff links only work over HTTPS, except from private addresses** (the LAN, Tailscale): opened over plain HTTP from outside, a link asks for no PIN or password and opens nothing, and says it needs HTTPS.
- **While the link is open:** the person drives the live view from the start, and the agent is paused: its connections close and its input is refused until hand-back, expiry or cancellation.
- **If the browser stops:** an open handoff is cancelled.

### Handing back by itself (`until_url`, PROJ-118)

People often stop once they see the signed-in page, without tapping Done, and the agent then waits up to 15 minutes for nothing. An agent that knows where the task ends can say so:
- **The pattern:** `until_url` is text matched, as a substring, against a tab's origin and path (`https://host[:port]/path`, as the browser shows it, the path percent-encoded or decoded), never its query, fragment or user name, such as `example.com/account` or `/dashboard`. At most 200 characters, and at least 4; control and invisible characters, `?` or `#` (which could never match), and a pattern that would match nearly any address (made only of `/`, `.` and `:`, or a bare scheme such as `https://`) answer 400; an empty one is none. Only `http` and `https` pages match. Case counts (hosts are lower case).
- **Watching:** while the handoff is open, the orchestrator asks the browser for its tabs every 500 ms with a plain HTTP GET of its `/json/list`, through the control socket's relay: no CDP connection at all, so it attaches to no page, opens no page session, enables nothing and goes through neither the page tools nor their lease, and the person shares the browser with no CDP client, in either mode. It starts looking once the person has opened the link (the handoff is unlocked; within half a second), not when the agent asks, so nothing the page or the agent does before then can end a handoff the person hasn't seen. The watch stops the moment the handoff ends, expires or is cancelled, or the browser stops or leaves Needs help; one goroutine per open handoff, none after. After an orchestrator restart, the sweep watches open handoffs again.
- **Which tab:** only the tab in front. `/json/list` lists tabs most recently activated first (Chromium sorts it by each tab's last activation; measured on the image's Chromium after `tabs` switch and new, and after ctrl+Tab, ctrl+1 and closing a tab with the live view's keys), so its first page is the one the person sees. It counts once its origin and path have changed since the watch first looked (when the person opened the link), or it opened since: a page already at the address, one that reloads, or one that changes only its query never ends a handoff; it takes a navigation to a matching origin and path. Every tab is remembered, so a tab that moved while behind (an opener that a sign-in popup sent on before closing) counts once it is in front; a background tab or popup that navigates by itself never ends a handoff while it stays behind. **Limits:** a page's own navigation, redirect or `history.pushState` to the address, in the front tab, is indistinguishable from the person's, so a page can end a handoff the person is on by sending its own front tab there (the pattern's minimum keeps it from being anything at all); a sign-in that ends on the page it started on (a form posting back to `/account` itself) never does, and the person taps Done as before; if the first look fails (the browser busy), the first that works is where the tabs start from, so a navigation before it doesn't count, nor does one made while the orchestrator was restarting.
- **The person is told:** while they drive, the handoff page says "This hands back by itself when the page reaches an address containing “…”", quoting the pattern (the agent's text, escaped, cut at 80 characters with an ellipsis), so a hand-back mid-task doesn't come as a surprise.
- **The end:** the handoff ends as `done`, as for a tap, with the fixed note "the page reached a matching address", never the address. The API adds `until_url_reached: true` (and echoes the agent's own `until_url`); MCP's `wait_for_handoff` says the page reached it. The phone's page shows **Done: handed back automatically**; the activity log says "Handed back when the page reached the expected address". Nothing the watch reads reaches the agent.
- **Unchanged:** the person can still tap Done or Can't do this (a tap and a match at the same moment end it once, whichever is first); expiry, the PIN, the policy (never lowered) and every rule above stay as they are. A match after the handoff ended, or once its 15 minutes are up, does nothing. An agent can't end a handoff sooner than a real navigation to the origin and path it named, nor learn where the person went.

### Handoff reasons

Typed so the UI can word the request well, each with a free-text detail:
- `sensitive_input`: login, 2FA, payment
- `captcha`
- `file_upload`: the agent may put the file in the uploads first (`upload_file`). No dialog shows on the screen (§3), and while a page's chooser waits Chromium's window takes no input, so the page shows the person a centred modal instead (PROJ-181): the profile's uploads to pick from (one, or several if the page takes several), **Upload from this device**, which stores the person's file in the uploads (100 MiB at most, the files cap and the same name rules as an agent's upload) and answers with it, and **Cancel**. Esc doesn't close it; the page waits for an answer. It appears only while the link holds control (not while the admin has taken it from the live view, PROJ-184), and the link reaches only its own browser's choosers and its own profile's uploads, with the cookie it gave, only while it is open. A chooser open when the handoff starts passes to the person, and one still open at hand-back passes back to the agent (its next action's notice says so), each with its whole 5-minute limit again.
- `review`: check before the agent continues
- `manual_step`

### Handoff over MCP

`request_handoff` opens the handoff, then:
- **Clients that can open URLs for their user** (URL elicitation, such as Claude) are asked to show the link. The tool call waits for the hand-back, up to 4 minutes at a time, then says it's still pending so the agent calls `wait_for_handoff`.
  - If the client declines the link (headless clients, such as `claude -p`, do so without asking anyone) or fails to show it, the link stays open and the agent gets it to pass on itself, as below. The agent can call `cancel_handoff` if nobody will take it.
  - The endpoint keeps MCP sessions (the 2025-11-25 protocol), since asking the client to show a link needs one. A client on the session-less 2026-07-28 protocol falls back to it.
- **Other clients** get the link to pass on themselves, and wait with `wait_for_handoff`.
- **When the admin's webhook was told** (`notified`), the text next to the link says so, so a headless agent waits for the person rather than calling `cancel_handoff`. It means the event was queued, not delivered.
- **The same rules as the API apply:** a PIN-policy handoff is refused while no handoff PIN is set.
- **`until_url`** works as in the API; `wait_for_handoff` then says the page reached the address instead of quoting a note from the person.

All endpoints take `Authorization: Bearer <agent token>`. The same actions are exposed as MCP tools at `/mcp`. The actions that change the page (`/click`, `/type`, `/computer`, `/act`, `/navigate` and `POST /tabs`) also take an optional `Idempotency-Key: <call id>` header, so a retried call isn't run twice (see Retries).

Starting a session returns its id, the CDP URL (proxied through the orchestrator) and the live view URL.

- **Scopes:** a token sees only the profiles it is scoped to; anything else answers 404, as if it didn't exist. Only a token for all profiles can create one.
- **Main site and icon:** creating a profile takes `site`, the main site whose favicon is the profile's icon in the web UI (a hostname such as `mail.google.com`, at most 253 characters; a URL is cut down to its host), and `icon_glyph` and `icon_color`, the fallback icon (see Profile icons in §9). Profiles are listed with them. The site BrowserPier infers from the browser's history isn't returned (it is read from pages, and says which sites a profile uses), and the icon itself is served only to the admin.
- **What agents can't change:** an agent creating a profile can't set its proxy (a proxy sees where the browser goes, and an agent can be steered by the pages it reads), read or change its `{sticky}` token (§3), or open the local network to its pages, and can make its handoff policy stricter than the default but never looser. Likewise it can ask for ad and tracker blocking (`block_ads: true`) but not turn it off (`false` answers 400).
- **Ad and tracker blocking** (PROJ-119): profiles and sessions say `block_ads`. `POST /api/sessions` with `"block_ads": false` starts the session without blocking, or turns it off in the running browser it attaches to, for the rest of that session; the profile's setting doesn't change, `true` (or nothing) leaves blocking as it is and never turns it back on, and the answer's `block_ads` says what the session does (`false`, with `ad_list_missing: true`, when the profile blocks but no list had been downloaded when the browser started). The agent log notes it. See Egress in §3 for what is blocked and the pages opened directly.
- **CDP:** `/cdp/{profile}` is the browser's WebSocket; `/cdp/{profile}/json/version` and `/json/list` work too, with their URLs pointing back through BrowserPier, so `connectOverCDP("https://…/cdp/{profile}")` works. The token never reaches the browser.
  - **Clients that can't set headers** get a ticket from `POST /api/sessions/{id}/cdp-ticket`, with the token in the header, and connect to the `cdp_url` it returns (`wss://…/cdp/{profile}?ticket=…`), as a WebSocket or as the `http(s)` URL Playwright fetches `/json/version` from.
  - **A ticket** opens one profile's CDP endpoint once, within 60 seconds, as the token that made it. It's kept hashed in memory only, and revoking the token voids it.
  - **The `/json` endpoints** use up the ticket they were called with, and the URLs they return each carry a fresh one, so a client can follow them. Calling `/json/version` and then `/json/list` takes two tickets.
  - **The token is never taken in the URL** (`?token=` answers 400): a proxy in front may log URLs, and a ticket that leaks there is already used or about to expire. The proxy refuses a Visual-mode session (no CDP client may attach to the page) and a browser a person is using during a handoff.
- **Visual mode:** screenshot, click and type go through the container's X display and xdotool. During a handoff, agents can still take screenshots but not click or type. Coordinates are screen pixels, and the screen includes the 32-pixel taskbar along the bottom; a screenshot can be scaled down with `?width=`, and the response gives the screen size.
- **Pace** (PROJ-113): every input action takes `pace`: `human` (the default) or `instant`. At human pace input moves as a hand does (`internal/motion`, a port of agweb's Motion model): the pointer glides from where it is along a bowed path at a Fitts's-law speed (0.2–1.15 s, plus a quick correction on long throws), lands at a point scattered around the target's middle, pauses (median 0.16 s) and holds the button about 116 ms; keys are held about 116 ms, with a typist's log-normal gaps between them (median 0.2 s, longer after spaces and punctuation); the wheel turns in notches that come faster mid-turn. `instant` is input as it was before: one move and a click, and `type` at 12 ms a key in Visual mode. The scatter is the point, but it mustn't miss: in Visual mode, which sees only a point, the glide's timing assumes a 44 px target, while the landing scatters as on an 8 px one, within about 3 px of the point asked for (SD about 1.3 px), so a 13 px checkbox or an 18 px row in a dense list is still hit; act scatters within the element's own box and checks the point it chose is the element's. Human pace makes calls slower: about a quarter of a second a character, so `type` takes at most 500 characters per call at human pace (2,000 at instant in Visual mode), and act's type steps 500 together; through MCP (`type_text`, and act's human-paced type steps together) the cap is 150 characters, about 40 s, so the call ends before an MCP client's request timeout (60 s by default in the TypeScript SDK), after which a client would retry and the text be typed twice. Longer text is split across calls, filled (`fill`), or typed at instant pace. A handoff, a stop or the token's revocation breaks off an action under way at once, and whatever it held is released. The per-call `pace` is the only setting for now; a per-profile default in Advanced settings, which a call's own `pace` would override, is a follow-up.
- **Computer actions:** `/computer` takes one action. `click {x, y, button?, double?}` and `type {text}` work as above; `scroll {x, y, dx?, dy?}` scrolls by whole wheel notches at a point, at most 20 each way; `key {keys}` presses a combination like `"ctrl+l"` or a list of up to 10, each made of X keysym names (`Return`, `Tab`, `a`…, with aliases such as `Enter`, `Esc`, `Cmd`, `PageDown`) joined by `+`; `drag {from: {x, y}, to: {x, y}, button?}` presses, moves (at human pace along a hand's path, both ends exact) and releases; `open {url}` opens an address through the address bar (below). Each also takes `pace` (above); so do `/click` and `/type`. These run through xdotool with the same checks as click, never as an xdotool script. `wait {ms}` pauses up to 10 s. `zoom {x, y, w, h}` returns that region of the screen as a PNG at full resolution, cut off at the screen's edges. With `screenshot: true` any other action answers with the screen afterwards (scaled to `width` if given) instead of 204; the action has run either way, so a screenshot that fails, or is over 64 MiB (never cut off), answers 204 with `X-Screenshot-Error` saying why. During a handoff, wait and zoom still work. The activity log names each action but never typed text: keys that could spell something are logged only as a count.
- **Text right after a shortcut** (PROJ-151): while a page has the keyboard, Chrome sends it every key and moves the focus to its own UI (the address bar for `ctrl+l`, the find bar for `ctrl+f`…) only once the page has answered that it left the key alone, so keys that arrive before that answer are the page's: an address typed into the page's search box, or each letter taken as one of its shortcuts. A page answers at once unless its key handler is busy, and measured on Chromium 156 (`images/chromium/ANTI-BOT.md`) nothing was lost at once behind a quick page, a page still loading after a restart, or a fresh browser; behind a handler that took 100 ms a key, every run lost the start of the address (Chrome waits for the page twice, for ctrl and for l, so the text typed in the next 0.1–0.2 s was the page's). So the container keeps a **gap**: an agent's `key` or `type` that comes less than 150 ms after the end of its `key` call ending on a browser-bound combination (any with ctrl, alt or super, wherever they come in it, or F1–F12, alone or with shift) waits out the rest, in the container, before it is sent; inside one `key` list, the same pause follows such a combination when it isn't the last, and a list cut short or failing after one arms the gap as if it had ended on it, since the shortcut may have reached the browser. A call that comes later waits for nothing. Plain keys, Return, Tab, shift and typing wait out a gap already running but don't start one; clicks, scrolls, drags and screenshots neither wait nor start one, nor does a person's input in the live view (its keys, its Type button, which has a route of its own in the container, and the clipboard box's paste). The gap is a floor, not a guarantee: a page that takes more than about 100 ms to answer each key can still receive the text, and an agent should look at the screen before typing after a shortcut on a page that is busy or still loading (the `press_keys` description says so). To open an address, `open` (below) has no such race. Nothing about it uses CDP. The wait ends with the request, sending nothing, and holds the input lock for at most the gap (never over 250 ms), so a handoff is delayed by no more than that; a key list's own pauses (at most nine) are part of its xdotool run, which, like any input, breaks off when the request ends and lets go of the keys it held.
- **Opening an address** (PROJ-164): `open {url}` (MCP `open_url`) does what a person does: a click in the address bar of the browser window in front, select all, the address, Delete (which drops a completion the address bar added after it) and Return, all through xdotool. A click on the browser's own UI moves the keyboard focus there at once, without asking the page, so unlike `ctrl+l` (above) a busy page can't take the address: measured behind a key handler that takes 400 ms a key, 20 of 20 at instant pace and 3 of 3 at human pace reached it, and the page saw no key (`TestOpenBehindABusyPage`; `ctrl+l` lost every run there). Agents are told to use it rather than `ctrl+l` to open a page.
  - **Pace:** at human pace the pointer glides to the address bar and pauses there, and the button, `ctrl+a`, Delete and Return are held as a hand holds them; the address itself goes in at 12 ms a key at either pace. No page sees those keys or their rhythm (they go to the address bar), a person often pastes an address, and a real paste would overwrite the profile's clipboard. An open takes about a second either way, plus the glide.
  - **The address** is checked as `navigate`'s is (`internal/weburl`: http and https only, no user name or password, a host, at most 8,192 characters; a space or a character past ASCII in the query is sent percent-encoded as UTF-8, `%20` or `%C3%A9`, as a browser sends it, for both: typed as it is, xdotool can drop a character such as `é` on its way into Chromium), by the orchestrator and again by the container, which also refuses any space or control character left (it would type as a key) and caps it at 2,000 characters, as an instant `type`. It reaches xdotool only as text after `--`, never as an argument of its own. The activity log names its origin only (`Opened https://example.com in the address bar`), as `navigate`'s does, since a path or query may carry a one-time link's token. On a session that blocks ads, the host is let through the list as for `navigate` (§3, Egress), once the agent has the browser's input and just before the open is sent, so an open the container refuses (the address bar covered) leaves it let through too, as a failed `navigate` does, while an open refused because a person has the browser (live view or a handoff), or because its token was revoked, changes nothing; `download_wait_ms` applies as for a click, since the address may be a file.
  - **Where the address bar is:** the browser window sits at 0,0 with no frame, filling the screen above the taskbar, and Chromium draws its toolbar at a fixed size, so the address bar runs from y = 46 to 80 and from x = 121 to the screen's width less 85 (measured on Chromium 156 at 640×480, 1280×800 and 1920×1080, `TestOpenAtEveryScreenSize`); the click aims at its middle (y = 63), clear of the security chip and the buttons at its ends, scattering at most about 26 px either way at human pace. These numbers hold for the Chromium major version they were measured on (`addressBarChromium` in `entrypoint/open.go`); the image records its Chromium's version when it is built, and on any other version (or none) `open` answers **409** saying so and telling the agent to use `ctrl+l` and typing, rather than clicking where the address bar may not be. Moving to a new Chromium means measuring again and moving the constant.
  - **What may be in the way:** no CDP is used to look. The container reads the X display (`entrypoint/xwin.go`, a read-only X11 client: xdotool can't read a window's role): before moving the pointer, and again with the pointer on the address bar just before the press (after the hand's pause, at human pace), the windows that show at that point; it presses only if Chromium's tabbed window (role `browser`) is on top there, at 0,0 and filling the screen above the taskbar. Otherwise it answers **409** with what is in the way, having pressed nothing: the browser is **full screen** (no address bar: press F11, or Escape for a page's full screen), a **pop-up window** a page opened covers it (even one exactly the size of the browser window, which only its role tells apart), a menu or bubble is open over it, or another window (a dialog). After the click it reads which window has the **keyboard**, before each run of 64 characters of the address, and before Delete and again before Return, each time after the pause that comes before the key (for the address bar's suggestions, and between the two keys), so the key follows the look at once: if it is no longer that browser window (a pop-up or a file chooser opened and took it), it stops there with a 409 saying how much was typed, and Return isn't pressed. Chromium's own hover cards and the address bar's suggestions are drawn inside the window and don't stop it. A page's alert or confirm dialog is drawn inside the window too, below the toolbar: the address bar still works, and opening the address dismisses the dialog. A page's `beforeunload` prompt can still stop the navigation, as it would a person's; a screenshot shows it.
  - **Limits:** it opens the address in the tab in front; it doesn't wait for the page to load, so the agent takes a screenshot (or sets `screenshot`) to see where it landed. Each look and the xdotool run after it are separate, so a window that opens in the moment between them (a few milliseconds, the time an xdotool process takes to start) still gets the press (the click, Delete or Return), or up to 64 characters of the address; the next look stops the rest.
- **Download notices** (PROJ-116): an action that may start a download says what it downloaded, so an agent that clicks "Export CSV" isn't left to guess, wait and call `list_files`. `act` (the whole call), `/click`, and `/computer`'s `click` and `key` (over MCP `act`, `click` and `press_keys`) list the profile's `files/downloads` before the action and again after, through `os.Root` (regular files only: names, sizes and times; a planted link is skipped), with no CDP at all, so both modes work alike. Chrome writes a download as `Unconfirmed N.crdownload` (a `.crdownload` in any case), sometimes through a hidden temporary file, and renames it to its name once it has finished.
  - **Waiting:** when nothing new is there, the notice keeps looking for 40 ms after the action ended, since Chrome creates the file only once the server has answered, often just after a click returns; an action that downloads nothing is held up by at most that (act's 40 ms run while its changes are read, and `/computer` takes its screenshot before looking). Only while a new partial download is there does it wait longer, looking every 200 ms for up to `download_wait_ms` (3,000 ms by default, 0 not to wait, at most 30,000; other `/computer` actions ignore it). A download already under way before the action is neither waited for nor named, unless it finishes during it. The 40 ms suit a server close by; a remote one usually answers later, so without `download_wait_ms` a Visual `/click` or `/computer` action (whose answer has nothing else to wait for) usually misses a remote download's start, and it is told with the next action (Late downloads). When the caller sets `download_wait_ms` itself, it expects a download, and the notice looks that long for one to start too (at least 40 ms, every 50 ms), then waits for it to finish as above: so `"download_wait_ms": 10000` on an Export click answers once the file is there, or after 10 s of nothing.
  - **Lines,** one per file, at most 5, then `and N more`: `downloaded report.csv (12 kB)`; `download in progress: report.csv (4.1 MB so far); list_files to check later`, without the name while Chrome still calls the file `Unconfirmed`, which it does until the end; `a download vanished before it finished` (cancelled, failed or removed; since a listing taken while Chrome renames the file may hold neither name, the notice lists the folder once more 50 ms later before saying so); `downloaded a.csv (3 B), then removed (the files cap evicts the oldest files)` when the cap's eviction took it between two listings, which never fails the action. Sizes are in SI units (1 kB is 1,000 bytes).
  - **Late downloads:** what finished between a session's last notice and its next action (a download that started after the 40 ms, or after the caller's `download_wait_ms`, or one told as in progress) is told with that next action, once: `downloaded big.csv (5.0 MB), after the last action's answer`. The last listing this needs is kept per session, in memory only, and goes when the session ends. A file a person downloaded during a handoff is told the same way.
  - **How it reaches the agent:** act's answer ends with `### Downloads` and the lines, fenced, since the file names come from the pages that offered them (cleaned of invisible characters and line breaks too); when a step failed after one that downloaded, the error carries them. REST `/click` and `/computer` keep their status (204, or 200 with the screenshot) and add an `X-Downloads` header only when there is something to say: one line of ASCII JSON, `{"files": [{"name": "report.csv", "size": 12345, "state": "downloaded"}], "more": 2}`, where `state` is `downloaded`, `in_progress`, `vanished` or `removed`, `earlier: true` marks a late one, `name` is `""` while Chrome hasn't named the file, and anything past ASCII is `\u`-escaped. Decided 2026-11-15: a header changes nothing for clients that check for 204 or read the PNG, which a 200 with JSON would. Its names are data, as in the files list; the MCP tools turn them into fenced lines after `Clicked.` (or after the screenshot).
  - **The activity log** says `Downloaded report.csv (12 kB)` for each finished file, at most 5 for an action, then `Downloaded N more files`, as the notice is capped; the web UI escapes the name like every entry.
  - **Limits:** a download Chrome holds for a person's decision (a file type it warns about from a plain-HTTP site, such as a `.bin`) stays `Unconfirmed` and is told as in progress until someone keeps it in the live view; a download whose server answers after the next action has begun is told with the one after.
- **Retries** (PROJ-156): MCP and HTTP clients time out and retry, and a human-paced action can run for minutes, so an action sent twice could click "Pay" twice. An agent gives an action that must not happen twice a call id of its own: the `Idempotency-Key` header over REST, `call_id` over MCP (passed on as the header; the rule is the API's alone). An empty `call_id` is refused like an empty header, not taken as none.
  - **The id** is 1 to 64 characters of `A-Z a-z 0-9 - _`; anything else answers 400 before anything runs. It is taken on `/click`, `/type`, `/computer`, `/act`, `/navigate` and `POST /tabs` (MCP `click`, `type_text`, `press_keys`, `scroll`, `drag`, `act`, `navigate`, `tabs`). Every other route answers 400 ("no call id is taken here"), so an agent never believes it is protected when it isn't; a test lists the routes and fails on one that hasn't chosen. Uploads, handoffs (a second request already answers 409 with the open one), answering a file chooser (`POST …/chooser`, MCP `choose_files`: a chooser takes one answer, and its ids aren't reused while the browser runs, so a repeat finds it closed and answers 409), session start and stop, profile creation and reads take none. `/computer`'s `wait` and `zoom` take the header but keep no receipt, as they don't touch the page.
  - **Receipts:** each live session keeps, per token and call id, the route, a keyed fingerprint of the request (HMAC-SHA-256 with a key random per process, over the body as canonical JSON: keys sorted, whitespace dropped, numbers as written), the token, the state and the start and end times; never the arguments or the answer. The body can hold typed text, so the fingerprint is never returned or logged; the call id is in answers but never in the orchestrator's log. Ids are per token: two tokens using the same id never meet, and a token sees only its own receipts.
  - **The rule:** the receipt is taken before the call waits for anything (its turn behind another page call), in one locked step, so two copies sent together make one call. It is **admitted** when the session grants the call its lease (`AgentInput` for a Visual-mode input, `PageLease` for a page tool), decided there and not from the status code. A click by ref (PROJ-150) reads the element first under a read lease, which admits nothing; only its input does, so a click refused after the read (a stale ref, a person who had the browser since) gives the id back. A call refused before that gives the id back, and it can be sent again: bad JSON or arguments (a body is one JSON value, with nothing after it; `/click`, `/type` and `computer`'s click and type check their body's shape, button and pace, and that a type has text, before the input's turn; only the screen's size and the text's length are left to the browser), no such session, the wrong mode, a person has the browser, another input under way, the caller gone while waiting for its turn (or by the time it came). An admitted call keeps its receipt, however it ended: a 409 can also mean "input broke off" or a step that failed after earlier ones ran.
  - **States:** `waiting` (taken, not yet admitted), `running`, then `ok`, `error` (it answered with an error once admitted; some of it may have happened) or `interrupted` (cut short by a handoff, Take control, a stop, a hold, the token's revocation, the caller going away or a panic; how far it got isn't known).
  - **A repeat** (same id, same route and fingerprint) is never run again, whatever the first one's end. Its answer carries `{"call": {call_id, tool, state, started, ended}, …}` and `Idempotency-Replayed: true`: 200 with a text saying it ran already and its result isn't kept (read the page again) when the first ended `ok`; 409 saying it is waiting for its turn or still running, and where to ask; 409 saying to read the page and send what is still needed under a new id after `error` or `interrupted`. A repeat never returns a screenshot, a snapshot or a download notice. The same id with another route or body answers 409 ("this call id named another call"), nothing run. Over MCP the same answers are tool results, an error unless the first call ended `ok`.
  - **Asking:** `GET /api/sessions/{id}/calls/{call_id}` (MCP `call_status`) answers with the token's own receipt, or 404. A 404 doesn't prove the call never ran: it may have been given back unrun, or have run and had its receipt dropped since (see Limits), so its answers and the waiting replay tell the agent to read the page before sending it again. `GET /api/sessions/{id}` (MCP `session_status`) adds the token's `running_calls` (its calls holding or waiting for the browser, and those with an id still running after it, such as a click looking for its download: tool, state, started, call id if any) and `recent_calls`: the last 20 activity-log entries its calls wrote on this session, newest first, with the call id and the receipt's state when there is one. They come from the activity log (§9), its agents' actions only (never BrowserPier's own entries, a tab title among them), so a call that failed outright shows only through its receipt; an entry naming a download, whose file name the page chose, is fenced. The state is looked up by call id when read: once an id has been taken again (given back, or its receipt dropped), an old entry shows the new call's.
  - **Limits:** at most 1,000 receipts a session; when full, the oldest ended one goes (a receipt waiting or running never does, and with 1,000 of those a new id answers 429), so an id 1,000 calls old can run again. Receipts are in the orchestrator's memory only, and go when the session ends: a stopped and restarted browser is a new session, where the old id answers 404, and after an orchestrator restart a repeat runs again (for `act` its refs are stale then, so it refuses; a Visual click would run). The id protects against the same request sent twice; it doesn't make a page's own double submit safe, and does nothing for a raw CDP client. A caller that goes away still cuts its call short, as without an id (the receipt then says `interrupted`). Over MCP, the Go SDK (v1.8.0, streamable HTTP, stateful) doesn't cancel a tool's context when the client's HTTP connection drops: the call runs to its end and its receipt says how it ended. It is cancelled, and ends `interrupted`, when the client sends `notifications/cancelled` (as clients do on their own timeout) or the MCP session closes.
- **Tokens without the UI:** `browserpier token create NAME [-profiles a,b]`, `token list` and `token revoke ID` manage tokens from the command line, e.g. through `docker exec`.
- **Two-step sign-in without the UI:** `browserpier 2fa status` says whether it is on and how many recovery codes are left, never a secret; `browserpier 2fa reset` turns it off (secret, last step and recovery codes removed), with no password, on a running server; sessions and the password stay. There is no API or MCP route for two-step sign-in.

### Visual-mode element tree

PROJ-150. Visual mode's counterpart of `snapshot` and of clicking a ref, with no CDP: the page is read from the accessibility tree Chromium publishes on the container's private bus (§3), so an agent reads small text and fields' states without a screenshot and clicks what it read.

- **How it reaches the page:** the entrypoint's tree reader (`images/chromium/entrypoint/tree.go`) answers `GET /tree` and `GET /tree/node` on the control socket. It is a pure-Go D-Bus client (`github.com/godbus/dbus/v5`, BSD-2-Clause) that sends only AT-SPI's read methods, kept in one allow-list (`readMethods`: `ListNames`; `Properties.Get` of `Name`, `Parent`, `ChildCount`, `CharacterCount`, `CurrentValue`; `Accessible.GetChildren`, `GetChildAtIndex`, `GetRole`, `GetState`, `GetAttributes`; `Component.GetExtents`, `GetAccessibleAtPoint`; `Text.GetText`; `Document.GetAttributes`), checked before anything reaches the bus. Never `Action`, `EditableText`, `Selection`, `GrabFocus`, `ScrollTo` or `SetCurrentValue`: those aren't OS input and a page could tell. Each read opens its own connection, finds the biggest showing document in Chromium's biggest showing window (the active tab's page: not Chrome's own toolbar, tabs or popups, nor other tabs), and walks it depth first, 32 calls in flight, what is on screen before the rest. It sends JSON: roles and states as AT-SPI's numbers, names, fields' text, boxes in screen pixels, a few object attributes (`xml-roles`, `text-input-type`, `html-input-name`, `id`, `placeholder`, and `autocomplete` if Chromium ever sends it; Chromium 156 doesn't), and each object's path as its identity, with `attrs_read` saying a field's attributes were read (not a read that failed). Attributes are read for every field whose value is printed: text fields, password fields, combo boxes, spin buttons and sliders. A password field's text is never read: only whether it has any.
- **Limits:** 20,000 nodes, 128 levels below the document, 1,000 bytes a string and 2 s a read; a read cut short answers what it has and says so (the snapshot then says the page is larger than BrowserPier reads at once, what is on screen first). A node with more than 64 children has them asked for one by one, as the limits allow (Chromium takes seconds to list thousands). One read at a time per container, and per session in the orchestrator, which takes a read lease (`sessions.Manager.ReadLease`): a handoff, a stop or the token's revocation ends a read in progress (a revocation also ends a read still waiting for its turn, and a read it ends after the tree came back answers 401, never the page), a person taking control in the live view breaks one off at once, and reads neither start, extend nor cut short the 5 seconds after an agent's input in which Take control is refused (PROJ-134): within them Take control is refused and the read goes on; a click by ref is a click and starts them.
- **visual-snapshot** `{max_chars?, query?}` answers `{"text": "…"}` in the page tools' shape (`internal/visualtree`, no CDP import): URL and title, then controls as `vk3n12 button "Sign in" @644,178` (role, name, value, states, the centre in screen pixels, or `[off screen]`; MCP's `visual_snapshot` gives the centre in the screenshot's pixels, as every MCP tool takes them) and text, within a budget (default 4,000 characters, at most 20,000; 0 for the URL and title only), the open modal dialog first, then what is in view, the main landmark and the rest; a navigation or menu of more than 20 controls is one line; a line after the fence says what was left out. Roles and states print as BrowserPier's own words (the page tools' `button`, `textbox`, `checkbox`…; an unknown role is a container, never named as the bus names it). A `<select>` shows its chosen option, headings start `# `, a label's text that is its control's name isn't repeated, and list markers are dropped. `query` keeps only the lines that hold it (ignoring case), in document order, each under the dialog, landmark, form, list or menu it is in, written `[dialog "Cookie settings"]`: the counterpart of `find`. Iframes are read, same-site and cross-site.
- **Refs** like `vk3n12` are their own space: `v`, a 2-character epoch random per session map, `n` and a number, so neither pattern matches the page tools' `a7e12` (act refuses a Visual ref; click refuses a page tools ref, saying which tools give which). The same rules: numbers never reused, at most 5,000 live (the oldest go), stale once the document changed (a navigation makes a new document object; a snapshot of a new one drops the old one's refs), the element is gone, a person had the browser since (the lease generation), or after an orchestrator restart.
- **Click by ref:** `click`, `/computer`'s `click` and MCP's `click` take `{ref}` instead of `{x, y}` (both is 400). BrowserPier reads that one element again (`/tree/node`), refuses it if it is gone or its document isn't the one showing (409 stale), if it isn't showing or its centre is off the page's area or under the taskbar (409, "scroll it into view, take a new visual_snapshot"), or if Chromium's hit test (`GetAccessibleAtPoint`, asked twice 100 ms apart, as its first answer can be a guess from boxes or the last point's) finds something else at its centre (409, naming what covers it, fenced). A hit test that fails or times out is no confirmed hit: 502 or 504, and nothing is clicked. Then it clicks that centre through xdotool exactly as a click at a point (`AgentInput`, human pace by default, download notices, the 5-second rule). The click carries the lease generation its point was read under: if a person had the browser between the lookup and the click (Take control and hand back), it is refused (409, take a new visual_snapshot) and never reaches the browser. The answer is `{"text": "Clicked vk3n12, <fenced role and name>"}`, or the screenshot when one is asked for. BrowserPier never scrolls for the agent. `double` and `button` work as with coordinates; type, scroll and drag keep coordinates (an agent clicks a field's ref, then types).
- **What the hit test can't see:** an overlay that is in no way accessible (a bare `<div>` with no role, text or handler) isn't in the tree, so the hit test finds its accessible ancestor, which usually holds the element too: that answer can't tell, and the click goes ahead.
- **Secrets:** a password field prints `[filled]` or `[empty]` whatever the reader sent, never a value or a length. Every other field that holds a value (a text field, a combo box, a spin button such as a `type=number` code field, a slider) is judged with `fence.Secret` from its input type, name, id, accessible name and placeholder; a secret prints the same, a combo box's selected option counting as its value. A field whose attributes the reader couldn't read (`attrs_read` false) can't be judged by its name or id, and prints `[filled]` or `[empty]` too: it fails closed. A line of page text that starts like one BrowserPier writes (a ref, `[`, `-- `, `URL:`) is prefixed `text: `, here and in the page tools' snapshot, judged as the fence prints it (invisible characters gone) and kept when the budget cuts the line, and names escape backslashes and quotes, so page text can't pass for a control or add states. **Known gap:** AT-SPI has no `autocomplete` attribute, so a one-time-code or card-security-code field with a neutral type, name, label and placeholder shows its value. When PROJ-125's scrubbing applies (it does to every API answer), this output is scrubbed too.
- **Refusals:** 409 for an API-mode session (saying snapshot reads the page there), for a session a person drives or that is in a handoff, or that isn't running; 404 for a session the token can't see; 401 when the token is revoked during the read; 409 when no page is showing (or Chromium is still building a big page's tree) and on an image without the tree reader (rare: `docker.Spec` 7 makes an update stop Visual browsers started under an older definition, which had no tree reader); 502 with the bus's error fenced when the tree can't be read; 504 when the read timed out with nothing read.
- **What the tree doesn't show:** Chrome's own interface (tabs, the address bar, permission prompts, the password bubble, the file chooser), other tabs, what isn't in the accessibility tree (`aria-hidden`, `display:none`, the inert page behind a modal dialog), canvas content, and a password's value. Text a person can't see may still appear (transparent or off-screen text): it is fenced like the rest.
- **The activity log** says `Read the screen's elements` and `Clicked vk3n12` (`Double-clicked`, `Right-clicked`), never page text.

### API-mode page tools

For agents that speak only MCP (or REST), six tools read and act on an API-mode page in a few hundred tokens, without raw HTML or a screenshot (PROJ-21). They answer `{"text": "…"}`, the same text the MCP tools return, and refuse a Visual-mode session (409). Another profile's session is 404, as everywhere.

- **How they reach the page:** each call opens one short-lived CDP connection from the orchestrator through the container's control socket, never through the agent proxy, and closes it before answering. It sends only the methods on the tools' allow-list (`internal/pagetools`), never a domain's `enable` or `DOM.getDocument`, runs its scripts only in an isolated world, and writes nothing into the page; `fill` and `select` set values as Playwright does. The agent's own CDP client can be connected at the same time.
- **The tools' allow-list** (`AllowedMethods()`, kept in step with this list by a test): `Accessibility.getFullAXTree`, `Accessibility.getPartialAXTree`, `DOM.describeNode`, `DOM.focus`, `DOM.getContentQuads`, `DOM.resolveNode`, `DOM.scrollIntoViewIfNeeded`, `DOM.setFileInputFiles`, `DOMSnapshot.captureSnapshot`, `Input.dispatchKeyEvent`, `Input.dispatchMouseEvent`, `Input.insertText`, `Page.createIsolatedWorld`, `Page.getFrameTree`, `Page.getNavigationHistory`, `Page.navigate`, `Page.navigateToHistoryEntry`, `Page.reload`, `Runtime.callFunctionOn`, `Runtime.evaluate`, `Runtime.releaseObject`, `Target.activateTarget`, `Target.attachToTarget`, `Target.closeTarget`, `Target.createTarget`, `Target.detachFromTarget`, `Target.getTargets`. The content endpoints have a list of their own (see Page content).
- **Lifecycle:** a call takes a page lease on the session: one call at a time per session, refused while a person has the browser, cancelled by a handoff, a stop, the token's revocation or a session hold (which waits for it to end). A lease doesn't show the agent as connected, but like a click it keeps a person from taking control while it runs and for 5 seconds after.
- **Refs** like `a7e12` name an element of one document: a 2-character epoch, random per session map (so refs from before an orchestrator restart answer stale), then a number never reused. A ref goes stale when its document changes, its node goes, or a person had the browser since; a ref from a tab that isn't active is refused. At most 5,000 are live per session, the refs that errors and wait_for hand out included.
- **Targets** (PROJ-123): a step of act, or wait_for, may name its element by `target` instead of `ref` (not both), so an agent that knows what to click needs no snapshot first, and a navigation that made every ref stale doesn't stop it. `role=button[name="Save"]` is an ARIA role (case aside; Chromium's own names a snapshot shows, like `PopUpButton`, too; `button` also matches a toggle or pop-up button, `img` and `image` each other) and a case-insensitive part of the accessible name (`name*=` is the same; single quotes; a backslash escapes a quote; a name may hold `]` when quoted; a trailing `…`, a snapshot's mark of a cut name, is ignored; spaces collapse); `role=button` alone takes any name. `text=Save` is the innermost element whose rendered text holds the text, ignoring case; `text="Save"` (or single quotes) is one whose whole text is exactly that, case included. Either may end with ` >> nth=N`: the Nth match from 0, `-1` the last. `role=generic` matches the generic controls a snapshot lists (a div or span control, see snapshot), by the text it shows as their name, not every plain div (Chromium's `generic` is on all of them, unnamed); a text match inside a generic control is the generic itself, as the snapshot lists it, even when the AX tree ignores it or leaves it out. At most 500 characters. CSS selectors and XPath are refused (400): they would reach elements the snapshot hides by design. So are an unknown role, a missing `]` or quote, and an `nth` that isn't a number.
  - **Resolution** reads what a snapshot reads, never a script in the page: the accessibility tree (`Accessibility.getFullAXTree`) with the DOM snapshot for what is shown, of the top frame (nothing inside iframes). A match must be visible by the snapshot's rules: an element, not AX-ignored (`aria-hidden`), laid out, not `display:none` or `visibility:hidden`, with a non-empty box. A role target matches on the role and name Chromium computes. A text target's text is the page's rendered text as the AX tree's text nodes give it (their DOM characters, so the spaces between inline elements stay; a space between blocks), never a field's value (text boxes, search boxes, comboboxes, spin buttons and sliders are skipped, and so is any text inside an `input` or `textarea` whatever role the page gives it, so a password can't be matched or shown); the match is each element whose text holds the target's while no visible element inside it does (a link inside a paragraph, not the paragraph; a phrase across the link, the paragraph). It is a whole-page read like `snapshot`: it takes one of the shared read slots and refuses a page of more than 60,000 DOM nodes (422, pointing to `find`). The read is checked against the tab's document afterwards, and one that straddles a navigation is refused (409, try again).
  - **Exactly one** visible match is acted on, and the step's result names it with its ref, which works like a snapshot's. None: 409 `no visible element matches role=button[name="Publish"]`, then, for a role target, the page's visible elements of that role (or that it has none); several: 409 `role=button[name="Delete"] matches 2 visible elements:` and `Be more specific, use one of their refs, or add >> nth=0`. Each lists at most 5, in document order, as `button "Delete" [ref=a7e12]` (role and name only, never a value; for a text target, an element with no name shows the start of its text, 40 characters), fenced, then `and N more`. The refs are real refs of the session's map, made as a snapshot makes them, so the next call can use one. The target itself is the agent's own words and is echoed outside the fence.
- **The active tab** is the browser's foreground tab, the one whose page is visible: `tabs switch` and `new` bring theirs to the front, so the tools, the live view and a handoff see the same one. When a page opens a tab (a sign-in popup), every tool's result says `a new tab opened: t3 (https://accounts.example)`, and the agent switches to it.
- **snapshot** joins the accessibility tree and a DOM snapshot of the top frame (an iframe is one line, not read: its origin, or its address when that has none, quoted if it has whitespace or a quote in it, so a page string can't start a line of its own). It spends its budget (4,000 characters by default, at most 20,000) on an open modal, then what is in view, then the main landmark, then the rest, controls before text in each, sums up a navigation or menu of more than 20 controls in one line, and says what it left out. Secret fields (as `internal/fence` judges them) show only `[filled]` or `[empty]`. A page with more than 60,000 DOM nodes is too large for the accessibility tree: `snapshot` says so, and `find` reads its text alone.
  - **Controls built from a div or a span** (PROJ-124), which have no role and only a pointer cursor or a tabindex give away, are a control line `generic "<its text>"` with a ref, as Playwright lists them, so the agent can click one. An element is one when it has no role of its own (Chromium's `generic` or `none`, AX-ignored as uninteresting, or left out of the AX tree, as Chromium leaves out a span whose click a listener on the document handles, as frameworks do); the pointer cursor starts on it (its computed `cursor` is `pointer` and its nearest laid-out parent's isn't: children inherit it and aren't controls for that) or its `tabindex` is 0 or more; it is shown, has rendered text, holds no shown control (a pointer div around a real button is the button's line), and isn't inside a control or another generic. Its name is its rendered text from the AX tree's text nodes, so hidden and `aria-hidden` text isn't in it; it is fenced and capped like every name. What is inside it isn't listed again: its text isn't a line of its own when the generic's line shows it whole (80 characters), and stays as text when the name is cut (a list of 2,000 rows that inherit the pointer from it, a scrollable `<pre tabindex=0>`), so nothing is lost or said twice. It counts as a control for the budget, `act` acts on its ref like any other, and a diff shows it like any line. The DOM snapshot asks for one computed style more (`cursor`) and nothing else is asked of the page. Roles aren't guessed from class names. Only elements Chromium gives no role of its own count (`generic` or `none`): a clickable `li`, `tr`, `td`, `p` or heading has one (list item, row, cell, paragraph, heading) and isn't listed, nor is an icon with no text; `find` or a text target (`text=…`) still reach their text, and act clicks what a text target matches. Decided 2026-11-15: widening the rule to every non-control role would add a control line, in the snapshot's budget, for each row, cell or paragraph a page styles with a pointer, for clicks a text target already reaches.
- **act** runs 1–20 steps in order, stopping at the first failure: `click`, `fill`, `type`, `press`, `select`, `check`, `uncheck`, `hover`, `upload`. Each but `press` names its element by `ref` or `target` (see Targets); a target is resolved when its step runs, so one after a step that navigated finds its element in the new page. Pointer steps check that nothing covers the element's centre (its own label may), typing steps that it has the focus before and after. The centre is that of the element's largest box, so a wrapped link isn't aimed at a sliver of its first line (PROJ-115). When something covers the centre, or it isn't on screen, act scrolls the element to the middle of the screen once (`scrollIntoView` in the isolated world: a sticky header covers what scrolling just into view leaves at the top) and looks again, then every 100 ms for up to the step's `cover_wait_ms` (1,000 ms by default, 0 not to wait, at most 10,000; in the REST step and the MCP `act` tool alike), finding the box afresh each time in case the element moved, so an overlay fading out is waited out. The wait counts from the first covered look, and is shared with the check before pressing at human pace: when something covered the point during the glide, act aims once more within what is left of it. An iframe over the element is waited for like any other cover. The looks are hit tests in the isolated world: only the scroll and the input reach the page, and an uncovered element is never scrolled to the middle. A handoff, a stop or the token's revocation ends the wait at once, and the call holds its lease no longer than the wait plus its own timeouts. A step still covered is refused (409) naming what covers it and, if one is open that the element isn't in, a dialog's title (`[role=dialog]`, `[role=alertdialog]`, `[aria-modal=true]` or `dialog:modal`; its label, else its first heading, at most 60 characters), each fenced. Each step takes `pace` (see Pace above; it applies to `click`, `hover`, `check`, `uncheck`, `type` and `press`). At human pace a pointer step glides from where act's pointer last stopped (in from an edge of the viewport on the first move, and again once a person has had the browser) to a point scattered within the element's box (`DOM.getContentQuads`; the same hit test as the centre's, and the point must not be on a control inside the element, such as a row's Delete button or a tab's close ×: a link, button, form field, `summary`, an element with a control's role, `onclick`, a non-negative `tabindex` or `contenteditable`; else the centre), with one `mouseMoved` per 60 Hz step, then checks the point is still the element's before pressing, since the glide took a moment. When a control inside the element has appeared under the point meanwhile (one shown on hover), the pointer moves on to the centre and presses there. `type` keys at a typist's rhythm; `fill` still puts its text in at once. Each session has its own random source, kept with the tools' per-session state. Each result names the element's role and name as they are when it acts; typed text is only counted. `fill` and `type` refuse date, time, range, colour and file inputs; `click` refuses a file input (or its label), whose chooser is a window of the browser's own that nothing over CDP could close, and points at `upload`. Clicking a date input opens Chrome's picker, which `press Escape` closes. A page's own button that opens a file chooser can't be told apart from another button: click it, then answer the chooser with `choose_files` (File choosers, below); act's answer ends with the chooser notice once it is open. The page can still change between a check and the input; act resolves, checks and dispatches back to back and echoes what it hit, and promises no more.
- **Changes** (PROJ-114): after its steps, act answers with what changed on the page since the agent's last snapshot of that document, under `### Changes`, instead of acting blind or asking for a whole snapshot (4,000–20,000 characters). It is the lines added (`+ `) or removed (`- `), each with its ref, after its nearest enclosing lines that didn't change (`  `, indented by two per level, at most 8 levels), at most 20 lines, then `(N more lines; snapshot for the whole page)`. A changed state (`[checked]`, `[expanded]`, `[filled]`, `[under an iframe]`…) or value is one removed and one added line with the same ref; a secret field still shows only `[filled]` or `[empty]`. When the two lines would read the same (what changed is past what a line shows, such as a long text's end), the added one ends `(changed past what this line shows)`. A removed item whose enclosing item changed or went too is printed right after that item's removed line, under it. Focus moving alone isn't a change; lines that only moved (another order, scrolled into another tier, a navigation summed up) aren't either, since a diff compares the page's items, matched by node and line, not the snapshot's text, which `snapshot`'s budget orders and cuts. Refs are stable within a document, so an unchanged line is the same element. An item's enclosing items are those whose node is its ancestor in the DOM (a link's paragraph, by its text). Nothing changed: `no changes since the last snapshot`. Another document in the tab (the steps navigated, or the page did since the snapshot, even to the same address): `navigated to <URL>` and `take a snapshot of the new page`, never a diff of one document against another (when act's steps navigated, this is known from the frame tree before any read, so the new page isn't read only to say so); the read is also checked against the tab's document afterwards, so one that straddles a navigation counts as one. No earlier snapshot of this document: `no earlier snapshot of this page; take one`. One that was too large to keep (its list past 4 MB): `this page is too large for BrowserPier to keep its last snapshot to compare with (over 4 MB); take a snapshot to see it`, which act says by default too, without reading the page (the tab remembers this for that document), and `snapshot` with `diff` leads with `This page is too large for BrowserPier to keep a snapshot of to compare with (over 4 MB); the whole page follows.` The diff text is fenced like a snapshot.
  - **Default:** `changes` is on when the active tab has a snapshot of its current document and `snapshot` isn't set; `changes: false` turns it off, `changes: true` asks for it anyway (`snapshot` and `changes` together are refused, 400). Decided 2026-11-15: most actions change a handful of lines, so the agent sees what its action did for a few hundred characters, and an agent that never snapshots pays nothing.
  - **The baseline** is the full item list of the tab's last read (not the snapshot's budgeted text), in the orchestrator's memory only: every `snapshot` (and act's `snapshot: true`) replaces it, and so does each diff, so the next action reports only its own changes. A diff that finds no baseline keeps its read as one; one that finds another document drops it. Kept lists are compacted (each line's key is a hash of its whole content; what is kept of names and text is what a diff line shows), at most 4 MB each and 32 MB across all sessions, the oldest dropped first; and dropped when the session ends (a call still finishing then keeps nothing, since its lease has ended), a person has had the browser (a handoff or taking control: refs go stale then too), the tab closes, or the session's ref map is new.
  - **The read** is a whole page read, as `snapshot` (after the same 100 ms act waits between steps, so the page can react), taking one of the shared read slots, for which it waits 1.5 s at most (not the 10 s other reads wait: the changes are extra, and the call holds the session meanwhile). The steps have already run, so whatever happens to it their result stands: when the slots stay busy, the page is too large or the read fails, act answers 200 with the steps and `The changes couldn't be read: …`, never an error that would make the agent run the steps again.
  - **`snapshot` with `diff: true`** answers in the same format, from the same baseline; with no baseline, or another document, it gives the whole snapshot after a line saying so, and that becomes the baseline (`max_chars` 0 with `diff` is refused, 400).
  - The activity log records the actions as before, and a snapshot diff as `Read the page`; never a diff's lines.
- **Downloads** (PROJ-116): when act's steps downloaded something, its answer ends with `### Downloads` (see Download notices above), after any changes or snapshot; `download_wait_ms` sets how long it waits for a download under way.
- **upload** (PROJ-117) `{ref, files: ["name", …]}` sets files on a file input without a chooser, for agents with no CDP client of their own. Each name (1 to 10) is a bare file name in the session's `files/uploads`, as `upload_file` or `POST /api/sessions/{id}/files` returned it, checked as those check it: no `/`, `\` or NUL, not `.`, `..` or another name starting with a dot, at most 255 bytes (400 otherwise); two dots inside a name (`report..v2.pdf`) are just dots. It must be a regular file there, checked through `os.Root` with no link followed, not even one inside the folder (422 `no uploaded file named "x"; upload it first with upload_file`). The ref must be an `<input type=file>`, or a `<label>` whose control is one (an input styled out of sight under its label is common: a transparent one the snapshot lists, named by its label; an `aria-hidden` or `display:none` one it doesn't, and then `find` gives the label's ref for its text). Several files need the input's `multiple`; a disabled input is refused. act sets them with `DOM.setFileInputFiles` on the input's backend node, with `/files/uploads/<name>` paths and nothing else, and checks the input holds as many files after; Chromium fires trusted `input` and `change` events, as when a person picks the files (see Anti-bot approach). The result names the input and the count: `uploaded 2 files to a7e12 button "Attachments"`. Any other target (a page's own button that opens a chooser with a script, say) answers 422 saying to target the `<input type=file>` itself, often styled out of sight; if the snapshot doesn't list it, the `<label>` that controls it; for a page's own button, to click it and answer the chooser with `choose_files` (File choosers, below). An upload step has no `pace`: nothing moves or types.
- **wait_for** waits for one condition: `text` (the page's rendered text contains it, ignoring case), a `ref` visible or hidden (`state`; a ref gone counts as hidden), a `target` visible or hidden (PROJ-123), `url_change`, or `load` (PROJ-122). It looks at once, then every 250 ms, for up to `timeout_ms` (10 s by default, 30 s at most), its last look at the deadline. Its answer says how it went (PROJ-122): `already true when wait started: text "Hello" is on the page` when the first look, before any sleep, found it so (an agent waiting for text already there, its own echoed message most often, learns its wait proved nothing); else `waited 1.4 s for text "Hello" to appear`; else `timed out after 10 s waiting for a7e12 to be visible`, and for a ref awaited visible, `; now: a7e12 is on the page but hidden` or `; now: a7e12 is gone (the page changed)`. A ref stale at the first look is refused (409) as by every tool. One that goes during the wait: a node taken out of its document may be put back, so the wait goes on; another document in the tab never brings it back, so the wait ends at once, answered `gave up after 1.2 s waiting for a7e12 to be visible; now: a7e12 is gone (the page changed)`. These answers are BrowserPier's words, outside the fence: the condition is the agent's own (its text quoted, at most 80 characters), and the state is the page's state, never its text. The activity log says `Waited for text: already true`, `: ok after 1.4 s`, `: timed out`.
  - **A target** (PROJ-123) is visible when exactly one visible element matches it (with `nth`, when that one exists), and the answer gives its ref: `waited 0.8 s for role=button[name="Save"] to be visible (it is a7e12)`. Hidden is no visible match (with `nth`, no Nth). Each look is a whole-page read, as act's, so the looks back off: 250 ms, then 500 ms, then every second. A look waits for a read slot no later than the deadline, and one that finds both slots taken, or that the browser refuses part of (as it can mid-navigation), is looked at again rather than ending the wait: at the deadline the answer says `now: BrowserPier was too busy reading other large pages to look` (after what the last look that could read found, if one did), and a refusal that lasted to the deadline is the answer (502). Several matches for 1 s, or at the deadline, fail the wait with act's ambiguity error (409, the candidates with refs); none at the deadline answers `timed out after 10 s waiting for role=button[name="Save"] to be visible; now: no visible element matches`, and a hidden wait still seeing some, `now: 2 visible elements match` (counts, never text). The target is the agent's own, at most 160 characters in the answer; the activity log names only its kind (`Waited for a role target to be visible: ok after 0.8 s`), since a target may quote the page.
  - **`load`** is for a single-page app that loads, then fetches its content: the tab's document is `complete` (its load event has ended), and neither the load nor any request ended in the last 500 ms. It reads, in the isolated world, `document.readyState` and the page's Resource Timing entries (`performance.getEntriesByType('resource')`: the latest `responseEnd`, against `performance.now()`), which the browser keeps for every page anyway; nothing is hooked or observed in the main world, no domain is enabled, no `PerformanceObserver` or mark is made. Resource Timing records a request when it ends, so requests still under way aren't seen: a long poll that never answers doesn't hold the wait, and a request slower than 500 ms isn't waited for. Counting requests in flight would take a hook in the page or `Network.enable`, which the tools never do. When the entries go down (the page cleared them), the quiet also counts from then. The top frame's requests only (an iframe has a list of its own), and Chrome keeps 250 entries unless the page asks for more: once the list is full, new requests aren't seen, so a met `load` with exactly 250 entries adds `(but the page's list of finished requests is full at 250, so later ones can't be seen)`. A timeout says which part was missing: `now: the document is still loading (readyState interactive)` or `now: the document is complete, but requests keep ending (the last 0.2 s ago)`. A page that stops its own load (`window.stop()`) is complete, but its load event never comes: once the document has been complete without one for 500 ms, the quiet counts from its last request (or its own response) instead, a met wait adds `(its load event never ran, as when a page stops its own load: the quiet counts from its last request)`, and a timeout says `the document is complete, but its load event hasn't run` before then, `the document is complete without its load event (the page stopped its load), but requests keep ending (…)` after.
- **navigate** takes only `http` and `https` URLs without a user name or password, and waits up to 30 s for the page to load. Then it waits out script redirects (PROJ-121), as a sign-in bounce makes them: an app's session check, the identity provider, its callback page's own redirect, each starting a navigation just after loading. Every 100 ms for 300 ms it looks whether the tab's document changed or went back to loading (the frame tree's document and `document.readyState`, polled as for the load: no domain enabled, no events); if so it waits for that page to load and watches again, until a page stays put for 300 ms, for at most 15 s and within the 30 s. A page still moving then is answered as it stands, with `The page was still redirecting after 15 s.` (`after 30 s.` when the load took the rest). Going back, forward or reloading waits the same way; a move within the document (only the fragment changed) waits for nothing. Polling sees a new document when it arrives, not when the page asks for it, so a hop whose next page takes more than about 300 ms to start arriving ends the wait there, and the answer shows the page before it. When the page it landed on, the last of any chain, is at another address than the one asked for (a server or script redirect), it adds `Redirected from: <the URL asked for>` under the URL, in the fence (PROJ-110); a different fragment, a trailing slash, the case of the scheme and host, a default port or percent-encoding don't count. Nor does a name typed in Unicode coming back as punycode: without an IDNA library, each label must match, or be a Unicode label against an `xn--` one with the same ASCII letters in order, so two Unicode names sharing those letters can pass as one. The `URL:` line always shows the real address. A navigation that fails, or lands on the browser's error page (a hop of the chain can), answers 502 with the browser's error when there is one; when the address that failed isn't the one asked for (a redirect led there; the error page names it), the error says `couldn't open the page after a redirect` and `Failed at: <that URL>`, in the fence. Only a new error page counts: a navigation from an error page that is still loading after 30 s is answered as still loading, not as failing at the old page's address. `net::ERR_ABORTED` (a download address, an empty 204 response) leaves the tab where it was, so it is answered at once, saying so, without waiting for an error page. A move that lands on an error page is in the activity log (`Went back, but the page couldn't be loaded`), since the tab did move.
- **Iframes in the way** (PROJ-110): the tools don't read or act inside iframes, but agents often meet one on top of the page, a cookie-consent banner from another site most of all. When what covers an element `act` aims at is an iframe, the error says so, with the origin of the document the iframe shows (from `DOM.describeNode`'s content document, or for a frame from another site its own target in `Target.getTargets`), never its `src`, which the page sets and can send the frame away from; if that isn't known, it says "from an unknown origin". The advice after the fence is BrowserPier's own voice, so it says only what is known (an iframe from that origin is in the way, and the tools can't reach into frames) and doesn't guess what the frame is: it suggests checking what it is, then points to what works: a handoff (`request_handoff`, `POST /api/sessions/{id}/handoff`) so a person deals with it, or restarting the browser in Visual mode and working on it on a screenshot. `snapshot` marks a control whose centre a shown iframe covers `[under an iframe]`, from the DOM snapshot's boxes and paint order alone (`includePaintOrder`; nothing more is asked of the page): the iframe's box holds the control's centre and its paint layer comes later. An iframe that clicks go through (`pointer-events: none`) or that has a negative `z-index` on it or an ancestor (Chromium numbers such a layer after its parent though it paints under the parent's content) marks nothing. The mark is a hint, not a promise: a marked control is one `act` probably can't click, and `act` checks before clicking. A known false positive: an iframe clipped by an ancestor's `overflow` still marks the controls under the part that's cut away, since the DOM snapshot's boxes aren't clipped; `act`'s hit test clicks those. The mark misses a control out of view that a fixed banner will cover once scrolled to; `act`'s hit test still catches that.
- **Cloudflare challenges** (PROJ-120, for PROJ-25): Cloudflare's challenge page ("Just a moment…") often passes by itself; when it doesn't, it wants a click on its checkbox, which sits in a closed shadow root inside a cross-origin iframe, so neither a snapshot nor act can reach it, and a click over CDP wouldn't pass it anyway. A native click does. So `snapshot` (diff too), `navigate`, `find` and `page_content` (markdown and readability) add one line when the page is one, after the fence (the words are BrowserPier's): `Cloudflare challenge. If it is still here after about 10 s, take a screenshot and check its checkbox, which snapshot can't see, is at this point (position read from the page's layout; the browser's own prompts can cover the page), then click it with a real click: computer click at screen x=…, y=… (MCP: click at …, … in screenshot pixels), or request_handoff with reason captcha. A named profile keeps the pass.` BrowserPier never clicks it by itself. The point comes from the page's layout, and the browser's own UI (a permission prompt, a bubble) can sit over the content area where a page could have put a lookalike widget, so the agent is told to look before it clicks.
  - **Detection** is part of the isolated-world read these tools already make (`jsPageInfo`): an `input` whose id starts with `cf-chl-widget-` (the challenge widget's hidden response input) whose parent has a non-empty box, on a page with a mark of Cloudflare's challenge page: a `#challenge-form` or `#challenge-stage` element, a script or iframe from the page's **own origin** whose path starts `/cdn-cgi/challenge-platform/` (not `/cdn-cgi/challenge-platform/scripts/jsd/`, the JavaScript-detections script Cloudflare adds to ordinary pages), or a title starting "Just a moment" (any case; the title isn't required, since Cloudflare words it in the visitor's language: a real challenge page seen on 2026-11-16 had a Latvian title, no `#challenge-stage`/`#challenge-form`, and only its own-origin `…/challenge-platform/h/b/orchestrate/…` script). Its widget's input is the same as a site's own Turnstile's (`cf-chl-widget-…_response`, `name="cf-turnstile-response"`), so the input tells nothing: a site's own Turnstile is told apart by its page, whose Turnstile script and iframe come from `challenges.cloudflare.com`, another origin, and which carries none of the marks. A widget already answered (its input has a value) doesn't count. No domain, no main-world script, no new method: `querySelector`s, and the parent's `getBoundingClientRect` only when the input is there.
  - **The point** is the checkbox's middle as the page lays the widget out: 21 px in from its left edge, halfway down its first 65 px. It goes from the viewport's CSS pixels to screen pixels with SPEC §3's geometry: the window at 0,0 with no frame, so x × `devicePixelRatio`, and y × `devicePixelRatio` below the browser's own UI (tabs and address bar), which is `outerHeight − innerHeight × devicePixelRatio`. The display's scale factor is 1, so a `devicePixelRatio` other than 1 is the page's zoom, which shrinks `innerHeight` but not `outerHeight` (at 100% this is `outerHeight − innerHeight`). The MCP point is that screen point in the screenshot's pixels, through the MCP tools' own scaling (`internal/screenshot`). `TestWindowGeometryMatchesTheImage` ties the window's place and the 32-pixel taskbar to the image's flags, so a change there breaks a test rather than moving the click.
  - **The numbers come from the page** (its layout, its zoom), so the point is clamped to the browser's content area, never its UI or the taskbar: two integers that can only name a pixel there. They are the line's only part from the page, so the line sits after the fence rather than in it, and says the position was read from the page's layout (a page can fake a challenge, so the agent looks before it clicks). Decided 2026-11-16, against fencing BrowserPier's own instructions with the page's text. When the checkbox is outside the visible area, the line gives no point and says to scroll to it and look again. A `/computer` click works on an API-mode session too.
  - **Limits:** `navigate` answers once the page has loaded, often before Cloudflare's script has added the widget, so the line may first come with the next `snapshot`. A site's own Turnstile whose hidden input took the challenge's id prefix would count too; its checkbox is in the same place. Other vendors' challenges aren't looked for. Visual-mode sessions get nothing new: the page tools don't run there.
- **The new-tab notice** gives the page's origin and path, escaped and capped at 80 characters (`a new tab opened: t3 (https://accounts.example/signin)`), but not its query or fragment: the path tells a sign-in popup from a help page for a few tokens, while a popup's query is mostly OAuth state, and `tabs` lists the whole address.
- **Many tabs** (PROJ-160): agents open tabs and seldom close them, and each holds its page's memory. From 10 open tabs on, the six tools end their answer with one line of BrowserPier's own, after the fence: `12 tabs are open; close the ones you're done with (tabs, action close)`. `tabs` gives it on every answer while there are 10 or more; another tool once each time the count has grown since its previous answer, not on every one. It's built from the count alone, never a title or an address, and the count comes from the `Target.getTargets` call each tool makes already: no CDP call of its own, and nothing in Visual mode. Tabs restored at start count too. BrowserPier closes no tab by itself and caps none (§13).
- **Isolated worlds, exactly:** code never runs in a world by its context number, which a cross-process navigation can make name a page's own world. Each call reads the world's `globalThis` once, keeps it only if the frame's document didn't change meanwhile, and runs everything as functions on it, or on nodes checked to be in it.
- **Memory:** one answer from the browser is capped at 32 MiB, and at most two whole-page reads (a DOM snapshot and an accessibility tree) run at once across all sessions, so large pages can't take a small host's memory; a read waits at most 10 seconds for a slot, and a handoff or stop still ends the wait. A page read keeps at most 4 MB of the page's text (find searches all of it, whole blocks included); when a page has more, find says some was left out.
- **Answers:** 200 with the text; 400 for a bad request; 401 when the token is revoked during the call; 404 for a session the token can't see; 409 when the session is in Visual mode, a person has the browser, a ref is stale or in another tab, a target matches no visible element or several, an element is covered or loses the focus, or the page navigated in the middle of the call (an element's object died with its document: never a 502, since the browser refused nothing; a ref whose document went between resolving it and checking it is stale, and a wait looks again); 422 for an input `act` doesn't handle, or a page too large to read; 502 when the browser refuses or can't be reached (its words fenced); 503 when other sessions' large pages have held both read slots for 10 seconds (try again shortly: a call waiting for one holds its session, so it doesn't wait longer); 504 when the page stops answering (a dialog, most likely).
- **Dialogs:** without `Page.enable` an `alert()` can't be seen or closed over CDP, so a call that the page stops answering while the browser still does says "the page is busy or has a dialog open; if it stays that way, request a handoff."
- **The activity log** records the action and refs only (`Clicked a7e12`, `Filled a7e13 (12 characters)`), never page text or typed text. The one exception is the active tab's title, in an entry of its own that only the admin reads (§9 Agent log). An upload names the files, which are the agent's own words (`Uploaded report.pdf to a7e12`); the web UI escapes them like every entry.

### Page content

`POST /api/sessions/{id}/content` returns the active tab (the page tools' active tab) in one of four formats, for an agent that wants a whole page or article rather than its controls (PROJ-20). MCP has the same as `page_content`.

| `format` | Mode | Answer | Options |
|---|---|---|---|
| `markdown` | API | `{"text": "…"}`: the whole page as Markdown (headings, lists, quotes, code, simple tables, links and images with absolute addresses), fenced | `max_chars` (default 20,000, at most 100,000), `offset` |
| `readability` | API | `{"text": "…"}`: the main text only, as plain text without links, as a reader view shows it; the fewest tokens | the same |
| `screenshot` | both | `image/png` of the screen, as `/screenshot` | `width` |
| `pdf` | API | `application/pdf`, as an attachment, never rendered; over MCP an embedded `application/pdf` resource | `landscape`, `background`, `pages` (like `"1-5, 8"`) |

- **How Markdown and the main text are made:** one DOM snapshot (`DOMSnapshot.captureSnapshot`) through the same kind of per-call connection as the page tools, with its own allow-list (`internal/pagetools`: targets, frame tree, isolated world for finding the active tab, the DOM snapshot and `Page.printToPDF`; no input, navigation or DOM writes). The snapshot is turned into text in Go (`internal/pagetext`); no script of BrowserPier's runs to read the page (the isolated-world look for a Cloudflare challenge, see API-mode page tools, reads a widget's box, not the text). The tab's document is checked before and after: a snapshot that straddles a navigation is taken again once, then refused.
- **What is left out:** what the snapshot shows isn't rendered (`display:none`, `visibility:hidden`, zero-size, scripts, styles, templates, SVG), form fields with their values, however they were filled (a password never comes this way; read controls with `snapshot`), and iframes' documents (one `[iframe: origin]` line). Text a person may not see but that is laid out (transparent, off-screen, clipped) stays, fenced, as in a snapshot; so does `aria-hidden` text, which a person sees but `snapshot` (reading the accessibility tree) leaves out. Shadow roots are read where they are shown. An element with no box of its own but shown content (`display:contents`) keeps its role: a heading, a link, a table row.
- **Links** keep absolute `http`, `https` and `mailto` addresses of up to 512 characters; a link to a script, to this page's fragment, or with a user name in it (`https://good.example@evil.example/`, as `navigate` refuses) keeps only its text. A link around blocks (a card on a front page) has its blocks, then its address on a line of its own. Page text can't make a heading, list, quote, fence or table row (it is escaped), and a `<!--` in it is written `<\!--`, so it can't hide the text after it from whoever renders the Markdown (the fence does the same).
- **The main text** (`readability`) follows reader views' heuristics, written for BrowserPier rather than ported: navigation, headers and footers outside the article, sidebars, forms, dialogs, buttons and blocks whose class or id names a banner, cookies, comments, sharing… (as words, so `cookie_notice`, `siteFooter` and `has-sidebar` count; never a block holding an `<article>` or `<main>` whose own class isn't one of these, so a comment's `<article class="comment-body">` doesn't count) go; a page with one `<article>`, else one `<main>`, has its main text there; otherwise blocks are scored on their paragraphs' length and commas and penalised for link text. Link lists in the result are dropped, unless the page is mostly links (a news front page). A word like content or post doesn't save a block named for comments, a footer or a sidebar (`post-comments`, `footer-content`). One retry, for a wrapper whose class misled it (`<div id="community-page">`, `<div class="layout has-sidebar">`): when the page has no article or main and one block left out by its class held most of the page's text (more than half when under 200 characters was found, 80% whatever was found), it is found again with that block kept, and taken if it keeps all that was found first, or joined with it in the page's order when the two don't overlap. Comments, footers and banners are never taken for wrappers. Forum threads, where every post is a block of its own, come back as one post (PROJ-92). A page where nothing stands out comes back whole, cleaned.
- **Length:** the text is cut at `max_chars` characters, at a line's end when one is near, and the line after the fence says `Characters 0 to 20,000 of 54,321. Read on with offset 20000.` A part that starts inside a code block opens it again. BrowserPier renders at most 2 MB of text and 200,000 DOM nodes of a page, 256 levels deep (deeper elements are their text alone, after a note saying so), in time and memory linear in the page. The DOM snapshot sends a string once however many nodes share it, so a page can give thousands of nodes the same megabyte; BrowserPier reads at most 256 bytes of a class or id, 1 KB of other attributes, 2 KB of an address, and 8 MB of shown text from the whole page, so that costs nothing either. Text that isn't shown, or is a script's, a style's or a field's, spends none of it, so hidden megabytes can't push the article out; text in navigation, sidebars, forms and dialogs has 2 MB of its own. When a page has more shown text than that, the line after the last part's fence says so, in both formats; beyond that it keeps what fits and says so, or answers 422 (`page too large to read; use find`). A content call takes one of the whole-page read slots the page tools share (two at once, for every session) and holds it while it renders or prints: at most about 30 seconds (the snapshot's 20, rendering's 10) for text, 60 for a PDF, and a handoff, a stop or the caller leaving ends it at once. When the slots stay taken for 10 seconds it answers 503 (busy, try again).
- **Screenshots** come from the X display, in both modes, with no CDP at all: the same picture as `/screenshot` and the `screenshot` tool, browser window included. `Page.captureScreenshot` would give the page alone and a full-page capture, but a full-page capture resizes the page, which it can see.
- **PDF** is Chromium's print (`Page.printToPDF`), at most 10 MiB (ask for fewer `pages` beyond it) and 60 seconds. The page sees it print, as when a person presses ctrl+P (see Anti-bot approach). A PDF, like a screenshot, is the page as it is printed or shown: it holds form fields' values in clear (a password field shows dots, but a one-time code or a typed address doesn't), and what the page's CSS shows only in print.
- **Visual mode:** `markdown`, `readability` and `pdf` answer 409 before anything connects; `screenshot` works. During a handoff only `screenshot` works, as for `/screenshot`.
- **The activity log** says `Read the page as Markdown`, `Read the page's main text`, `Took a screenshot` or `Printed the page to PDF (120 kB)`, never page text (but for the tab's title, in an entry of its own for the admin only, §9 Agent log).

### Files

Downloads land in a per-profile folder. The API lists, fetches and deletes them, and uploads files into the session so the agent or a human can pick them in a file chooser. Files are kept with the profile until deleted, or until a size cap evicts the oldest.

- Each profile has `files/downloads` and `files/uploads`, mounted at `/files` in its browser. A managed Chromium policy sends every download to `/files/downloads` without asking, in both modes, with no CDP involved.
- An uploaded file lands in `/files/uploads/<name>` (the response gives the path; a name already taken becomes `name (2).ext`): an agent sets it on a file input with act's `upload` step, or with `DOM.setFileInputFiles` from its own CDP client, or answers a page's file chooser with it (`choose_files`), and a person picks it in the file chooser modal. A person's **Upload from this device** in that modal lands there too, through the same code. Uploads are at most 100 MiB.
- **Over MCP,** `upload_file {session_id, name, content_base64}` writes the file through the same code as the REST endpoint (the token's scopes, the cap and eviction below, the activity log's `Uploaded report.pdf`) and returns the name to pass to `upload`. It takes at most 20 MiB: the file comes whole inside one MCP message, a third larger in base64, and is held in memory while it is decoded, so `/mcp` takes requests up to about 28 MiB (the SDK's default is 4 MiB). Each such request holds several copies of its message for a moment (over 100 MiB near the cap), so only two requests over 4 MiB (or of unknown length and longer than that) are served at once, across all tokens, and others wait their turn; smaller requests never wait. Whitespace in the base64 (line breaks, spaces, tabs: MIME wraps it at 76 characters) is dropped before the size check and the decoding. Content that isn't base64 (standard, padded or not) or is over 20 MiB is refused with a message saying so; larger files go through the REST endpoint.
- The cap is per profile, downloads and uploads together (`BROWSERPIER_FILES_LIMIT_MB`, default 1024); the oldest files go first, and a download in progress is never evicted.
- Downloads come from untrusted pages, so the API always serves them as attachments (`application/octet-stream`, `nosniff`, a sandbox CSP), never rendered.
- The browser can put anything in these folders, symlinks included. The orchestrator only touches them through `os.Root` and only serves regular files, so a planted link can't expose a host file.
- Actions that may start a download say what they downloaded (Download notices, above). The list holds finished downloads only: neither a `.crdownload` nor Chrome's hidden temporary files.
- **File choosers** (PROJ-152): a page's file chooser (a file input, a script's `input.click()`, `showOpenFilePicker`) shows no dialog: the browser's portal (§3) holds it, in either mode, with no CDP. An agent answers it as below; the person in control answers it in the live view or on the handoff page (People, below).
  - **Listing:** `GET /api/sessions/{id}/chooser` answers `{"choosers": [{"id": "c3", "multiple": false}], "text": "…"}`. Ids are never reused within a browser's life. What each accepts is the patterns Chromium made of the input's `accept` (MIME types become extensions; the catch-all is dropped): page text, so cleaned (invisible characters and control characters gone), at most 32 of 64 bytes, and given only fenced, in `text`, never as bare JSON strings; the browser doesn't enforce it. Listing is a read: allowed during a handoff, and it isn't agent input (no `AgentInput`, no `Touch`). MCP: `list_files` adds the profile's open choosers.
  - **Answering:** `POST /api/sessions/{id}/chooser` with `{id, files: [names]}` (1 to 10; one unless the chooser is `multiple`) or `{id, cancel: true}`. Names are bare names of files in the profile's `files/uploads`, as `upload_file` returned them: `files.ValidName` (400 otherwise), then a regular file opened through `os.Root` with no link followed (422 `no uploaded file named "x"`), before anything goes to the browser; never `files/downloads` (decided for now, revisitable). The browser checks each name again with `lstat` directly in `/files/uploads` and builds the only URI Chromium gets, `file:///files/uploads/<percent-encoded name>`. Answering is input: it goes through `AgentInput` (the 5-second rule) and is refused (409) while a person has control or during a handoff. 409 also for an id that is gone (`that file chooser closed`), 422 for several files to a single-file chooser, 503 when the portal isn't running (a browser started on an image from before it). MCP: `choose_files {session_id, id, files}`, an empty list cancelling.
  - **The time limit:** a chooser nobody answers is cancelled after 5 minutes (decided for now, revisitable); the page sees `cancel`. The 5 minutes start again whenever control changes hands (a person takes control or hands back, a handoff starts or ends; PROJ-181), so whoever has the browser then gets the whole time.
  - **People** (PROJ-181): while a person has control (the live view's Take control, or a handoff link's), the page shows them a centred modal for the oldest open chooser (§7, `file_upload`; §9). Its routes are `GET`/`POST /profiles/{name}/chooser` and `POST /profiles/{name}/chooser/upload` for the signed-in admin, and the same under `/h/{token}/chooser` for a handoff link's holder (its own session only, while the link is open, §7). The page polls `GET …/chooser` every second while it has control; it answers the modal (rendered by the server, the names escaped) or 204, and isn't input. `POST …/chooser` takes `id` and `file` (repeated) or `cancel`, checked as an agent's answer is (bare names of regular files in the uploads, before anything reaches the browser); `POST …/chooser/upload` takes `id`, then `file`, stores it through the same code as an agent's upload, then answers with it. Each is refused (409) unless the one asking holds control (PROJ-184): Take control records who took it, the admin (any of their signed-in browsers, so signing in again while a live view stays open changes nothing) or the handoff link, so while the link's holder drives the admin's routes are refused, and while the admin drives from the live view the link's are. Each Take control is also a turn of its own: a live view whose control ended behind its back (the handoff finished, Hand back from another page) and was taken by someone else, even another of the admin's views, neither releases it nor lifts their keys when it closes, loses focus or hands back, and its input and clipboard reads are refused, checked against its turn in the same step that admits them. A turn is the takeover's number (PROJ-196, §3 Control): the chooser's answer names it to the browser like the live view's input, so the browser refuses an answer held up past the end of that takeover. The hand-back itself lets go of any key or button the live view still holds, as it fences the takeover, however control ends. A Take control that waited for an agent's action to let go is refused if control was handed back meanwhile. The agent's answer is refused while a person has control. Nothing of the page reaches the modal: not its accept list, not its address. The activity log says `A person chose 1 file` or `Cancelled a file chooser`, never a name.
  - **Notices:** while a chooser is open after an action, the answers of `act`, `/click`, `/type` and `/computer` (MCP `act`, `click`, `type_text`, `press_keys` and the other Visual tools) end with one line in BrowserPier's own words, outside the fence and quoting nothing from the page: `a file chooser is open (c3): choose_files answers or cancels it`. act's text ends with it; the Visual routes carry it in an `X-File-Chooser` header, as `X-Downloads`. The chooser opens a moment after the click, so the line may come one action late (an instant click usually has it; `list_files` and `GET …/chooser` always do).
  - **Save as** (ctrl+S, `showSaveFilePicker`): answered at once with a new, empty file in `/files/downloads`, which Chromium then writes, so the file is a download like any other: the suggested name without path separators, control characters or a leading dot, at most 240 bytes, `name (2).ext` when taken (a planted link counts as taken), created exclusively without following a link; at most 64 in 10 minutes. Chromium's default kind is kept (MHTML is out of scope). Saving several files into a folder is refused.
  - **Activity log:** `The page opened a file chooser`, `Answered a file chooser with 2 files`, `Cancelled a file chooser`; never the accept list or a file name.

### MCP tools

- **Endpoint:** `/mcp` speaks MCP over streamable HTTP and takes an agent token like the API. Each tool calls the API in-process with the caller's token, so scopes, refusals and the agent log are the API's. An MCP session belongs to the token that opened it.
- **Setup guide:** `GET /mcp/setup` is a Markdown page for agents, with this BrowserPier's address filled in, that tells an agent how to connect itself. It covers checking `PIER_TOKEN` (without printing it), the setup for each common client with the token read from the variable at connect time, never written into a config, checking with `list_profiles`, and the REST API as the fallback without MCP. It holds no secret, so it needs no sign-in; under `/mcp/` Umbrel lets it through.
- **Tools:**
  - `list_profiles`, `start_browser` (with `allow_ads` for a session without ad and tracker blocking), `stop_browser`
  - Visual mode: `screenshot`, `visual_snapshot` (see Visual-mode element tree), `click` (at a point or a `ref`), `type_text`, `press_keys`, `open_url`, `scroll`, `drag`, `wait`, `zoom`
  - API mode: `snapshot`, `find`, `act`, `wait_for`, `navigate`, `tabs` (see API-mode page tools)
  - `page_content`: Markdown, the main text or a PDF in API mode, a screenshot in either (see Page content)
  - `list_files`, `upload_file`, `choose_files` (see Files)
  - `request_handoff`, `wait_for_handoff`, `cancel_handoff`
  - `call_status {session_id, call_id}` and `session_status {session_id}`: how a call with a `call_id` went, and the session's state, mode, the agent's calls under way and its recent ones (see Retries in §8). `click`, `type_text`, `press_keys`, `open_url`, `scroll`, `drag`, `act`, `navigate` and `tabs` take an optional `call_id`, which their description, the server's instructions and `/mcp/setup` say to send with an action that must not happen twice.
- **Explicit handles:** `start_browser` returns a `session_id` and every stateful tool takes it as an argument. Nothing depends on the MCP connection staying open, so several browsers can run in one conversation.
- **Untrusted content:** every piece of page-derived text returned to an agent (downloaded file names, the page tools' snapshots, matches, step results and tab names, Visual mode's element tree and what a click by ref names, errors that quote the page, and the page as Markdown or main text) is handled the same way:
  - wrapped in an `<untrusted-content-…>` fence whose tag name carries a random marker, so the page can't write the closing tag, saying it is data, not instructions (look-alike tags in the text are defused)
  - stripped of invisible Unicode (zero-width, bidi, tag characters), with HTML comments defused rather than dropped: `<!--` is written `<\!--`. What the fence wraps is page text, file names, logs and errors, never HTML, so a `<!--` in it is text a person sees; dropping it hid everything after it, and defused, a `<!--` can't hide text from a person reading a transcript that renders HTML or Markdown either (PROJ-95). That holds for `<!--` only: other constructs a renderer may hide, such as `<!x …>`, `<?…?>` and `<![CDATA[…]]>`, aren't defused yet, a follow-up tracked in PROJ-129. A caller that ever fences raw HTML drops its comments itself, by parsing it.
  - password and one-time-code field values redacted (`internal/fence`), at the source where the output is structured (a snapshot shows such a field as `[filled]`). Redaction prevents accidental leaks, not leaks by a manipulated agent: a code split across several boxes, one shown as page text (a webmail profile) or a token in a URL still reaches the agent.
  - **secrets BrowserPier itself filled replaced by `<hidden>`** (PROJ-125, for PROJ-57's vault fills; see also PROJ-60 and PROJ-61), wherever the page echoes them, as below.
- **Filled secrets** (PROJ-125): once BrowserPier types a value the agent never sees (a vault fill, PROJ-57), it knows that value, so it takes it out of everything it hands back, not only out of the field: a page may echo it in its text, its title, a GET form's URL, a link or an error.
  - **The set** is per session, in the orchestrator's memory only (`sessions.Manager.RegisterSecret`, the internal hook PROJ-57 calls; until then only tests do). No REST or MCP call registers one: an agent knows what it typed itself, which is out of scope. Nothing writes the values to the log, the database or a file, error paths included. The set goes when the session ends (stopped or failed), so a stop and a start begin with none. Since a browser reopens its tabs as it starts (§3, `RestoreOnStartup`), a tab could then show the value again with nothing left to hide it, so when the profile's last browser to run (its latest earlier session with a container) had a secret typed into it (`had_fills`, below), the next start removes Chromium's record of the tabs before the container starts: the `Default/Sessions` folder of the profile's Chromium folder (and the `Current`/`Last` `Session`/`Tabs` files of Chromium before 100), through `os.Root`, with one line in the log. That start opens no earlier tab; the cookies, session-only ones included, and the rest of the profile are kept (`TestTabsWithASecretArentReopened`). If they can't be removed, the start fails. The set stays through a handoff or a person taking control, since the page may still show the value then and hiding it costs nothing. Decided 2026-11-15, against clearing it when the lease generation changes: that would show the value again in a tab's URL after any handoff. **Orchestrator restarts:** the values go with the orchestrator, while the browser may run on and still show them, so the first secret also marks the session in the database (`had_fills`; only that it had one, never a value), and the mark is stored before the call returns (if it can't be, the call fails and the value isn't typed). When the orchestrator picks up a running browser so marked, it stops it the usual way, logins kept, with a warning in the log, instead of answering for it unscrubbed; the next start begins with none.
  - **What is hidden:** each secret of at least 4 characters, also once normalized as below (shorter ones would hide ordinary text, so PROJ-57's UI should warn about them), exactly (no fuzzy or partial matches), in these forms: as typed; JSON-escaped once and twice, with and without `\/`, HTML-safe as Go writes it (`\u0026`) and ASCII-only (`\u00e9`, as Python and the `X-Downloads` header write it), with lowercase or uppercase hex (`\u00E9`, as Jackson and .NET write it); `encodeURIComponent`, `application/x-www-form-urlencoded` (`+` for a space), Go's and RFC 3986's percent-encodings, and what a browser itself escapes when a page puts the raw value in a URL's query, path or fragment, each with uppercase or lowercase hex (`%2F`, `%2f`) and each encoded a second time (`%252F`, a URL carried in another URL's query). Text is matched in a normalized shape, so every mix of these is hidden too: an HTML character reference stands for its character (named, `&amp;` `&lt;` `&gt;` `&quot;` `&apos;` `&nbsp;`, or numeric, `&#47;` `&#x2F;` `&#x2f;`, as encoders mix them: mustache, Go's `html/template`, .NET); a backslash before ASCII punctuation stands for the punctuation (page_content's Markdown escapes, `\_` `\*` `\[` `\#` `1\.`, and JSON's and JavaScript's `\"` `\\` `\'`); and a run of whitespace, no-break spaces included, is one space (as Markdown and the reader view collapse it). The match maps back to the bytes it stands for, so what is replaced is the escaped text itself, and a text with no secret comes back as it was. Where matches overlap (one secret inside another, or two touching) their union becomes one `<hidden>`, so no part of either is left. Tests run real secrets through page_content's own renderers before scrubbing.
  - **Where:** the last step before anything leaves, after fencing has built the final text. Every agent API route is built by one wrapper (`API.agent`), which holds a text answer back and writes it scrubbed: a JSON answer string by string (keys too; the rest byte for byte, so a quote in a secret can't break the document), any other text whole, and every header (`X-Downloads`). A test lists the registered routes and fails on one that isn't built by it, with a test of that test. The MCP server scrubs every tool result again in its middleware, after the tool has turned the API's answer into its text, so nothing a tool decodes or joins can bring a value back; a test calls every listed tool over an API that leaks the secret, and shows each is caught without the scrub. That covers snapshots and diffs, find, act's results and changes, wait_for, tabs' titles and URLs, navigate (with Redirected from and the address that failed), page_content's Markdown and main text, error messages, handoff answers (the origin), the downloaded file names of `list_files` and download notices, and the session's crash output. The activity log is scrubbed as each entry is written, again when the live log is read, and the run's whole log once more as it ends, before its secrets are forgotten (§9 Agent log); a session's kept last log line too. So is the orchestrator's own log line for a page tool's or content call's internal error, which may quote the page.
  - **Scope:** the secrets used are those of the live sessions of the profiles the token may see, as they are when the call comes in and when it is answered (a value filled during the call counts). An agent is never told that a value is another profile's secret.
  - **Not scrubbed:** screenshots, PDFs and a downloaded file's bytes (`GET /api/profiles/{name}/files/{file}`, its name in the `Content-Disposition` header is): they are the page itself, which no text replacement can reach, so a screenshot taken while a page shows the value shows it. Nor is raw CDP (`/cdp/{profile}`): it is full control of the browser and can read any field's value anyway (see Security). Scrubbing costs one pass over the answer whatever the number of secrets (Aho-Corasick over all their forms, built once per change of the set): under 15 ms for 2 MB and 10 secrets; nothing when a session has none.
  - **An oracle for weak secrets:** hiding a value tells whoever reads the answer which text was the secret. An agent (or a page) that can make the page echo text it chooses, by typing candidates into a field the page shows back or putting them in a URL, can test guesses one by one and see which comes back `<hidden>`. Against a long random password that is useless; against a short or numeric one (a 4-digit PIN, a 6-digit code) it recovers the value in at most a few thousand tries. Inherent to scrubbing, so it isn't fixed here. For PROJ-57: refuse, or at least warn about, vault fills of short or all-numeric values (and of anything under `scrub.MinRunes`, which isn't hidden at all), and say in its UI that such values are guessable by an agent this way.
- **Visual-mode actions:**
  - Each action can return a screenshot after it.
  - `click`, `type_text`, `press_keys`, `open_url`, `scroll` and `drag` take `pace` (`human`, the default, or `instant`), as do act's steps; see Pace in §8. Human-paced typing through MCP takes at most 150 characters a call (`type_text`, or act's type steps together; `open_url` types its URL at once at either pace, so it takes 2,000), against the REST API's 500, and the tool descriptions say it takes about 0.25 s a character.
  - Screenshots are downscaled server-side to fit 1280×720 (1440×900 becomes 1152×720). Tools take coordinates in the screenshot's pixels, and BrowserPier scales them to the screen. The page tools' Cloudflare note gives its point in these pixels too, through the same function (`internal/screenshot`), and `click` works on an API-mode session as well.
  - `zoom` returns a region at full resolution.
  - Responses are kept short: one line of text, plus the image where there is one, the download notice when `click` or `press_keys` downloaded something (see Download notices), and the chooser notice while a file chooser is open (see Files).

### Settings and what they decide

- **Defaults for new profiles** (handoff policy, auto-stop, proxy, Block ads and trackers) are set in Settings and apply to every new profile, including ones an agent creates. An agent can still only raise the policy from the default, and can't turn blocking off for good.
- **A default proxy with `{sticky}`** (see §3) gives every new profile the same template and a token of its own, so each keeps its own exit. Changing the default doesn't touch existing profiles; one gets `{sticky}` by editing its own proxy.
- **Test proxy:** next to the proxy field in New profile, Edit profile and Settings (the default proxy), off while the field is empty. It tests what the field holds, or the stored proxy while the field still shows it masked, after the checks a save makes, and shows the result under the field without saving anything (except a profile's first `{sticky}` code, given on Edit as a start would); editing the field clears it. One test runs at a time for the whole instance, and at most 6 a minute. It is the admin's only: agents can't set a proxy, so they can't test one either (no API route, no MCP tool). The log says that a test ran, for which profile (or Settings), and how it went, never the proxy or the exit IP.
- **New exit IP:** in a profile's ⋯ menu when its proxy holds `{sticky}`, after a confirmation saying that sites may ask its accounts to sign in or verify again and that the country may change. It replaces the profile's token, for the admin only, and is disabled while the browser runs ("Stop the browser first"), since the forwarder keeps its credentials for the whole run. The stored location is left alone: at the next start the usual rule applies (same country keeps the time zone, a new one brings a new time zone and language).
- **Ad and tracker blocking** is a box under a profile's Advanced settings; the profile page says how many connections the running browser blocked, or that blocking is off for this session.
- **Memory limit:** `BROWSERPIER_RAM_LIMIT_PERCENT` wins when it is set, as `BROWSERPIER_ADMIN_PASSWORD` does; otherwise the limit is set in Settings (10–100%, default 70%) and applies at once to the next start.
- **Changing the PIN** needs the current one; changing the password needs the current one and signs out other devices. Wrong tries are limited.
- **Two-step sign-in** (Admin account): Off, or On since a date with the recovery codes left, and a warning at two or fewer. Turning on asks the password, then shows a QR code (drawn inline as SVG, never from a URL) with the key as text and the account label (`BrowserPier:<host>`, the host from `BROWSERPIER_PUBLIC_URL` or the page's), and asks for one code; the new secret lives in memory only, for this browser's session and 10 minutes, until then. The recovery codes are shown once, in that response. Manage turns it off, replaces the app or makes new recovery codes, each with the password and a code. Changing the password doesn't ask for a code and leaves two-step on.
- **Handing back from the app:** when an agent asked for help, the profile page shows the request with **Done, hand back** and **Can't do this** and a note, like the phone page; either answers the agent at once.
- **Notifications** (PROJ-157): one webhook URL, an address for links (used when `BROWSERPIER_PUBLIC_URL` isn't set), a box per event (handoff asked for, expired, cancelled by five wrong PINs: on; browser failed: off), Save, Send test, Regenerate secret and Remove. The secret is shown once, on the first save and on Regenerate; changing the URL keeps it. Admin only: no agent route or MCP tool reads or sets any of it, and no environment variable does. Details in deploy/README.md.
- **Agent log** (PROJ-158): each browser run (a session) has a log of what happened in it, for the admin. Each entry has a kind:
  - **action:** what an agent's call did (attached, clicked, typed N characters, took a screenshot, asked for help, downloads and uploads, connected over CDP). Each also records the token, route and call id that wrote it, which the page doesn't show: an agent reads its own token's recent actions (`recent_calls`, §8 Retries), never another's, and nothing else of the log.
  - **session:** "Started from the app", and how the run ended, from a closed set, in fixed words: stopped by the agent (named), from the app, idle for the profile's auto-stop, to make room for another browser (§13 RAM limit), started by an older BrowserPier, BrowserPier restarted while it held filled secrets, didn't answer as BrowserPier restarted (so a person's last takeover couldn't be fenced, §3 Control), with BrowserPier (`StopAll`, or a start its shutdown cut short), or just "Stopped" for a stop the BrowserPier before a restart had begun, whose reason went with it; or failed: the browser exited unexpectedly, didn't close cleanly (recent logins may be lost), lost track of its container, didn't start (these four are also the webhook's `browser.failed` categories). They never quote the container's output, the session's error or the crash reason, which a page can influence; the profile page shows those for the last session.
  - **control:** a person took control (from the live view, or through the handoff link) and handed it back, written only when it really changes hands; and, while they hold it, that they set the browser's clipboard or pasted from the clipboard box (§11, never the text or its length), or answered a page's file chooser (how many files they chose, or that they cancelled it; never the names).
  - **handoff:** the link was opened (once per handoff), handed back done or can't, expired, reached its `until_url`, and why it was cancelled: withdrawn by the agent, five wrong PINs, or the browser stopped. Never the agent's detail, the person's note, an address, the PIN or the link.
  - **watch:** when someone starts watching (no viewer before) and when nobody is any more; a live view that comes back within 30 seconds takes the second back. Never who: no IP address, user agent or account. Profile-card previews count as nothing.
  - **page:** the active tab's title, when it differs from the last one noted: page text, for the admin only. It comes only from what the page tools already read for their answer (snapshot, navigate, tabs, page content, act's snapshot): no new call into the page, no polling, so an agent that uses only screenshots, `/computer` or raw CDP leaves none. It is noted only while no person has control and no handoff is open (page tools are refused then), in a field of its own, never in an entry's words; control, C1 and bidi characters are removed and whitespace collapsed; over 512 bytes it isn't kept (the entry says only "The page changed"); it is scrubbed (filled secrets, §8), then cut to 80 characters; a title right after another replaces it, so titles can't push actions out. After a hand-back, the first title the agent reads can show what the person did (a search in a title); PROJ-155 will hide what a person typed.
  - **Kept runs:** when a run ends, its log is kept for its profile: the last 5 runs, each for 24 hours after it ended, whichever is less (checked when a run is added or read; no timer); a failed start replaces a failed start that is the newest run, so a retry loop can't push out useful runs. One run, live or kept, keeps its newest 500 entries and 64 KiB (of text, with a fixed overhead per entry); one entry's words are stored whole up to 2 KiB (a longer entry, such as a long list of file names, is stored as "An entry too long to keep (over 2 KiB)", so a secret registered later can't be cut across its end), and shown, in the web UI and to an agent's `recent_calls`, and kept, cut to 400 characters after they are scrubbed with the secrets as they are then, so a secret registered later still matches whole; a kept run is the newest of its scrubbed entries that fit in 64 KiB, how it ended among them, since a scrub can make an entry longer; all kept runs together, 8 MiB, the oldest run dropped first. A kept run holds its session, mode, start and end, how it ended, who started it, and its entries. Deleting a profile drops its runs; export and import leave them out.
  - **Memory only:** nothing of the log goes to the database, a file or the orchestrator's log; a restart or an update forgets it all (§3). Entries are scrubbed of filled secrets as they are written, again when read, and the run's whole log once more as it ends, with the session's final secrets, before they are forgotten.
  - **Where it shows:** the live view's side column has the current run's newest 50 entries, polled; while the browser is stopped, how and when its last run ended ("Last run ended 14:02. Stopped: idle for 30 min."), with a link. `/profiles/{name}/log` (admin only, not polled, `no-store`) has the current run whole and Previous runs, newest first, each with when, how it ended, who started it and its entry count, opening to its entries. Every entry is text escaped by the template, the title too. No REST or MCP route reads a kept run, and a stopped session's `recent_calls` stays empty.
- **Appearance:** light or dark, following the device's own setting unless it chooses System, Light or Dark in Settings. The choice is per device, kept in a cookie, so a phone and a desktop can differ; the sign-in and handoff pages follow it too. Real websites (previews, the live view) keep their own colours, slightly dimmed in dark except while you drive them.
- **Recordings** (PROJ-23): Record sessions is a box in a profile's settings, and applies at once, to a running browser too. The profile page shows **Recording** or **Recording paused** beside the status while the browser runs, and a **Recordings** cell: one row per session with a recording (when it started, how long was recorded, its size), each opening the player, and Delete all; the live view's hint adds that nothing is recorded while you have control, in full screen too, where the pill isn't shown, and follows the setting as it changes (the admin's live status carries it).
  - **The player** (`/profiles/{name}/recordings/{session}`) plays the segments in order in one `<video>`, with play and pause, speed (1×, 2×, 4×, 8×), seek on a timeline of wall-clock time that hatches the gaps and names their reason on hover, and Skip gaps (on by default; off, a gap is waited through at the speed chosen, saying why: "A person had control. Nothing was recorded from 14:04:31 to 14:05:10."). Vanilla JS, no build step. It can delete the recording.
  - **From the agent log:** while the session runs, each log entry the recording covers links to its moment in the player (`?t=`, wall-clock milliseconds), on the profile page and in the current run of its log page. A kept run's entries (Agent log above) don't link yet, so after a stop the player stands alone; the index keeps wall-clock times, so PROJ-188 can line them up without changing it.
  - **Admin only:** the player, the segments and the deletes answer only the signed-in admin: a segment answers 404 to anyone else, the others 401 to a request with an agent's token. A segment is served as `video/mp4` with `nosniff`, `Cache-Control: no-store` and Range support, never with an attachment name, from ids checked against BrowserPier's own forms and opened through `os.Root`.
  - **Settings:** Keep recordings for 1 to 90 days (default 7), and Space for all recordings (default 2048 MB, at least 64; the indexes count). Recordings always leave 1 GiB free on the data dir's disk. When either limit is reached, the profile holding the most gives up its oldest segment first, until there is room, among profiles with a whole segment to give (one whose bytes are all in a segment being written gives nothing). Recordings give way only when that can make the room: when the disk is short because of other data, which removing every recording wouldn't fix, none is removed, the write is refused and a warning says so once. A segment that has no room isn't written, the index says `lost`, the profile page shows **Recording paused** with "Nothing is kept for now", and the session goes on. Older segments are removed by an hourly sweep, at start, and when the retention is shortened; a lower space limit applies when saved.
  - **Deleting** a running session's recording also drops the segment being written; what the session records afterwards is a new recording.
- **Previews:** profile cards show a small screenshot of each running browser. Taking one doesn't count as use, so an open page never keeps a browser from stopping when idle.

### Profile icons

- **Source, in order:** the main site's favicon from the profile's own favicon cache; else the fallback icon and colour chosen in New profile or Edit settings; else a glyph and colour picked from a hash of the profile's name, so it stays the same.
- **Main site:** the one set (`Site`), or, while none is set, the registrable domain (per the Public Suffix List) visited most in the browser's history (`SiteInferred`), recorded at each graceful stop. The inferred one never replaces the one set. A favicon counts for the site when its page is on the site's host or a subdomain of it.
- **Reading:** only after the browser has closed cleanly, at each graceful stop (and when the main site is changed while it's stopped), never while Chromium holds the databases, and never from the network. `chrome/Default/Favicons` and `History` are browser-written, so they're read as hostile: through `os.Root`, as private copies of the main file only (a `-journal` or `-wal` the browser left is ignored, never replayed), opened read-only and immutable, tables checked to be tables, with caps on size (32 and 64 MiB), rows and time (10 s). A failure leaves the cached icon as it was and never fails the stop.
- **The image:** the largest bitmap up to 64 px, else the smallest above, from the icon of most of the site's pages. A PNG, or an ICO holding PNG or 24/32-bit BMP images, of at most 256 KB and 256×256, is decoded and drawn again as a 64×64 PNG; nothing else of the file is kept, and SVG is never taken. It's cached as `profiles/<name>/icon.png`, beside `chrome/`, where the browser can't write.
- **Serving:** `GET /profiles/{name}/icon`, to the admin session only (agent tokens can't), as `image/png` with `nosniff`, `Cache-Control: private, max-age=3600` and an ETag; pages link it with its version.
- **Fallback choices:** glyphs envelope, briefcase, code, document, chat, cart, globe, bank, calendar, cloud, chart, key; colours blue, sky, violet, indigo, teal, cyan, slate. Never orange (a person is needed) or red (failure).

### Export and import

- **Export:** a stopped profile can be exported from Profiles' ⋯ menu, by the admin only (never through the agent API or MCP: an archive is live cookies).
  - **Format:** a gzipped tar encrypted with age and a passphrase of at least 10 characters (`age -d` opens it too). It starts with `manifest.json`: the format version, the BrowserPier version and the profile's settings, main site and fallback icon included, and its cached icon. On import the icon is drawn again like one read from the browser, and one that doesn't pass is dropped; an icon choice this version doesn't know falls back to the default instead of failing the import.
  - **Contents:** the profile's `chrome/` and `files/` (never its recordings, which live elsewhere), without `run/` (the control socket, and briefly proxy credentials), Chromium's caches and locks, or the mount markers. Only regular files and folders are read, through `os.Root`.
  - **The proxy:** it comes with the archive, password included, since the archive is a secret anyway. So does local network access, and the `{sticky}` token, so the profile keeps its exit on another BrowserPier. An archive without a token (made before PROJ-153) gives the profile a new one when it needs it; importing the same archive twice gives two profiles the same token, which is intended: they are the same accounts.
  - **Streaming:** the archive is streamed as it's made, with no temporary file. If anything fails midway, the download is cut off, and an age archive cut short doesn't decrypt.
- **Import:** from Profiles. The archive becomes a new profile under its own name or one you give.
  - **Streaming:** the upload is streamed, never stored whole. It's extracted into a folder of its own, then the profile is created and the folder moved into place last.
  - **What's accepted:** only regular files and folders under `chrome/` and `files/`, through `os.Root`, with caps on total size (8 GiB) and entries. The import stops before it would leave less than 512 MiB of disk free.
  - **Cost cap:** a crafted archive can't make the passphrase check cost more than age's default scrypt work factor (2^18).
- **While a profile is exported or imported** its browser can't start and the profile can't be deleted.

### Interaction rules

- Needs help is visible from anywhere in the UI: an orange status, sorted to the top, and a "N needs you" chip in the shared header.
- Red is reserved for destruction. Stop is neutral; Delete sits in the ⋯ menu and asks for confirmation, naming what will be erased.
- Stop warns when an agent is using the browser.
- Each profile has one main action in a fixed position (Take control, Live view, Start, Retry). Everything else is in the ⋯ menu.
- Take control is blue everywhere; hand back is neutral. Mono type only for things you copy.
- Browser controls are disabled while the agent drives. While the human drives, the keyboard goes to the browser and Esc releases it.
- "Stop browser" is the label everywhere. Copy actions confirm with "Copied".
- Nautical theme in the logo and a few touches of copy; functional labels stay plain.

## 10. Anti-bot approach

- Headful Chromium on a virtual display, with no automation flags.
- Visual mode sends real OS-level input through xdotool, not CDP input events. The CDP connection itself is detectable, so in Visual mode no CDP client stays attached to the page.
- **A pause after a shortcut** (PROJ-151, see §8) adds no event: the same keys are sent, the next ones only come at least 150 ms after a shortcut, as a person's do.
- **Opening an address with a click** (PROJ-164, `open`, see §8) is what a person does: the pointer goes to the address bar, clicks, and the address is typed. The page sees the pointer leave it and the focus go, then the new page loads with the focus, as after a person's Enter; it sees none of the keys. `TestVisualModeLooksLikeAPerson` opens its detector both ways and finds nothing either way.
- **Input that moves like a hand** (PROJ-113): behaviour scripts read the pointer's path and the keyboard's rhythm, not just where a click lands. At human pace (the default; see Pace in §8), in Visual mode and in act, the pointer glides along a bowed, slightly wobbling path at a Fitts's-law speed instead of jumping, aims with a person's scatter, pauses before pressing and holds buttons and keys, and typing has a typist's uneven gaps instead of xdotool's even 12 ms. It's behaviour, not fingerprint spoofing: the browser says nothing different about itself. `TestVisualInputLooksHuman` and `TestActInputLooksHuman` check what a page's own script records (at least 10 moves on a 400 px click, off a straight line; a 60–200 ms hold; scattered landings; key-down gaps with a mean of 0.12–0.45 s and a coefficient of variation over 0.25). Typing mistakes and corrections are out of scope.
- Residential IP: a home server's own connection by default, with an optional per-profile proxy. On a VPS, a residential proxy is close to required for protected sites.
- A desktop like a person's: a window manager whose taskbar reserves the bottom of the screen, so `screen.availHeight` is less than `screen.height`, as it is with a panel and unlike headless (PROJ-29).
- Timezone and locale always match the exit IP. Chromium's interface languages are installed, so `Intl` agrees with `navigator.languages`.
- WebRTC sends no UDP, so it can't leak the host IP behind a proxy.
- No fingerprint spoofing: each profile keeps one real, consistent fingerprint over time.
- Persistent, aged profiles with real logins help on their own.
- **Back/forward cache off** (PROJ-160, for memory, §3): a page that Back returns to is loaded again, so it sees `pageshow` with `persisted` false and a `back_forward` navigation, as a page the cache didn't keep does in any browser, and nothing is spoofed. One thing differs, for every page: Chrome with the cache on gives a page it didn't restore a `notRestoredReasons` object (`masked` reasons, measured with an `unload` handler), and with the cache off it's always `null`, so any page that reads it after a Back can tell the cache is off. `images/chromium/ANTI-BOT.md` lists it under the signals that remain; accepted for the memory.
- **Validation** (PROJ-15): `images/chromium/ANTI-BOT.md` has the results against public detection pages, and the signals that remain (software WebGL on llvmpipe, which says so though it isn't SwiftShader, and a 0×0 window as a page's first script often sees it, which a window manager didn't change; its cause is being checked in PROJ-65). `TestVisualModeLooksLikeAPerson` checks Visual mode in CI's Docker tests.
- **Page content** (PROJ-20): Markdown and the main text read only a DOM snapshot, the screenshot comes from the X display, and 20 runs of each against the same detector showed nothing. A PDF is a print: the page sees `beforeprint` and the print media query, as when a person presses ctrl+P, and nothing else. That is recorded in `images/chromium/ANTI-BOT.md` and accepted, since printing is something people do; an agent on a site that watches for it uses Markdown instead.
- **Cloudflare challenges** (PROJ-120, for PROJ-25): the page tools notice a challenge page from the isolated world (a `querySelector` and a box) and tell the agent where its checkbox is on the screen, for a real click through xdotool (`/computer`, at either pace) or a handoff. That click is OS input like a person's; nothing clicks over CDP, BrowserPier never clicks by itself, and nothing about the browser changes. A named profile keeps Cloudflare's clearance cookie, so the pass lasts.
- **Visual mode's element tree** (PROJ-150): read over the session bus (Chromium's accessibility, Visual mode only), with no CDP, so nothing attaches to the page; the reader only reads (no AT-SPI action, focus or scroll), and `TestVisualSnapshotStaysQuiet` saw nothing in 20 snapshots and 20 clicks by ref while catching its positive control. What a page can notice is accessibility being on, which is fixed for a session: no web API reports it, but a page that inserts thousands of elements at once spends longer in long tasks (about 2.5 times, with Chromium's `basic` mode; five times with the full one, which is why it isn't used), which a script could time against its own baseline. Measurements in `images/chromium/ANTI-BOT.md`.
- **File choosers without a dialog** (PROJ-152): the portal answers Chromium over D-Bus, with no CDP, in both modes; the files arrive with the trusted `input` and `change` events a person's pick gives, and the X focus leaves the browser's window while the chooser waits, as a dialog takes it. 20 rounds against the continuous detector showed nothing; the measurements are in `images/chromium/ANTI-BOT.md`.
- **BrowserPier's own CDP use** (the API-mode page tools, PROJ-21): one connection per call, no domain ever enabled, scripts only in an isolated world, nothing written into the page. `TestPageToolsStayQuiet` runs each tool 20 times against a continuous detector (`browsertest.Watch`, on the page's main thread and in a worker), which must catch its positive control, a client doing what Playwright does; the tools showed nothing, but for act's `upload`: its files arrive with trusted `input` and `change` events but no click before them (a person clicks to open the chooser, or drops the files), which the detector sees and which is accepted. The measurements and the residuals (such as `fill` putting its text in at once) are in `images/chromium/ANTI-BOT.md`. Visual mode doesn't use them.

## 11. Security

- Private by default: behind Tailscale or a VPN is the recommended setup. Public instances must use HTTPS.
- The orchestrator holds the Docker socket, which is powerful. Keep it minimal, and only ever start containers from BrowserPier's own browser image. It starts three kinds, all from that image: browsers; the sandbox check (`sandbox-check`, no network, no mounts) that picks the AppArmor profile; and the proxy test (`proxy-check`, PROJ-154), with a browser's security options and network, no ports, no added capability, one mount (its own folder, holding the proxy file), 128 MiB and 64 processes, removed when the test ends and at start-up. Neither check is labelled as a browser, so reconciling never takes one for a browser. Every create goes through one guard (`internal/docker/guard.go`, PROJ-159) that checks the whole body, right before Docker sees it, against a fixed envelope per kind of container (a browser, the sandbox check, the proxy test): the image, user, labels, environment names, capabilities, security options, mounts, network, user namespace, shared memory and limits must be exactly BrowserPier's, and every other field unset. It catches BrowserPier's own mistakes, in today's code and in later changes; it runs in the orchestrator's process, so it is no defence against an orchestrator that is itself compromised, which holds the socket anyway.
- Raw CDP has no authentication, so it is never exposed directly; it goes through the token-checked proxy.
- CDP access is equivalent to full control of every logged-in account in that profile. Docs say so plainly, and tokens are scoped per profile. It is also why raw CDP isn't scrubbed of filled secrets: a CDP client can read a field's value directly.
- Secrets BrowserPier fills itself (PROJ-57's vault fills) are kept per session in memory only, never logged or stored, and replaced by `<hidden>` in every encoding in every REST answer, MCP tool result and activity log entry (Filled secrets, §8; PROJ-125, see also PROJ-60 and PROJ-61). Screenshots and PDFs can't be scrubbed: they show the page as it is, the value included if the page shows it. A browser that outlives an orchestrator restart with secrets typed into it is stopped when picked up (only that it had one is stored).
- **The live view's clipboard** (PROJ-194): the browser's clipboard (X's CLIPBOARD selection, through `xclip`, no CDP) is read only when the person with control opens the clipboard box (unless it holds text they haven't sent) or presses its Refresh, never polled or synced, and reaches their own clipboard only when they press Copy, so a page can't put text there on its own (a command to paste in a terminal, say). Text they send stays on the browser's clipboard for the rest of the takeover, until they send other text or the page copies something. However their control ends (Hand back, the handoff's Done, Can't do this, expiry or cancel, the live view closing, reloading or losing its connection, BrowserPier restarting), both X selections are emptied: CLIPBOARD (what Ctrl+V pastes) and PRIMARY (what is selected in the page, which a middle-click pastes, and agents have a middle button), whoever holds them, Chromium included. Each is taken by an `xclip` offering no text, seen to own the selection before it ends and leaves it with no owner, so a later paste of either pastes nothing. That happens a tenth of a second after the person's last input has reached the browser, so a copy they had just pressed is emptied too, and only then do agents get the browser back, and recording, if the profile records, may resume (§3, Recording); if emptying fails, that is logged, by status code or kind of failure alone (never the container's words, which could carry the text), and the browser is handed back all the same. Only the end of a person's own takeover does this (PROJ-196): once it has ended some other way than through their live view (a handoff ending, Hand back used from another tab), that live view only learns it has no control, and nothing it sends afterwards (input, a lift of held keys, a clipboard read or set, a take, a hand-back, closing) reaches the browser, ends whoever's control came since or empties their clipboard; a take from it is a take afresh. Input refused because the browser is stopping, a blur included, ends that viewer's control too, so a stop that fails never leaves the browser under a control no one holds; and a handoff that ends while its browser is stopping leaves it Running, not Needs help, should the stop fail. None of this outlives the session: what was admitted for one browser is waited for, and broken off, before the profile's next browser can start on the same control socket. Agents have no clipboard endpoint. The text is never logged anywhere, nor its length (the agent log says only "Clipboard set" or "Pasted from the clipboard box": a length would tell agents a password's), and it isn't scrubbed of filled secrets: it goes to the person, not an agent.
- The activity log (§9 Agent log) is the admin's: what agents did, how runs ended, control, watching and handoffs, in BrowserPier's own fixed words, and tab titles, which are page text shown to the admin (escaped, scrubbed, cut to 80 characters). It never holds typed text or what was sent through the clipboard, a handoff's detail or note, a page's full address, a PIN, the container's output or who watched. Two things in it can still say where the browser went or what a person did, and now survive a stop for up to 24 hours: an `Opened …` entry (navigate, a new tab) names the origin (scheme and host, never a path or a query; an address without a host, such as `about:blank` or a `data:` URL, as given, cut short); and a tab's title is page text, so the first one read after a hand-back can show what the person did there (a search in a title) until PROJ-155. It is in memory only, kept up to 24 hours after a run, and no agent reads it beyond its own token's actions on a live session.
- Tokens, the PIN and the admin password are hashed at rest. So are the two-step recovery codes. The exceptions are stored as they are, because the server must use them (§6): the webhook's secret and URL, like `device_key` and proxy passwords, and the two-step authenticator secret, from which it computes codes. None is ever logged, and the authenticator secret is never shown after it was confirmed.
- **The webhook** (PROJ-157) may point at `https://`, or at plain `http://` only when every address its host resolves to is private (loopback, RFC 1918, `fc00::/7`, `100.64.0.0/10`); never link-local (a VPS's metadata endpoint), multicast, broadcast or unspecified. The rules are checked again on the address dialled for each POST, not only when saved; it goes direct, never through `HTTP_PROXY`, a profile's proxy or a browser, and follows no redirect. Its body holds nothing a page or an agent wrote except the page's `origin` (scheme and host, a field only, never in the sentence a chat shows): fixed words, the profile's name, the typed reason, policy or failure category, times, ids and the token's name. Its links are built on `BROWSERPIER_PUBLIC_URL` or the admin's address for links, never on the request's Host, which an agent chooses.
- Agent tokens are never taken in a URL. Clients that can't set headers connect to CDP with a single-use ticket that lasts a minute.
- Treat profile folders as secrets, since they hold live session cookies. With `password-store=basic`, cookies on disk are effectively readable.
- **Recordings** (PROJ-23) hold the screen as the display showed it while agents acted: what a screenshot would show, balances, mail, a one-time code in a visible field, what an agent typed in a plain field. They can't be scrubbed (as screenshots can't; PROJ-125, PROJ-155). Never a person's control: Take control and a handoff stop the recorder before the person's input can reach the page (§3, Recording). Only the signed-in admin plays, lists or deletes them; agents can't read, list or turn them off. They are **not encrypted separately**: they get the data dir's protection, as profile folders do, since the admin password sits on the same disk on Umbrel and with `BROWSERPIER_ADMIN_PASSWORD`, so a key it wraps would protect little. Residuals: after hand-back the first frame shows the screen as the person left it, with whatever is still on it; a page's changes more than 30 s after the agent's last action aren't recorded; with raw CDP an agent can make the screen show anything, so a recording is what the display showed, not proof of what the agent did; and recording costs CPU and memory in each recorded browser while an agent works.
- Page text returned to agents is fenced and sanitised (see MCP tools), since agents browse untrusted pages. The page tools' snapshots leave out what is AX-ignored, `display:none`, `visibility:hidden` or zero-size, but keep text a person may not see (transparent, off-screen, clipped or the page's own colour) and accessible names (`aria-label`, `aria-labelledby` even to a hidden node, `alt`, `title`, placeholder): that text is contained, not filtered. On a page too large for the accessibility tree, `find` reads the DOM snapshot's laid-out text alone, which includes `aria-hidden` text (contained the same way). It is fenced and capped like the rest, and the tool descriptions say so. So is the browser container's own output: a session's `last_log`, and Chromium's crash reason after its `error`, since a compromised page can write to it. The UI shows the reason unfenced. The page as Markdown or main text (Page content) follows the same rule, without the AX tree, so `aria-hidden` text a person sees stays; a PDF or a screenshot is the page itself, which no fence can wrap, and a PDF's MCP result says it comes from a web page.
- Visual mode's accessibility tree (PROJ-150) goes over the session bus below: a path socket in a 0700 folder of the browser's uid inside the container, with EXTERNAL authentication: no TCP, no abstract socket, nothing in the folder shared with the orchestrator, and Chromium's renderers (seccomp-filtered and chrooted into an empty folder) can't reach it. The tree reader on it only reads, from one allow-list; the orchestrator reaches it only through the control socket.
- Pages can't reach the local network, the Docker host or a VPS's metadata endpoint through the browser, unless the admin allows a profile the local network (see Egress).
- A file chooser can only be answered with files from the profile's `files/uploads`, checked by the orchestrator and again by the browser container (Files, §8): Chromium's GTK dialog let whoever drove it send a page any file the browser could read, its profile's cookies included. The portal is in every browser, and a browser whose portal can't start doesn't start, so no GTK dialog is left to fall back to (PROJ-183). The residual is a browser started on an image from before the portal: it keeps Chromium's dialog, and the hole, until it restarts (its `GET /chooser` answers 404, so the modal and the agent's routes treat it as having no portal). The browser definition went to 7 with the portal, so the first start of the version that brings it stops the browsers an older BrowserPier started (logins kept) instead of picking them up; only a browser image pinned to an older version (`BROWSERPIER_BROWSER_IMAGE`) would keep the dialog. Restart browsers after updating if in doubt. A person's upload from their device goes through the same name rules and caps as an agent's, and a handoff link reaches only its own browser and profile. The session bus is a local socket in a 0700 folder, for the browser's uid only, which Chromium's sandboxed renderers can't reach; on it only the portal's name can be owned.

## 12. Deployment and packaging

- **Generic (primary):** `deploy/docker-compose.yml` and `deploy/README.md` (the install guide for a fresh VPS).
  - **The orchestrator container:** runs as the installing user (`PUID`/`PGID`) with the Docker socket's group added, and `./data` bind-mounted (its host path is detected).
  - **Ports:** the app listens on 127.0.0.1:7437 unless `BROWSERPIER_BIND` says otherwise (a Tailscale address, say). Live views use 7438 UDP and TCP.
  - **HTTPS:** the `https` profile adds Caddy for automatic HTTPS, from the shipped `Caddyfile`: no access log, and `?ticket=` and `?token=` redacted from its error log. The guide also covers an existing reverse proxy (WebSockets, long timeouts, no query strings in any log).
  - **Trusted proxies:** the compose network has a fixed subnet (`BROWSERPIER_NET`) with fixed addresses, and only Caddy's is trusted for `X-Forwarded-*`. A proxy on the host is trusted by setting the network's gateway instead.
  - **Image:** `BROWSERPIER_VERSION` defaults to `latest` in the repository, and to the release itself in the files attached to a GitHub release, which is where the install guide downloads them from. `edge` follows `main`.
  - **Releases:** a `v*` tag publishes both images (`0.1.0`, `0.1` and `latest`), then CI makes the GitHub release with the pinned install files and the version's `CHANGELOG.md` section. `RELEASING.md` has the steps.
  - **Configuration:** through environment variables, where an empty value counts as unset. Without `BROWSERPIER_ADMIN_PASSWORD`, the first-run setup page asks for the code printed in the log.
  - **AppArmor:** a one-shot `apparmor` service, behind `--profile apparmor` for Debian 13 and later, loads and installs BrowserPier's AppArmor profile where Docker's may refuse Chromium's sandbox (AppArmor 4 with Docker 29.1 or earlier). BrowserPier waits for it but starts whatever its outcome (see §3, Sandbox).
- **WebRTC on a server:** advertise the public IP (or the Tailscale IP), open one UDP port with a TCP fallback.
  - **TURN:** the `turn` profile adds coturn on the compose network, publishing 3478 UDP and TCP. It takes TURN REST API credentials from `BROWSERPIER_TURN_SECRET` and relays only to BrowserPier's address on that network, over UDP only: every other peer is denied (the host, the LAN, other containers, the internet), so it is no open relay, and its relay ports stay unpublished. An allowed address covers all its ports, so refusing TCP relays (`no-tcp-relay`) is what keeps the web app out of reach. Each viewer may hold 40 relays, 300 in all: generous, since a page takes one per TURN URL and network interface, and a UDP relay a page left without releasing counts until it times out. Its settings go to a file, not its command line, so the secret doesn't show in the host's process list. It runs with no capabilities but `NET_BIND_SERVICE` (its binary carries it as a file capability and won't start without it), no-new-privileges and a read-only root, and answers no unauthenticated STUN (`no-stun`).
  - **TLS on 443 isn't bundled:** Caddy holds 443. TURN over TCP on 3478 covers networks that only block UDP; for those that allow only HTTPS, the guide points to a TURN server elsewhere (`turns:` on 443), set with the same variables.
- **Umbrel:** `yakitori-browserpier` in the author's community app store (`Oni-giri/yakitoris-app-store`); the source is `umbrel/yakitori-browserpier/`.
  - **Sign-in:** the app password (`deterministicPassword`) is the admin password. Umbrel's login stays on for the UI; `/api`, `/cdp`, `/mcp`, `/h` (handoff links) and `/static` are whitelisted, since agents and phones can't sign in to Umbrel and BrowserPier checks them itself.
  - **Ports:** Umbrel opens it on **7436** (7437 is taken by another app in Umbrel's store); BrowserPier still listens on 7437 inside. Live views publish 7438 UDP and TCP directly.
  - **No TURN:** an Umbrel is reached on the LAN or Tailscale, where live views connect directly, and a TURN server at home would need ports forwarded on the router.
  - **Live-view addresses:** `exports.sh` reads the host's own addresses (LAN and Tailscale, not Docker's bridges) when the app starts, since the container can't see them.
  - **Trusted proxies:** only the app network's gateway, which Umbrel's proxy (part of umbreld since umbrelOS 2.0) connects from. Other apps on that network can't forge `X-Forwarded-*`. The app therefore requires umbrelOS 2.0 (`manifestVersion: 2.0`); older versions, whose proxy was a container, refuse to install it.
  - **Stopping:** with `BROWSERPIER_STOP_BROWSERS_ON_EXIT=true`, BrowserPier stops its browsers on the way out, through the normal stop, once it accepts no more requests. So stopping, updating or uninstalling the app in Umbrel ends its sessions (logins are kept). This differs from the generic install, where browsers keep running through an update. A `post-stop` hook stops any browser left over.
  - **AppArmor:** a `pre-start` hook loads BrowserPier's AppArmor profile at every start of the app, after a reboot too (see §3, Sandbox). Umbrel's app update copies only the files it knows (`docker-compose.yml`, `umbrel-app.yml`, `exports.sh`, `hooks/`, `icon.svg`), not extra folders, so the hook carries the profile and its loader as heredocs, generated from `images/chromium/apparmor/` and kept identical by a test. It always exits 0, since Umbrel ignores a hook's exit status, and says in one line of umbreld's journal whether it loaded the profile, didn't need to, or couldn't, and why. A failed load leaves browsers under Docker's profile if the sandbox works there, otherwise unconfined, as BrowserPier's log says.
  - The Docker socket mount keeps it out of Umbrel's official store, whose rules forbid it. Being in a community store, it isn't subject to that store's review of hooks either.
- Browser containers are started by the orchestrator, not listed in the compose file. (The `apparmor` service runs the browser image too, but only its profile loader.)
- App data holds the database, one folder per profile, and `recordings/<profile>/<session>/` (PROJ-23): segments and an index, mode 0700/0600, beside `profiles/`, never inside it (that tree is mounted into browser containers). The folder appears with the first segment. Deleting a profile deletes its recordings (moved aside first, as its folder is); Reconcile at start removes recordings of profiles that are gone and half-written segments. A backup of the data dir includes the recordings; leave `recordings/` out of it if you don't want them there. Export and import leave them out.
- The orchestrator listens on port **7437** by default ("PIER" on a phone keypad), set with `BROWSERPIER_LISTEN`. It avoids 8080 and other ports common among self-hosted apps. (On Umbrel, where app ports must be unique, it's opened on 7436: see above.)
- **Profile export and import:** from a profile's ⋯ menu, download it as a password-encrypted archive, and import one into a new profile. A profile must be stopped to export, so its files are consistent.

## 13. Decisions

| Question | Decision | Why |
|---|---|---|
| Live stream | WebRTC (pion), H.264 from the virtual display | Smooth, and no CDP attached to the page, so Visual mode stays hard to detect. |
| Orchestrator stack | Go, single binary, SQLite | Low idle RAM, native Docker SDK and pion. |
| Frontend | Go templates + htmx, small vanilla JS for WebRTC | No build step; everything ships in the one binary. |
| Notifications | One optional admin-set webhook, signed, told when a handoff is requested, expires or is cancelled by wrong PINs, and optionally when a browser fails; no agent text in it; the handoff link only for PIN and sign-in policies | Headless and scheduled agents have no channel to the person. Changed 2026-11-16 at the owner's request; was "None from BrowserPier" (PROJ-157). |
| Webhook contents | The typed reason, never the agent's `detail`; links on `BROWSERPIER_PUBLIC_URL` or the admin's address for links, never the request; one webhook and one JSON format (`text` and `content` for Slack and Discord), no templates; ntfy left out (it would need its own format) | The detail is free text from an agent that reads untrusted pages, and a channel would show it as BrowserPier's words. The request's Host is the agent's choice. |
| Webhook delivery | In memory, 4 POSTs under way (Send test included) and 64 waiting, 10 s each, the host's lookup included; network errors, timeouts and 5xx tried again after 2 s and 10 s; anything else final, 429 included (no `Retry-After`), redirects not followed; at most 6 `handoff.requested` per profile in 15 minutes; nothing kept or retried across a restart; `browser.failed` off by default; nothing for done, can't, `until_url`, withdrawn or a stopped browser | A dead or slow webhook must never hold up a handoff or a session, and an agent talked into a loop of handoffs must not flood a channel. A queue on disk would hold links. |
| RAM limit | Stop the longest-idle unused browser, else refuse; the same when the host is short of free memory, with no extra setting | Agents get a browser when possible and a clear error when not, instead of hanging in a queue. A host short because of other apps would otherwise swap, or have its OOM killer end another app or a browser mid-task. |
| Stop errors | A stop Docker reports as failed counts when the container has stopped, with a warning in the log | The browser closed the usual way, and its exit status still tells a clean close from a crash. Refusing answered 502 and could record the session as crashed, over a fault in the host's network teardown that only the host can fix. |
| Profile backups | Encrypted export and import in the UI | Losing the server shouldn't mean logging in everywhere again. |
| Deployment | Generic docker-compose first (any VPS), Umbrel app second | The author runs it on Umbrel, but it should work for anyone on a plain server. |
| Fingerprints | No spoofing; one stable real fingerprint per profile | Spoofing needs CDP on every page, and a changing fingerprint flags logged-in accounts. |
| Proxies | Per-profile, authenticated, via a forwarding proxy; timezone and locale matched | On a VPS, residential proxies are what makes protected sites usable. |
| Sticky proxy sessions | `{sticky}` in a proxy URL's user name or password becomes a random per-profile token (8 characters, `a-z0-9`), never the profile's name or the session id; the template is stored and shown, and filled in only when the browser starts; New exit IP, while stopped, is the only way to change it | A default proxy copied to every profile gave them all one exit IP with a sticky provider. The name would tell the provider what a profile is for (`bank`), and a session id changes at every start. Filling in at start keeps the token out of every place a proxy is shown. Decided 2026-11-17 (PROJ-153), revisitable: the name, both credentials allowed, the token's form, an imported profile keeping its token. |
| Testing a proxy | From a short-lived browser-image container on the browsers' network, running the entrypoint's own forwarder and lookup (`proxy-check`); the outcome is a fixed category, never the proxy's or the endpoint's words; the lookup endpoint is the one starts use, so no new third party learns anything; the result line is parsed strictly and nothing is stored | A test that passed where a start would fail (another network, another HTTP client) would be worse than none. The proxy's reason phrase is a third party's text, so the check reports kinds the forwarder's typed errors carry. Decided 2026-11-17 (PROJ-154), revisitable: the proxy handed over as a file rather than on standard input; no test with the lookup off; one test at a time and 6 a minute; 128 MiB; New profile and Settings test `{sticky}` with a throwaway token. |
| Page egress | Through the forwarder in the container, which refuses private and link-local addresses; a profile can be allowed the local network | The browser shouldn't be a way into the LAN, the host's other apps or a VPS's credentials. Kept in the container for now: `--network none` makes Chromium report itself offline. |
| CDP without headers | Single-use, one-minute tickets; the token is never taken in the URL | A proxy in front may log URLs, and a logged token would be good until revoked. `?token=` was removed before the first release rather than deprecated, as nothing depended on it. |
| Orchestrator ↔ browser container | A Unix socket in a per-profile folder shared with the orchestrator | Nothing listens on a network, so a page or another container can't reach CDP. |
| Profile storage | Bind-mounted folders in the data dir, not named Docker volumes | One directory to back up or move; export and downloads read files directly. The host path is detected from the orchestrator's own mounts. |
| License | Apache 2.0, not AGPL | Self-hosters are the users, and many companies forbid AGPL code, even for internal tools. Same license as Steel; the patent grant and NOTICE come with it. |
| Session cookies across a stop | "Continue where you left off" (`RestoreOnStartup: 1`): Chromium keeps session-only cookies and reopens its tabs | A stop or idle auto-stop otherwise logged out of every site whose login is a session cookie. It's Chromium's own mechanism and a common setting, so it changes nothing a page could hold against us; saving and restoring cookies ourselves would have missed sessionStorage and added a file of live tokens. |
| Agent input pace | Human by default (glide, scatter, hold, a typist's rhythm, from agweb's Motion model, MIT), `instant` per call; Visual mode times the glide for a 44 px target and scatters the landing as on an 8 px one (within about 3 px) | xdotool's jumps and 12 ms keystrokes are what behaviour scoring looks for, and pacing is behaviour, not spoofing. The cost is slower calls (a 500-character cap per call at human pace, 150 through MCP). Visual mode sees only a point, so a scatter sized for a 44 px target (up to about 18 px) would miss small checkboxes and dense rows, where a miss is the wrong action; an 8 px scatter stays on a 13 px box and still doesn't land on one pixel every time. Decided 2026-11-15 (PROJ-113); the landing narrowed to 8 px after review. |
| act's answer | What changed since the agent's last snapshot of the page (a diff of the page's items, at most 20 lines), on by default once there is one; `changes: false` turns it off | An agent otherwise acted blind or took a 4,000–20,000-character snapshot after each action, while most actions change a handful of lines. Items, not snapshot text: the snapshot's budget reorders and cuts lines, which a text diff would report. Decided 2026-11-15 (PROJ-114). |
| Script redirects after navigate | Polled, as the load is: every 100 ms for 300 ms after each load, the tab's document and `readyState`; followed for at most 15 s | A navigate that answered after the first hop of a sign-in bounce reported a page already going, and the agent's next read landed mid-navigation. CDP's lifecycle events would see a hop as it starts, not as it arrives, but need `Page.enable`, which the page tools never send; the price is that a hop slower than about 300 ms to arrive ends the wait early. |
| act and wait_for targets | `role=…[name="…"]` and `text=…` resolved against the accessibility tree and DOM snapshot a snapshot reads, exactly one visible match or an error listing up to 5 with refs; no CSS selectors | An agent that knows what to click had to snapshot first, and every navigation made its refs stale. Selectors run in the page would reach what the snapshot hides by design (hidden text, `aria-hidden` copies) and are a script in the page; the AX tree is what the agent sees, and an ambiguous target never guesses. |
| Div and span controls in a snapshot | An element with no role on which the pointer cursor starts, or with a tabindex of 0 or more, with text and no control inside, is a `generic "<text>"` line with a ref; its text isn't repeated when the line shows it whole | Many pages build buttons from divs with a click handler; the AX tree shows their text with nothing to click. The pointer cursor is what a person goes by, and only where it starts (children inherit it), so a list of 2,000 rows is one line, not 2,000. Playwright does the same. Decided 2026-11-15 (PROJ-124). |
| Download notices | Two listings of the downloads folder around the action, through `os.Root`, no CDP; a 40 ms look for a download to start (the caller's `download_wait_ms` when it sets one), a wait only while a partial download is there, and what finished between actions told with the next; REST in an `X-Downloads` header | Works the same in both modes, and Visual mode keeps nothing attached to the page. An action that downloads nothing is held up 40 ms at most (often 0, under act's changes or a screenshot). A header keeps 204 and the screenshot's 200 as they were. |
| Handing back at an address | `until_url` (at least 4 characters, not just `/`, `.`, `:` or a scheme), matched against the front tab's origin and path, watched with an HTTP GET of `/json/list` every 500 ms from when the person opens the link; the front tab must have navigated since; a fixed note | A person who stops at the signed-in page no longer leaves the agent waiting 15 minutes. `/json/list` is ordered by activation (measured), so its first page is the tab in front, read with no CDP connection at all; counting any tab let a background tab or popup end a handoff the person was in the middle of. Watching from the unlock, not the request, means nothing ends a handoff before the person has seen it. The query never counts: it carries OAuth codes and tokens, and the agent never learns the address. Decided 2026-11-15 (PROJ-118); revised the same day after review: front tab only, from the unlock, a minimum pattern. |
| Filled secrets in answers | Every value BrowserPier filled (PROJ-57) is replaced by `<hidden>` in every agent-facing answer, in every common encoding, as the last step: one wrapper for all REST routes and the MCP server's middleware, both checked by tests; per session, in memory, until it ends | A page echoes what it gets (a GET form's URL, a title, an error); the fence's field redaction can't see those, but BrowserPier knows the value it typed. agweb's `fill --secret-cmd` does the same. |
| Ad and tracker blocking | By host name in the container's egress forwarder, from domain lists the orchestrator downloads every 4 days, with a built-in allowlist of challenge providers; on for new profiles (Settings' default), off for existing ones (the migration); the admin sets it per profile, an agent can only turn it off for one session; a host the agent opens with `navigate` or a new tab is let through | Fewer tokens and less CPU on ad-heavy pages. Chromium can't run uBlock Origin (MV2), but every connection already goes through the forwarder by name, where blocking injects nothing into pages and needs no CDP, so Visual mode stays clean. Pages do see it as they see any DNS-level blocker's: a listed host's requests fail (see ANTI-BOT.md). Decided 2026-11-15 (PROJ-119): existing profiles keep how they ran, since blocking can break a page they rely on. The forwarder can't tell the top-level document, so "pages opened directly load" covers what BrowserPier opens; cosmetic filtering, scriptlets and redirects are out of scope. |
| Session recording | A separate low-rate pipeline (5 fps, 3/4 size, constant-quality H.264 in fragmented MP4 segments that play alone), not the live stream; per profile, off by default, the admin's alone; only while an agent acts (a 30 s tail), never while a person has control or a handoff is open (not a setting); stopped under the session manager's lock before Take control or a handoff returns; admin-only playback; not encrypted separately; 7 days, 2 GiB, 1 GiB left free, the profile holding the most gives up first | The live stream exists only while someone watches, serves one reader, runs at 30 fps and shows a person's typing. Only-while-acting costs less CPU and disk and shows the agent, not an empty desk. A key wrapped by the admin password would sit on the same disk as the password and the live cookies beside it. Still screens: rather than detect damage in X, the orchestrator ends a segment after 3 s of skip-frame-sized fragments and starts the next on the first larger one, judging box sizes only. Decided 2026-11-16 (PROJ-23, from the easi.run audit; ideas only, no code); built 2026-11-18. |
| Visual-mode page reading | AT-SPI tree, read-only, Visual sessions only: Chromium's accessibility on the browser's private session bus (the file chooser portal's, PROJ-152; one bus, not two) and `--force-renderer-accessibility=basic` from the browser's start, read by a godbus client in the entrypoint with one allow-list of read methods; refs of their own; click by ref through xdotool | Visual mode had only screenshots and guessed coordinates on the sites where it matters most. The accessibility tree is the page as assistive technology reads it, with no CDP attached, and reading it caused nothing the detectors see. API mode keeps today's setup: it has the CDP page tools. Fixed per session, never toggled, so a page sees one state. `basic` rather than the full mode: the same tree for the reader at a quarter to a half of the main-thread cost to heavy pages. Decided 2026-11-18 (PROJ-150). |
| WebGL renderer | Mesa llvmpipe through ANGLE's OpenGL backend (`--ignore-gpu-blocklist`), pages composited in software (`--disable-gpu-compositing`); no fallback, not spoofed. Decided 2026-11-17 (PROJ-148) | SwiftShader's renderer string is the one red line on bot.sannysoft.com and an item of CreepJS's "like headless"; llvmpipe is what GPU-less Linux desktops and VMs report. Measured on one amd64 host and a residential connection; arm64 and AppArmor profiles unchecked: sannysoft all green, CreepJS "like headless" 44% to 38%, BrowserScan and deviceandbrowserinfo unchanged; the same memory, less CPU (WebGL at 63 instead of 48 frames a second as measured, both a little high, since 63 is the 60 fps cap, scrolling a heavy page at a quarter of the CPU), and no new package, as xvfb already pulls Mesa in. A renderer that could change between starts would change the profile's fingerprint, so there is one. |
| Back/forward cache | Off (`--disable-features=BackForwardCache`): Back loads the page again instead of showing it at once from memory. Decided 2026-11-17 (PROJ-160) | Chromium kept a page the tab had left whole in memory for up to ten minutes, and nothing in a container tells it memory is short: a 200 MB page was still counted four minutes on, against the RAM limit that stops other browsers and refuses starts. Agents navigate a lot (search, result, back), and an instant Back is worth less to them than the memory. Measured on our image first (ANTI-BOT.md); the spare renderer, measured the same way, stays. |
| Many tabs | No tab cap; from 10 open tabs on, the page tools say how many are open (§8), and the agent closes what it's done with | A cap means closing tabs: in Visual mode that needs something watching targets, and no CDP client may stay attached there; a person in the live view or a handoff would see tabs vanish; and a sign-in popup past the cap would be closed, breaking a login, the product's main job. Revisit if tabs prove a real memory problem. |
| Address-bar search suggestions | Off, by managed policy (`SearchSuggestEnabled: false`) | Chromium sent successive prefixes of a typed address to the search engine's suggestion service, one at each pause, an http address's path and a token in it included, before the page opened. A policy covers agents' typing and a person's in the live view alike, with nothing in the input path. Pages can't see it; a person sees fewer suggestions (ANTI-BOT.md). Decided 2026-11-18 (PROJ-191). |
| Chromium sandbox | On, with a seccomp profile that allows user namespaces | Pages are untrusted; the container is a second boundary, not the only one. |
| GPU process sandbox | Chromium's GPU seccomp policy on, with Mesa kept single-threaded until it starts (`LP_NUM_THREADS=0`, `MESA_SHADER_CACHE_DISABLE=true`) and `--gpu-sandbox-failures-fatal=yes`. Decided 2026-11-18 (PROJ-165) | The GPU process parses what pages send it, and ran with the container's seccomp filter alone because llvmpipe's threads kept Chromium's sandbox from starting. The price is WebGL on one core: a light WebGL page at 29–34 instead of 63 frames a second (117–119% instead of 244% of a core), a scene that kept every core busy at 0.8 instead of 4.2 (107% instead of 568%), so up to the host's core count slower; idle and ordinary pages, memory and start-up are unchanged. Measured on amd64; arm64 is unchecked (PROJ-187). A GPU process that can't sandbox itself exits rather than running without it, and pages then get no WebGL. |
| Cloudflare challenge pages | The page tools spot one (the widget's `cf-chl-widget-` input) and say where its checkbox is on the screen and in MCP screenshot pixels, for a `/computer` click or a handoff; BrowserPier doesn't click it | The checkbox is in a closed shadow root in a cross-origin iframe, which the page tools can't see, and a CDP click doesn't pass; a native one does. Clicking by itself would make BrowserPier a challenge solver, which a person or the agent should decide on. Either pace hits the 21 px box: a human-paced click lands within about 3 px of the point. Decided 2026-11-15 (PROJ-120, for PROJ-25). |
| Desktop in the browser container | JWM with a 32-pixel taskbar along the bottom (a clock only); the browser window at 0,0, unframed, fills the rest | A bare Xvfb screen has no work area, which detection reads as headless. A real window manager reserves the taskbar's strip, so nothing is faked. At the bottom, the window stays at 0,0 and Visual-mode coordinates stay screen coordinates. ## 14. Roadmap

### v1: everything needed to run it daily, privately or on a VPS

- Browser image with the Chrome launch setup, basic cookie store and graceful shutdown
- Orchestrator core, auth with rate limits, agent API, WebRTC live view
- Auto-stop and RAM limit
- Handoff links with reasons, origin-only prompts and MCP elicitation
- Files: downloads and uploads
- Per-profile proxies with credentials, timezone and locale matching
- MCP endpoint with explicit session handles, untrusted-content fencing and Visual-mode actions
- Web UI (8 screens, see `design/`), encrypted profile export/import
- Generic docker-compose with HTTPS (Caddy), first-run setup, Umbrel app
- Anti-bot validation
- TURN support for viewers on UDP-blocking networks (planned for v1.1, done early): bundled coturn or your own

### v1.1: efficiency and reach

- Content endpoints: page to Markdown or readability text, screenshot, PDF (done, PROJ-20: see Page content)
- Token-efficient API-mode tools: accessibility snapshot with stable refs, find, batch, covered-element check (done, PROJ-21: see API-mode page tools)
- Seed a profile from your own Chrome: cookie and localStorage JSON export/import, so you don't have to log in again inside BrowserPier
- Navy-style logo
- A signed webhook when a person is needed: handoffs asked for, expired or cancelled by wrong PINs, and optionally failed browsers, for Slack, Discord or your own endpoint (done, PROJ-157: see deploy/README.md, Notifications)

### Later: useful, not urgent

- Test a proxy before a browser uses it: exit IP, country, time zone and languages, lookup time (done, PROJ-154: see §3)
- Two-step sign-in for the admin (done, PROJ-162: authenticator app and recovery codes, see §6). Passkeys would be a follow-up; they need a fixed HTTPS origin.
- MP4 recording of what agents do, for replay (done, PROJ-23: a pipeline of its own, not the live H.264 stream; see Recording in §3)
- Automatic login-wall and CAPTCHA detection that triggers a handoff

### Beyond v1: productization (vision, not committed)

v1 stays fully self-hosted on one box. The aim right now is to ship a complete, solid FOSS product, not to compete with hosted providers or chase uniqueness; good ideas from other projects are welcome. This section is where BrowserPier could go afterwards. Nothing here is scheduled; it exists so v1 doesn't close doors.

**Groundwork that's cheap in v1**
- Put the browser lifecycle behind a `Runner` interface (start, stop, and optionally suspend/resume, for a profile) with local Docker as the only v1 backend.
- Put profile storage behind a `ProfileStore` interface with a local folder as the only v1 backend.
- Both are internal Go interfaces: no new features, no new config.

**Stage 1: FOSS adoption**
- One-line install; templates for Umbrel, CasaOS, Unraid and Coolify.
- Python and TypeScript SDKs; ready-made integrations with browser-use (the first example: it connects over CDP), Stagehand and Playwright.
- Docs and example agents ("log into X once, then automate it").

**Stage 2: teams and several machines** (likely the first paid tier)
- Postgres instead of SQLite; a distributed lock so "one running browser per profile" holds across machines.
- `ProfileStore` on S3-compatible storage (S3, R2, MinIO): profile packed, encrypted and uploaded on stop, restored on start. Chrome caches (Cache, Code Cache, GPUCache) are left out so snapshots stay small and cold starts fast.
- `Runner` backends for remote Docker hosts and Kubernetes.
- Multiple users with roles, SSO (OIDC), an audit log, profiles shared within a team.
- Team handoff queue: "google needs a human", whoever is free takes it; push notifications or a small mobile app.

**Stage 3: hosted product**
- Billing per browser-hour plus profile storage; regions; bring-your-own or provided proxies.
- Freeze/resume browsers from memory snapshots instead of stop/start: an idle browser costs disk only and resumes in milliseconds with its tabs open. Candidates: Unikraft Cloud (what Kernel uses for headful Chromium) or Firecracker on our own bare metal (needs KVM).
- Abuse prevention from day one: sign-up checks, rate limits, domain blocklists. Hosted browsers attract spam and fraud.
- Trust: profiles encrypted with customer-held keys, EU hosting and data residency.

**Ideas that grow out of the core** (not a race with anyone; just what persistent profiles and handoffs make possible)
- Profile health: detect when a profile has been logged out and ask a human to log in again before an agent hits the wall.
- Password manager integration (Bitwarden, 1Password) for re-logins without exposing secrets, with domain-bound secrets: a credential can only be typed on the domains it's allowed for (PROJ-57; what it fills is already kept out of agents' answers, PROJ-125).
- Session recordings and an audit trail of who, agent or human, did what in which account.
- Handoff as a product: the phone and PIN flow, team routing, response-time stats.

**Business model:** open core. The self-hosted single box stays free; team features (Stage 2) paid or source-available; a hosted cloud for people who don't want to run it.

**Landscape to watch:** Browserbase (hosted), Steel (open source, Apache 2.0), Kernel (hosted on Unikraft; its browser images are open source under Apache 2.0, with headful Chromium and a WebRTC live view), Cloudflare Browser Run (hosted; every request carries signed bot-identification headers, so it doesn't suit anti-bot use), browser-use (an open-source agent library that drives any CDP browser, so a client of BrowserPier rather than an alternative; its hosted Browser Use Cloud keeps cookies and localStorage per profile, syncs logins from a local browser and has a live preview).
